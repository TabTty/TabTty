## What to build

Implement the six whole-codebase architecture designs finalized on 2026-11-18: recording finalization/waiting ownership (Q1-Q3), terminal-payload transport ownership (Q4-Q6), verified file publication/reconciliation (Q7-Q11), vault management-operation ownership (Q12-Q16), shared SSH channel invariants (Q17-Q19), and shared grapheme ownership with amended paste behavior (Q20-Q27, including final Q23 acceptance). The independent aggregate-paste Q28/Q29 branch is superseded.

The plan contains 26 implementation slices and one focused cross-owner integration-verification slice. It builds on the current Rust terminal, file-operation, broadcast, history and closure paths, rather than recreating those features. The related [earlier architecture map](https://github.com/TabTty/TabTty/issues/4) and [Rust terminal/closure map](https://github.com/TabTty/TabTty/issues/16) remain unchanged. Their issue state alone is not evidence of missing or completed runtime behavior; each slice establishes its own attributable evidence for the current accepted contract.

## Acceptance criteria

- [ ] Ordinary callers use the accepted complete operations with immutable observations. Keep terminal semantics in Rust, application/session/transport/file coordination in C#, and presentation/localization in WPF resources. No new generic provider framework, managed terminal fallback, external SSH client or macro runtime is introduced.
- [ ] Recording owns its file completion and protected wait policy; transports and shared SSH channels distinguish protocol results, ordered consumption, definite submission and actual release. Complete-operation cancellation and cancellation of observation remain distinct.
- [ ] Profile/store/vault publication reports actual target and preservation facts and adopts only under the accepted proof rules. Reconciliation never repeats mutations. Vault operations keep shared unlock, explicit initialization/archive, selection-role atomic visibility and original secret lifetimes.
- [ ] Unicode uses the accepted pinned definitions and authoritative owned spans. Long received graphemes retain their first 256 scalars while full-stream break state continues; outbound input remains exact except an explicitly stopped scalar/codec-safe prefix.
- [ ] Retain a configurable per-paste maximum of 512 MiB by default, measured in actual preconversion UTF-16 text bytes. Confirm otherwise valid within-limit clipboard text for CR/LF or strictly more than 1 KiB. Use shared-source accounting in the existing 4 GiB application envelope, the existing 2 MiB/256-unit input-work allowance per target and the original 30-second broadcast preparation deadline; add no independent aggregate setting or 80% rule.
- [ ] Every slice exercises a complete real consumer path with independent expectations and its relevant accepted verification cases. Preserve existing English/Japanese text, system language/theme behavior, file-backed connection profiles, supported locations and the accepted Microsoft/OpenSSL/Rust dependency boundaries.
- [ ] Before implementation, record a reproducible current baseline and recheck affected authentication/vault/SSH guidance as required. Freeze the specified finite internal ownership limits in versioned implementation policy and test configured boundaries; do not invent new product preferences or claim measured capacity from design accounting.
- [ ] Keep existing callers working during exercised prefactoring and staged migration, then remove retired recipes after their last consumer moves. Each implementation slice validates its delivered path; the cross-owner verification ticket adds combined race evidence without deferring those checks or replacing the existing deployment/performance acceptance issue.
- [ ] Publish children with ready-for-agent and wayfinder:task labels, native sub-issue relationships and native blocked-by edges. Work only the unblocked frontier after implementation is separately authorized. Do not close, relabel or modify the earlier parent issues as part of publication.

Publication records the approved ticket plan and does not start implementation or prototyping; those require the user's separate explicit request.
