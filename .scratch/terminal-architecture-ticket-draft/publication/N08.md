## What to build

Support cp936, cp949, and cp950 receive and strict transmit behavior in actual native terminal sessions, independently of the selected encoding in the other direction.

## Acceptance criteria

Consultation outcome, 2026-11-17: the user approved the specified shared recovery and exact whole-send policy. Use explicit native Microsoft CP936/949/950 conversion with that policy. Static assessment found no additional identity-specific table or patch; native equivalence remains acceptance work. Consult before adopting any newly required mapping correction, replacement data or custom behavior. Do not reconfirm the approved shared scope or silently substitute a near-equivalent encoding. These design decisions do not authorize implementation.

- [ ] Preserve all three profile identities and exact accepted mappings using permitted Microsoft sources/offerings, with recorded data provenance.
- [ ] Compare defined/undefined shaped pairs and standalone-byte mappings against independent expectations. Cover every byte split, invalid-continuation prefix replacement and byte reprocessing, pending-prefix EOF, chunk boundaries, and malformed-to-control resynchronization; valid delimiter-looking trail bytes remain part of their unit. Verify supported-platform availability.
- [ ] Preserve independent source partials and initial-state rules. Raw bytes remain unchanged while decoded C1 scalars do not execute VT commands.
- [ ] Strictly preflight outgoing units, reject substitutions and unmappable input without live encoder changes or prefix sends, and preserve accepted local-echo boundaries.
- [ ] Verify receive, display, send, and recording through the actual profile/session/adapter path with independent expected bytes and text, including resource rejection. Add no managed codec callback or temporary handoff.
