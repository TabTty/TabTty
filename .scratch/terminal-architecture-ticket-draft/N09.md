# Use native CP932 and EUC-JP terminal encoding

## What to build

Support exact CP932 and EUC-JP receive/transmit behavior in actual native sessions, including the accepted Japanese table, extension duplicates, kana, and malformed-unit rules.

## Acceptance criteria

Consultation outcome, 2026-11-17: the user approved native Microsoft CP932 as the planned base mapper, with Rust owning the selected JIS/EUC repertoire and exact reverse choices, optional CP932 SO/SI receive handling, EUC SS2/unsupported SS3, shared malformed/control recovery, and complete-send preflight. Do not infer a CP932 SO/SI transmit feature. Native API equivalence remains acceptance work. Existing managed CP932 overrides are excluded from this approval; any concrete native mapping mismatch and proposed correction require separate consultation. Do not reconfirm the approved scope. These design decisions do not authorize implementation.

- [ ] Preserve the specified CP932 mapping vectors. For the JIS/EUC-compatible 94-by-94 table, exclude undefined cells and the specified private-use mappings outside that grid, and select the smallest adopted row/cell for duplicate reverse mappings. Do not apply those grid exclusions to ordinary CP932 support.
- [ ] Implement accepted CP932 kana and EUC SS2 behavior; treat a well-shaped unsupported SS3 unit as one replacement. Verify every representative byte split, invalid continuation reprocessing, EOF, and independent receive sources.
- [ ] Verify the accepted extension vectors and exact distinctions such as U+301C versus U+FF5E, with no best-fit or normalization substitutions.
- [ ] Exercise independently configured receive/transmit, strict rejection, local echo, display, and recording through the real profile/session path without managed codec callbacks or temporary codec handoff.
- [ ] Preserve the existing strict SFTP filename behavior where codec services are shared, without expanding file-operation scope. Record mapping provenance and keep the common shared interpretation/admission contract.
