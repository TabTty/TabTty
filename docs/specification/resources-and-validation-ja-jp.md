# リソースの計上、受け入れ、配布条件

2026-11-10 時点の仕様。合意済みの Q124、Q146～Q148、Q159～Q160 に基づく初期の技術的制限であり、実測済みの容量ではない。この時点でベンチマーク、実行時テスト、試作、依存関係のインストール、リリースは未実施。

共有予算と維持する貼り付けごとのサイズ・確認要件を組み合わせた Q26 を含む、合意済みのコードベース全体のアーキテクチャ Q20～Q22、Q24～Q27 により、以下の書記素保持と貼り付け受付を変更する。その後の独立貼り付け予算案は置き換えられた。候補 6 全体の最終認識合わせ Q23 は 2026-11-18 に完了した。設計上の契約であり、実装や実測容量を示さない。

## 初期の内部予算

| --- | --- |
| 端末グリッド | 2～1024 列、アクティブ行 1～512。アクティブ行は接続時に取得した保持行数以下とする。余ったビューポート領域は使用しない。 |
| 保持行 | 合意済み範囲 100～100000、既定 5000。モデルごとの通常画面のアクティブ行とスクロールバックの合計。別の予算を満たすための早期除去は行わない。 |
| 端末状態と共有貼り付けの合計枠 | 端末状態はセッションごとに 2 GiB を維持する。既存のアプリ全体 4 GiB 枠に、切断後も保持するタブと両モデルに加え、共有貼り付け本文・共通作業・実際の送信先別貼り付け作業を一度ずつ計上する。 |
| 状態の計上 | 割り当てたセルスロットごとに最低 64 バイト。所有する UTF-16 テキストの容量、行、クラスタ、由来、インデックスの容量、ネイティブモデルのバッファーを実割り当てサイズで加える。実際に所有権を共有する不変バッファーだけを一度にまとめて計上する。 |
| 保存するクラスタ表記 | 先頭 256 Unicode スカラー値を保持する。以後の継続も入力全体の上限付き分節状態に反映し、長さだけでセッションを失敗させたり人工的なクラスタ境界を作ったりしない。幅は保持した接頭辞から求める。 |
| 受信キュー | セッションごとに 2 MiB と 1024 項目、アプリ全体で 128 MiB。未完了の読み取りバッファーと受信元の不完全な単位を含む。 |
| CSI/ESC パーサー | シーケンスごとに 4096 バイト、主パラメーター 32、各サブパラメーター 16。数値演算を検査する。 |
| 文字列制御 | OSC/DCS/SOS/PM/APC 文字列ごとに最大 1 MiB を消費し、上限付きの認識済みフィールドだけを保持する。超過は明示的なリソース障害。 |
| 入力 | 既存のセッションごとのキュー・事前検査・送信作業 2 MiB とキュー単位 256 を、通常入力と送信先別の貼り付け作業で共有する。既存の別途予約するエンコーダー・ブラケット終端容量を維持する。 |
| 共有貼り付け本文 | 不変の原文一つと共通の解析・プレビューをアプリ全体 4 GiB 枠で所有する。物理的な共有は一度、実コピーと重なりは別々に計上する。 |
| クリップボード貼り付け受付 | 1 回あたりの設定可能な本文上限は既定 512 MiB。送信先の符号化前の実 UTF-16 本文バイト数で数え、終端 NUL、割り当て余白、別のクリップボード形式を除く。符号化後のペイロード上限は別に設けない。有効で本文上限内のテキストは CR/LF を含むか 1024 バイトを超えたら確認する。 |
| 自動応答 | セッションごとに 64 KiB とキュー内の 128 応答。入力予算に含める。実行中の貼り付けに割り込まない。 |
| ログペイロード | 合意済み上限は記録グループの全形式合計で 8 MiB と 4096 項目、アプリ全体で 256 MiB。キュー内、ステージング済み、処理中、失敗したが所有中のデータも計上し続ける。 |
| ログ I/O | ファイルごとに未完了の書き込み一つ、アプリ全体で最大 128。失敗またはキャンセル済みの以前のパートグループはセッションごとに一つ、アプリ全体で 32。空きがなければ再試行は待機するか失敗を表示する。 |
| ファイル準備 | アプリ全体で同時に四つ。キャンセル済みで未完了の準備は最大八つ。キャンセルのたびに新規ワーカーを繰り返し作らない。 |
| 起動キュー | 保留中のファイル起動 64 件。超過分の新規要求は容量エラーとし、既存セッションを閉じない。 |
| バックグラウンド CPU 作業 | 端末処理ワーカーは最大四つ、検索と強調は最大二つ、高負荷の KDF やインポートのワーカーは実行中一つ。UI、受信、ログの所有者は正規表現を実行しない。 |
| 再計算可能なキャッシュ | アプリ全体で検索と強調の範囲 64 MiB、グリフとレイアウトのスナップショット 128 MiB。端末内容を除去する前に、キャッシュを捨てて再計算する。 |
| UIA スナップショット | アプリ全体で一時スナップショット 64 MiB。要求された結果全体の容量を確保できなければ、プロバイダー呼び出しを明示的に失敗させる。GetText の暗黙の切り詰めやページ分割は行わない。 |

割り当ての計上は受付と会計の規則である。CLR、WPF、OS、グラフィックス、ネイティブ暗号処理、ドライバーのオーバーヘッドが異なるため、プロセスのワーキングセットの厳密な上限は示さない。可能なら変更や割り当て前に予約する。予算が逼迫したら、先に再計算可能なキャッシュを捨て、新しい作業を拒否または延期する。既存の端末状態で解消不能な障害が起きた場合は、該当セッションだけを終了し、利用可能な出力を保持して取得が不完全であることを明示する。保存済みの保持行数、エンコーディング、ハンドシェイク、記録形式、内容を黙って変更しない。プロセス全体の致命的な OOM からの回復は保証しない。基準となる 20 タブの通常テキストは計上上の予算に収まる。実際のオーバーヘッドは測定する必要がある。

TCP/SSH はバックプレッシャーが働く間、新しいペイロードの受付を止め、予算が空けば再開できる。シリアルは選んだハンドシェイクと明示的なオーバーラン方針に従う。損失のないバックプレッシャーは仮定しない。パーサーや端末状態の割り当てに解消不能な障害が出た場合は、正常な接続と表示したまま無期限に待機しない。障害の影響は限定する。ログ I/O 障害では記録を止め、正規表現のタイムアウトでは該当ルールを一時停止し、検索やキャッシュの逼迫は再計算可能な処理だけに影響する。長い書記素の継続は上限付き保持の方針に従い、保存接頭辞が 256 スカラー値に達しただけでは障害にしない。観測は保持接頭辞を連結して再分節せず、正本の保存区間を維持する。

明示的に設定可能とした 1 回あたりの本文上限を除き、この表はバージョン管理する内部方針。新しい設定 UI は設けない。測定後の調整では、合意済みの機能と障害時の挙動を維持する。約束済みの範囲、保持行数、受け入れ目標を引き下げるには明示的な仕様決定が必要。

## 共有貼り付け本文と既存の入力作業

復帰した当初の Q26 方針では、既存のアプリ全体 4 GiB の計上枠に端末状態と貼り付け所有データを含める。セッションごとの端末状態 2 GiB は維持する。不変の貼り付け原文一つと共通の解析・計画・索引・プレビューをアプリ単位で所有し、送信先は全文を別々に保持せず参照する。各送信先の入力枠へ原文全体を重ねて計上しない。実コピー、取得・圧縮時の重なり、ネイティブ・managed 間の受け渡し、所有中のプール、送信先別作業、遅延した後処理は実際の所有容量で計上し続ける。物理的に所有を共有する割り当てだけを一度にまとめて数える。

各送信先の既存の入力枠 2 MiB・256 単位は、通常入力と貼り付けのキュー・事前検査・送信作業を合わせて制限する。別の貼り付け用 2 MiB 枠は追加しない。実際の送信先別貼り付け作業はアプリ全体 4 GiB 枠にも属する。複数段階の受付制約であり、物理的な割り当てを二重に作るものではない。既存のエンコーダー・ブラケット終端予約を維持し、その実容量もアプリの枠へ含める。ローカルエコーの端末状態は引き続き端末状態の受付に従う。他のリソースは既存の予算と所有を維持する。

本文全体のコピーや他の所有領域の拡張前に、制御可能な容量を予約する。コピー前にサイズを調べるか、予約した領域内で上限付き取得を行う。外部クリップボード提供元はサイズが分かる前にデータを生成する場合があり、即時キャンセルは保証しない。遅れて返る結果の所有を制限し、キャンセルのたびに所有者から切り離したワーカーを増やさない。プレビューはスカラー境界を守る上限付きページで不変本文の全体へアクセスできるようにし、全文を単一の表示用コピーへ渡したり、全書記素の索引を無制限に作ったりしない。以前の符号化済みペイロード 1 MiB による拒否を、設定可能なクリップボード本文上限（既定 512 MiB、536870912 バイト）へ置き換える。送信先の符号化前の実 UTF-16 本文をコード単位あたり 2 バイトで測り、終端 NUL、割り当て余白、別のクリップボード形式を除く。実際の CR/LF を正規化せず数える。保存済み上限は操作開始時に取得し、後の設定変更でその操作を切り詰めたりキャンセルしたりしない。上限ちょうどは検証と容量次第で受け付け、超過は操作全体を拒否する。符号化後の上限は別に設けない。[設定の永続化](persistence-and-windows-ja-jp.md)を参照。実際の所有容量のピークは共有の合計枠と既存の作業上限へ収める必要があり、本文設定は空き容量や準備時間を保証しない。

最初の本文やブラケット開始マーカーを送る前に、固定した全送信先で入力全体を検証し、残りの送信、中止、正常な終端処理に必要な作業容量のピークを予約する。送信先ごとの符号化済み全文は保持せず、上限付きの作業領域を再利用する。確認画面で送信を選んでも受付は保証しない。準備や予約が失敗すれば全送信先に何も送らない。同時送信準備の既存の 30 秒期限を維持し、必要な確認の後、確認が不要なら準備開始時から計る。ダイアログで利用者が使う時間を含めず、再試行で期限を再開始しない。最後の送信先の変換後と最初の送信確定直前にもキャンセルと期限を検査する。

元の期限内で既存の上限付き拒否・延期・容量待ちを使う。容量待ちで複数セッションのロックを保持せず、部分予約を解放して同じ期限内で再試行し、循環待ちを作らない。新しい待機列、全貼り付けの直列化、別操作の本文除去、入力の切り詰め、一時ファイルへの退避は追加しない。独立した端末状態、トランスポート、OS 割り当ての失敗は既存方針を維持し、貼り付けの受付逼迫だけで正常なセッションを閉じない。

実割り当て容量と将来の予約は別々に計上し、予約消費時は割り当ての計上へ置き換えて二重計上しない。送信開始後と中止・終端処理は確保済み作業領域を再利用し、別操作はその容量を奪えない。キャンセル、ウィンドウ閉鎖、観測者の離脱、操作の失効だけでは返却せず、ワーカー・結果・書き込みが実際に所有権を解放した時点まで計上する。共有の 4 GiB は計上上の枠であり、厳密なプロセスのワーキングセット上限、割り当て成功、OOM 回復の保証ではない。独立した貼り付け領域、空きメモリ割合の規則、合計上限の設定は設けない。

人間のクリップボード貼り付けの確認は[入力契約](session-and-recording-ja-jp.md)に従う。取得した本文上限内で他の条件も有効なテキストが、CR/LF を含むか 1024 バイトを超える場合に同じ確認を表示する。両条件を満たしても一つの確認とする。CR/LF がなく 1024 バイト以下なら、サイズや設定上限との一致だけでは確認しない。不正な入力や本文上限超過は一部も送信せず拒否する。AI が渡す貼り付けは [AI コラボレーション](ai-collaboration-ja-jp.md)の独立した UTF-8 256 KiB 要求上限と認可・確認契約を維持する。解析の共用でこれらの外部上限を除去したり、通常の AI 要求・トランスポートバッファーを貼り付け所有へ移したりしない。

## スケジューリングと不変の結果

一つのセッション内は順番に処理し、約 5 ms または 1024 操作のバッチの間で実行を譲る。これはスケジューリング目標であり、ネイティブ処理を途中で打ち切る期限は設けない。セッション間を公平に処理する。UI の再描画要求は最新スナップショットにまとめ、可視タブごとに毎秒最大 60 フレームを目標とする。途中の描画を省いても端末操作やログデータは破棄しない。非表示のタブと最小化されたウィンドウのタブは、定期スナップショット、描画、強調表示を止めている間も、受信、端末状態の更新、ログ記録を続ける。再表示時に最新状態を提示する。

強調表示はテキストの更新が約 500 ms 止まった時点で行う。タブ切替やスクロール時は停止を待たず、可視範囲を評価する。出力に追従する自動スクロール時はテキストの更新が止まるまで待つ。行とセットの組ごとにキュー内のリビジョンは一つでよい。未着手の旧作業は置き換え、セッション、内容、セットのリビジョンで古い結果を破棄し、置き換え前の一致履歴を保持しない。合意済みの 100 ルール、パターン 4096 単位、行 65536 単位、列挙する一致 4096 件、検索タイムアウト 50 ms、協調的な作業区間約 20 ms を維持する。長すぎる行や一致が多すぎる行に部分的な強調を重ねない。

端末タブは、適用中のハイライトルールセットの版と、そのセッションで停止中のルールを管理する。どのペインでタイムアウトしても、そのルールは同じタブの全ペインで停止し、後から開くペインにも停止が適用される。一度の停止につき通知は1回とする。同じセットを使う別のタブは、それぞれの停止状態を維持する。各ペインは自分の可視範囲を評価して描画結果を保持する。評価開始後にルールセットの版や停止状態が変わっていれば、遅れて届いた結果を破棄する。

ルールを停止したら、そのルールによる強調を全ペインから直ちに外す。残りのルールから正しいスタイルがすでに確定している範囲には、そのスタイルをすぐ適用する。確定できない範囲は、再評価が終わるまで受信した ANSI 色を含む端末本来の属性で表示する。再評価中も受信と描画を続ける。

どのペインから「強調ルールを再開」を実行しても、そのタブで停止中の全ルールを再開する。停止したルールの正規表現か「大文字と小文字を区別しない」を変更して保存すると、そのルールの停止を解除する。名前、スタイル、順序、有効・無効だけの変更や、他のルールの編集では停止を維持する。評価の対象は有効なルールに限る。新しい端末セッションは停止中のルールがない状態から始まる。

検索は文字列検索とし、既定では大文字と小文字を区別しない序数比較を使う。対象は通常画面の保持内容に限り、検索文字列は UTF-16 で 1024 コード単位以下。一致のキャッシュは最大 10000 件とし、上限に達してもキャッシュ外を上限付きで移動できる。同じリビジョン、キャンセル、ワーカーの方針で作業量を制限する。端末内容、選択とコピー、ログ、トランスポートは検索結果を待たない。

［次へ］［前へ］では、一度の走査で移動先を探し、強調表示する一致も集める。走査は上限付きで進め、指定した方向で最も近い一致が確定したら、操作したペインでその一致を表示して枠で囲む。折り返した先の一致に移動するときは、操作の起点からその方向の端までに一致がないことを先に確かめる。残りの強調表示と件数を更新しても、どのペインも再スクロールしない。件数が未確定の間は検索中または集計途中であることを示す。検索条件や端末内容の更新で古くなった結果は破棄する。

端末タブごとに一つの検索担当が、検索文字列、大文字・小文字の設定、実行中の検索、共有する一致範囲とそのメモリ予約を管理する。現在選んでいる一致は各ペインが持つ。未選択の場合、［次へ］は操作したペインの表示範囲の先頭から、［前へ］は末尾から検索を始める。

検索欄を閉じると検索を取り消し、一致の強調を消して、保持結果用のメモリ予約を返す。同じタブで開き直せるよう、検索文字列と大文字・小文字の設定は残す。タブを閉じて取り除くと検索担当は終了し、保持結果を直ちに解放する。遅れて届いた移動通知や検索結果は破棄する。取り消した検索のワーカー枠と一時作業領域は、その検索が実際に終了した時点で返す。タブの移動では検索状態を保つ。

タブ全体で共有する最大1万件のキャッシュには、各ペインに見えている一致を優先して保持する。キャッシュ外の一致にも移動でき、現在の一致はそのペインで枠を表示する。総数がちょうど1万件なら確定した件数を示し、1万1件目を確認したら `10,000+` と表示する。

[SFTP の契約](file-transfer-ja-jp.md#file-management-deadlines-and-limits)は転送バッチ、チャネルバッファー、要求、一覧と計画のメタデータ、ローカルプロバイダー呼び出しに別の上限を定める。バルク転送は端末チャネルと認証済みトランスポートを共有する。端末の対話応答目標と上記の端末および記録の予算を維持する。

## バックグラウンド受信の効率化目標（2026-11-14）

追加の 1～6 受信タブの負荷では、非選択タブと最小化ウィンドウの継続受信を高速化し、アプリ全体のメモリを約 1 GB に収めることを目標とする。基準の保持行数 5000 行と 3 種類すべてのログを有効にして測定する。表示履歴の蓄積、非表示での受信、EOF とログ排出、復帰までを含め、private memory と working set のピークを記録する。GB は十進表記（1,000,000,000 バイト）とし、ピークがこの基準を超えたか明記する。端末の計上量やコア単体の測定でアプリ全体を代用しない。

これは負荷条件を限定した追加の最適化目標であり、プロセスの上限強制や、内部の受付予算と既存の 20 セッションの受け入れ負荷を置き換えるものではない。達成のために保持行数を減らしたり、出力を破棄したりしない。初回の C# 測定結果と残るメモリ差は[実装状況](implementation-status-ja-jp.md)に記録する。

## 決定的な性能負荷

合意済みの基準は構成を記録した Windows 11 x64 PC、CPU 4 コア以上、RAM 16 GiB、ローカル SSD。二つのウィンドウでそれぞれ一つのタブを選択する。接続確立後の暗号が aes128-gcm@openssh.com の SSH セッション 20 個、120×40 のグリッド、各 5000 保持行、ログ 3 形式をすべて有効にする。参照機の条件であり、新しいインストール要件やタブ数の上限は設けない。

UTF-8 で 4096 行の繰り返しサイクルを定義する。表の `dddd` はゼロ埋めした 4 桁の十進インデックス 0000～4095、`F` は厳密に ASCII の X 96 個。バックスラッシュによるエスケープは実際の CR/LF/ESC バイトを表す。

| インデックスを 6 で割った余り | 行の厳密な構成 |
| ---: | --- |
| 0 | `INFO status index=dddd F\n` |
| 1 | `WARN count=dddd F\r\n` |
| 2 | `ERROR code=dddd F\n` |
| 3 | `status index=dddd 接続状態を確認しています F\n` |
| 4 | `\x1B[31mERROR\x1B[0m status index=dddd F\n` |
| 5 | `progress count=dddd 10%\rprogress count=dddd 100% F\r\n` |

名前付きプレースホルダー `dddd` と `F` だけを置換する。他の空白と文字はすべてリテラル。内容を変化させたりランダム化したりせず繰り返す。論理行の途中に待ち時間を入れない。トランスポートのチャンクはバイトストリームを変えずに 1/7/64/4096 バイトの順で分割する。将来のフィクスチャ生成器は、得られたペイロードのダイジェストと厳密な符号化済みサイクルをテストレポートとともに保存する。

セッションごとに、`INFO`、`WARN`、`ERROR`、`code=[0-9]+`、`count=[0-9]+`、`[0-9]{4}`、`status`、`progress`、`接続状態`、`X{16}` の十個の単純なパターンを使う。すべて有効にして大文字と小文字を区別し、それぞれ明示的な固定色を指定する。端末ペイロードの合計実測値を毎秒 1,048,576 バイトとする。均等配分と一つの高負荷な生成元（残り 19 セッションも接続を維持）の両方を実行する。保持範囲が埋まってから各負荷を 30 分間測定する。受信ペイロードバイト数をトランスポートのバイト数や生成文字数で代用しない。

各実行で少なくとも 600 回のローカル操作を決定的な 3 秒間隔で予定し、タブ選択、入力受付、ローカルメニューの開閉を順に繰り返す。ディスパッチャーでの待ち時間を含め、元の入力時刻から、有効で最新のビューポートの表示またはローカルキューやコントロールでの受付までを測る。接続先のエコーや RTT は含めない。p95 は 100 ms 以下とし、最大値と長い停滞も報告する。過負荷ではキャンセルや切断の受付の p95 を 250 ms 以下とし、トランスポートやファイルの完了にかかる時間とは区別する。キューのピーク、リソース拒否、欠落した出力、ログ状態、実メモリ、CPU、ストレージを記録する。目標未達は解決が必要な失敗とする。出力の破棄や基準の黙示的な緩和は認めない。この時点で結果はない。

SFTP の送受信と並行して同じ端末応答目標を検証する。共有接続での転送の停滞と鍵再交換を含める。Raw ログを端末バイト列だけの期待ダイジェストと照合し、転送のリソース使用量は個別に報告する。[SFTP の受け入れケース](file-transfer-ja-jp.md#acceptance-cases)を参照。

## 実装とリリースの条件

初期の基盤は C#/WPF/.NET 10 LTS、自己完結型 x64 ZIP 配布、公式 Microsoft と OpenSSL ライブラリ、用途を限定した bcrypt_pbkdf の例外。OpenSSL 3.5 LTS はセキュリティ修正のサポート対象版を使う。実装開始時にネイティブバイナリ、ソース、データのハッシュとライセンス通知を固定する。必要な再配布物とネイティブ依存関係を同梱し、クリーンなサポート対象 PC に別途インストールを求めない。ネイティブ呼び出しは管理下の範囲を絞ったアダプターを優先する。作業ディレクトリや管理されない検索パスから暗号プロバイダーやライブラリを読み込まない。

Windows 11 ビルド 22000 から利用可能な API を基準にし、必要な場合はパッケージに最小値を宣言する。配布時にサポートするエディションとリリースは、Microsoft と選んだ .NET バージョンのサポート対象でもあること。API の可用性と製品サポート期間は個別に確認する。ARM64 は任意で、提供する場合は対応するネイティブバイナリとテストが必要。

明示的な承認後に、機能を縦に通す段階で実装する。セッション、コーデック、端末、記録の純粋な契約と決定的なテスト、WPF のプロファイル、設定、タブ、アクセシビリティの統合、Telnet とシリアル、暗号と vault と独立した鍵ベクトル、SSH のトランスポート、認証、チャネル、最後に機能横断の障害と性能の検証。段階は作業順の指針であり、初期リリースの範囲を縮小しない。ユーザーファイルを書き込む前にバージョン付き形式に照らしてシリアライザー定数を固定する。不一致があれば契約を明示的に訂正し、互換性のない v1 を暗黙に作らない。

初回 ZIP リリース前に、受け入れマトリックスに合格し、独自 SSH と vault とネイティブでの秘密情報処理の独立レビューを終え、クリーンな PC への配布を検証し、依存関係と OS のサポートバージョンを記録して、再現可能なパッケージと保守手順を用意する。ZIP の更新は明示的な手動フォルダー置き換えとし、ユーザーデータはプログラムファイルの外に置く。新しいストアを破壊するダウングレードは拒否する。アプリの更新機能、自動アップロードやテレメトリ、秘密情報を含むクラッシュダンプ、マクロランタイムは導入しない。セキュリティ勧告や依存関係の更新には、レビュー済みの再ビルドと回帰検証が必要。同梱ランタイムは自動更新されない。

ZIP を作成する前に、信頼したビルド環境が記録した OpenSSL ソースのバージョンと SHA-256 をプロジェクトの固定値と照合する。さらに、同じ記録にある二つの出力ハッシュを、同梱する OpenSSL DLL と秘密鍵インポート用ライブラリの実ファイルと照合する。記録がない場合や照合に失敗した場合は ZIP の作成を中止する。照合したビルド記録を ZIP に同梱する。

将来の Store リリース前に、発行元とパッケージの ID、署名、関連付けの宣言、パッケージ版のデータ場所の解決、ZIP から MSIX への移行、アンインストール時の保持、認証を確定する。保存と起動は論理上の所有者の内部に置き、パッケージ化でセッションやファイルの識別を変更せずに済むようにする。仕様や初回 ZIP の準備完了による Store 公開の承認はない。

実装準備完了は、製品の決定、観測可能な契約、初期予算、検証計画を記録し、開発を妨げる未回答の決定事項がない状態を指す。コードの存在、ベンチマークの合格、独立レビューの完了、リリースの準備完了は個別に確認する。開発開始にはユーザーの明示的な依頼が必要。
