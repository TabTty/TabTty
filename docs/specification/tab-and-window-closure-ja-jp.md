# タブとウィンドウの閉鎖設計

担当範囲と一括・自動閉鎖の動作は、2026-11-16 の[アーキテクチャのヒアリング](../drafts/terminal-architecture-deepening.md) Q9-Q10 で合意した。
これは目標設計であり、実装済みの動作や新しい検証結果ではない。Q11 の名前付き完結操作と、Q13 の失敗結果・待機中止後の所有は合意済み。Q12a-Q12b で、確認中の通常の進捗を受け入れ、ウィンドウ閉鎖が先行するタブ閉鎖を待ち合わせる方針も合意した。Q14 では例外的な対象変更時の結果と候補全体の最終認識合わせを完了した。記録・パーサー・閉鎖の3つの設計は実装準備完了である。実装・試作には別途の依頼が必要となる。

## 担当範囲

C# のアプリケーション module が、明示的なタブ／ウィンドウ閉鎖の操作全体を所有する。対象の特定と確認、既存の確認判断の取得、対象・世代・所有権の検証、各所有者への終了依頼、待機・失敗・許可された後処理引継ぎ、既存の配置・アプリ調整を通じた表示削除までを担当する。
ユーザーによる一括閉鎖と自動閉鎖も、以下に示す対象に対してこの流れを使う。自動閉鎖の通知も同じ閉鎖調整へ渡し、表示だけを直接削除して後処理を省略しない。UI は意図を渡し、必要な確認を表示し、結果を受け取る。Disconnect、Completion、転送閉鎖、放棄、削除を UI 自身で組み立てない。

| 責務 | 所有者 |
| --- | --- |
| 閉鎖全体の調整、確認の有効性、重複要求の調整、待機と結果 | C# の閉鎖 module |
| 受信締め切り、未送信入力の取消し、通信終了、記録確定、実ファイル I/O の所有 | 既存のセッション・入力・記録 module |
| SFTP 操作・チャネルの後処理、provider 完了、一時パスや不確定結果の報告 | 既存のファイル操作・転送所有者 |
| 同時送信のジェスチャー・貼り付け完了と、タブ移動の操作全体 | 既存の BroadcastInput module |
| 配置、空ウィンドウ方針、移動保護、起動要求の順序、最終終了 | 既存の配置・アプリ調整役 |
| 共有の無効化、外部ハンドル、処理中の観測の所有 | 既存の AI module |
| 端末の意味、EOF・記録の意味、保持状態、最終ネイティブ解放 | 所有するセッション・adapter を通じた Rust 端末 module |
| ローカライズした確認、後処理待機の選択、表示 | WPF の表示 adapter |

閉鎖 module は資源操作を各所有者に依頼し、合意済みの[記録・パーサー設計](native-terminal-core-ja-jp.md)、[ファイル操作 module](file-operations-ja-jp.md)、[同時送信 module](broadcast-input-operations-ja-jp.md)を再実装しない。認証、vault、設定保存、マクロ実行環境の新しい方針は追加しない。

## 意図ごとの動作

| 意図・出来事 | 転送ウィンドウの扱い |
| --- | --- |
| 個別端末タブの明示的な閉鎖 | 対象タブに関連するウィンドウを、既存の後処理・報告方針に従って閉じる |
| 端末ウィンドウの明示的な閉鎖 | 対象端末タブに関連する転送ウィンドウを閉じる。必要な接続・ファイル作業の確認をまとめる |
| 現在のウィンドウで［切断済みをすべて閉じる］を実行 | 対象の端末タブに関連する転送ウィンドウも、明示閉鎖と同じ後処理・報告方針で閉じる |
| 保存した設定による切断済みタブの自動閉鎖（Q10 修正） | 対象タブに関連する転送ウィンドウも、明示閉鎖と同じ後処理・報告方針で閉じる |
| タブを残す切断・接続先喪失 | アプリが動作している間、切断済み転送ウィンドウの結果を保持する |
| タブ移動、ペイン削除、配置だけのグループ変更 | 既存のセッション・転送の寿命を維持し、合意済みの移動・配置契約を使う |
| アプリの最終終了 | 既存の終了規則に従う。転送結果ウィンドウだけでバックグラウンド動作を継続しない |

［切断済みをすべて閉じる］は、操作したウィンドウの全タブグループを対象とする。切断アイコンのタブ（通常切断、利用者が取り消した再接続）と、警告アイコンのタブ（接続試行の失敗・タイムアウト、成立済みの接続を終了させた通信エラー）の両方を閉じる。どちらか一方だけでも、自動クローズ設定にかかわらずコマンドを実行できる。接続が続いているタブ、認証や利用者の入力を待つなど試行中のタブ、設定・エディターは残す。記録だけが失敗して接続が続くタブも残す。

成立済みの接続の通常切断と、利用者による再接続の取消は、自動クローズ設定に従う。利用者が初回接続を取り消した場合はどちらの設定でも閉じる。試行の失敗・タイムアウト、成立済みの接続を終了させた通信エラーでは、自動クローズが有効でもタブを残す。利用者は残った出力と理由を確認してから手動で閉じられる。[接続結果ごとのタブの扱い](persistence-and-windows-ja-jp.md)を参照。

一括閉鎖・自動閉鎖では、各対象に Q10 の転送ウィンドウの後処理を適用する。接続や試行がすでに終了した対象には、接続終了の警告は不要である。必要な場合の実行中ファイル作業の確認と、判明した未完了後処理の報告は既存方針に従い、必要な承認前に取消しを開始しない。自動閉鎖でも必要な報告や未保存ログの確認を省略しない。接続先からの切断自体は外部の出来事であり、その後の閉鎖を拒否しても元には戻せない。

## 合意した完結操作の interface（Q11）

通常の UI コマンドには、次の名前付き完結操作を使う。

```csharp
await closure.CloseTabAsync(tabId);
await closure.CloseWindowAsync(windowId);
await closure.CloseDisconnectedTabsAsync(windowId);
```

これらは説明用の名前であり、実装済みの型ではない。呼び出し側は安定したタブ／ウィンドウ識別子を渡す。module が現在のセッション・転送所有権と配置を取得し、内部の表示 adapter で必要な確認を行い、操作全体と結果を所有する。呼び出し側が管理する確認チケット、Begin/End の手順、後処理・破棄の義務は渡さない。自動閉鎖も既存のライフサイクル調整を通じて対象タブに同じ流れを使い、4つ目のユーザーコマンドや別の閉鎖手順を追加しない。

名前付き操作は、種類を渡す単一操作と同じ depth を持つ。利点は名前の見つけやすさと、既存コマンドに合う引数である。interface の seam は UI・ライフサイクルの意図と、アプリの閉鎖操作全体の間に置く。資源操作と配置方針は既存所有者に残す。確認の有効性と対象が重なる要求の調整は、別途合意した次の Q12 に従う。

## 確認と閉鎖処理の待ち合わせ（Q12a-Q12b）

### 通常の進捗では確認をやり直さない

安定したタブの識別、接続世代、関係する転送の所有権、配置、承認が必要な影響を捕捉する。新たな閉鎖の影響を開始する前に、既存のアプリ調整の順序で再検証する。承認はその対象と影響に適用し、同じ表示位置や名前を持つ別の接続・追加対象には流用しない。

確認中に同じ対象の転送が終わった場合は、そのまま回答を受け付ける。確認済みの作業が減るだけの通常の進捗・完了では、確認をやり直さない。接続先から切断されたことを理由に接続終了の警告を追加しない。それが自動閉鎖を起動した場合は、次項に従って既存の閉鎖と調整する。

独立した処理で既に削除された対象は、その結果を観測し、再び削除しない。ウィンドウの最終削除を確定する前に、残る対象と既存の最終ウィンドウ規則を検証する。通常の進捗を受け入れることは、新しい世代・影響する作業・未確認の対象追加を承認することではない。予定する新しい影響に対して承認が無効になった場合、その影響を開始せず対象の変化を報告し、新たに有効な判断を必要とする。確認中ずっとロックするのではなく、現在の所有権を再検証する。

Q14 の合意事項：このような無効な要求は、新たな影響を起こさず対象の変化を知らせて終了する。自動で対象を取り直して確認を繰り返さず、新しい要求で有効な判断を得る。既存の独立した閉鎖は継続する。これは例外的な対象変更の扱いであり、Q12a の通常進捗や Q12b の再操作不要の動作は変えない。

### 既存処理を共有し、要求ごとの承認範囲を保つ

合意した A・B の例では、A の閉鎖は承認済みでログの後処理を待っている。後からウィンドウを閉じる要求が来たら、A の既存処理を利用し、B など残る対象に必要な確認をまとめて行い、各対象が既存の閉鎖条件を満たしたらウィンドウを閉じる。A が終了途中だったことを理由に、もう一度閉じるボタンを押す必要はない。A の確認、切断、記録確定、転送ウィンドウ閉鎖、ネイティブ解放を繰り返さない。

同じ要求の繰り返し、一括閉鎖、自動閉鎖にも同じ所有権の規則を適用する。広い要求が来ても、先行する承認範囲は拡張されない。同じ要求は進行中の処理・結果を観測し、完了前に完了扱いで返したり別の後処理を始めたりしない。追加対象には適用される承認が必要である。両方がまだ確認中に重なった場合も、既に閉鎖が確定した対象を再検証して同じ対象の記録で調整し、後続要求が来たこと自体を許可としない。

対象ごとの閉鎖実行と、それを観測する要求を分ける。対象は再利用される画面位置だけでなく、寿命と世代で識別する。要求は対象の実行を待ち、相互に待ち合う可能性のある別のウィンドウ要求全体を待たない。後処理の判断と時間計測は対象ごとに一つとし、合流で5秒の待機をやり直したり、損失確認を重ねたり、先の「待機を続ける」を置き換えたりしない。既存のモーダル表示順と上限付き後処理受付を維持する。

タブが表示中の一覧から消えた後も、共有する実行と結果を観測できるようにする。合流で後処理容量を重複計上せず、ある対象の損失許可を別の対象へ流用しない。後処理の選択をまとめて表示する場合も、実際に示して承認された所有者だけに適用する。

ライフサイクルやウィンドウのコールバックが、待機対象の処理と循環しないようにする。セッション完了を待つ閉鎖に対して、セッションの切断通知がその閉鎖全体を待ってはいけない。最後のタブ削除やウィンドウ閉鎖イベントの再入は、既存の表示確定を確認・再評価し、同じウィンドウ要求を再び開始して待たない。調整役の状態遷移は短くし、ダイアログや非同期後処理を待つ間は順序制御のロックを保持しない。同じ切断通知の重複で、拒否された閉鎖の確認を自動的に繰り返さない。

後から表示したウィンドウ閉鎖の確認を拒否した場合、その要求による新たな影響を B などに与えない。先に承認した A の閉鎖や、独立して起動した自動閉鎖は取り消さない。結果では新たに開始した影響と、共有・独立完了した処理を区別し、「拒否」を「どこにも変化がなかった」と誤解させない。後続要求の承認が無効になり適用できない場合も同様とする。

承認後の発行済み作業は実際の完了まで既存所有者が保持する。合流で期限を短縮したり、必要な損失判断を省略したり、ウィンドウ削除だけで資源を解放済みと報告したりしない。既存規則でまだ削除できない対象があれば、ウィンドウ閉鎖は待機を維持するか実際の失敗を報告する。必要な対象削除が未解決のままウィンドウ全体の成功にしない。最終表示確定時には既存調整役を通じて配置と全種類のタブを再検証する。

## 寿命と完了の区別

[セッション・記録契約](session-and-recording-ja-jp.md)と[転送契約](file-transfer-ja-jp.md)に従う。閉鎖の判断、表示削除、上限付き後処理への引継ぎ、実際の I/O 完了は別の出来事である。既存の損失・後処理方針で表示を閉じた後も、発行済み作業とメモリを実際の完了まで所有者に残す。既存契約が求める場合は、判明した未確定結果を閉じる前に報告する。表示を閉じたことを永続保存の成功として扱わない。

記録の後処理が5秒続いた際の既存の選択は「待機を続ける」を既定とし、その選択は停滞による自動放棄より優先する。未保存データを伴う閉鎖では未発行作業を放棄し、発行済み作業の取消しを要求するが、実際の所有権は保持する。通信と記録の終了には独立した完了規則がある。無制限のバックグラウンド後処理や、容量の受付を迂回する経路は追加しない。

EOF・切断では保持する Rust 端末の所有を終えない。保持された切断済みタブは端末状態を維持する。最終的なタブ削除では、その所有者を通じて端末の所有を明示的に終了する。WPF の Unloaded やタブ移動を端末破棄に置き換えない。独立して所有する不変な結果と発行済み I/O は、それぞれの寿命と課金を維持する。明示・一括・自動の削除はすべて上表の転送ウィンドウ閉鎖方針を適用する。表示削除に失敗してタブが残る場合、その端末状態を先に破棄しない。

## 合意した失敗・観測の契約（Q13）

処理開始前の確認拒否・取消し・無効な確認・確認表示の失敗は、その閉鎖要求による新たな影響を残さない結果とする。独立して完了した作業や接続先からの切断を元に戻す意味ではない。通常の進捗と承認の無効化は、上記 Q12 の規則で区別する。

処理開始後は、呼び出し側が待機をやめたり表示がなくなったりしても、module が全対象の後処理を所有・観測する。想定される失敗は、実際の表示の状態、判明した失敗・損失・未確定結果、残っている後処理を含む、不変で上限付きの結果として返す。一つの所有者の失敗で他の後処理の観測を失わず、開始済みの影響が元に戻ったとも扱わない。操作の task も WPF のイベント処理とは独立して保持・観測する。

表示削除、許可された後処理引継ぎ、実際の解放を区別する。最終解放の観測は読み取り専用であり、呼び出し側に後処理・破棄の義務を追加しない。解放完了は外部処理がすべて成功した証拠ではなく、アプリ最終終了後の後処理存続も約束しない。想定される失敗を未観測の task 例外として放置しない。

ログ損失の選択肢を表示できなかったことを、損失の許可として扱わない。必要な未確定転送結果の報告に失敗した場合は、黙って閉じず失敗として報告する。最終表示削除に失敗したビューが必要とする状態は保持する。Q10 の自動閉鎖にもこれらを適用する。

[ウィンドウ契約](persistence-and-windows-ja-jp.md)による起動要求・閉鎖・移動確定の順序を維持する。最後のタブを閉じたあとも、ウィンドウは開いたままにする。移動先確定後に元を除去する規則、設定・エディターの Save/Cancel、最終終了規則を維持する。

## 検証と実装準備

本番の閉鎖 interface と実物の Rust・セッション・資源所有者を使う。確認、時刻、I/O、配置を制御できる adapter で重複・古い要求・遅延完了を観測し、実際の WPF・ファイル・通信・provider を使う統合検証も残す。内部 helper の呼び出し回数ではなく、接続・記録・表示の結果と所有権を検査する。

閉鎖による影響を残さない確認拒否、ウィンドウの一括確認、Q10 の一括・自動閉鎖での転送ウィンドウ閉鎖とタブを残す切断での結果保持、受信・末尾の一度だけの確定、後処理の失敗と待機・損失の選択、古い世代の完了、不変スナップショットを保持したままの最終 Rust 解放、移動・起動・閉鎖の順序、最終ウィンドウ終了を検証する。既存の過去の検査はこの目標の保証を証明せず、今回も再実行していない。
