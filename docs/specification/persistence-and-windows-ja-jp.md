# プロファイル、設定、パス、ウィンドウの所有権

2026-11-10 時点の仕様。Q109～Q116、Q155～Q158 の内部契約を確定する。起動時の登録と信頼は、今後実装する[プロファイルの信頼仕様](profile-trust-ja-jp.md)に従う。

2026-11-16 に合意したエクスプローラーとエディターの仕様は、プロファイルをタブで編集し、起動経路を端末ウィンドウに限定していた以前の記述に優先する。

## 共通 JSON ルール

UTF-8 のオブジェクト、`schemaVersion: 1`、大文字と小文字を区別する英語のプロパティ名、ID には小文字でハイフン付きの正規 UUID 文字列を使う。新しい書き込みは BOM なしとし、ユーザーが編集できるこれらの JSON ファイルでは先頭の UTF-8 BOM を一つ許可する。不正な UTF-8、プロパティの重複、一意性が必要な ID の重複、コメント、末尾の空白以外の文字、未対応のスキーマバージョンや必須機能、不正な型、必須フィールドの欠落、未知の列挙値を拒否する。読み込み時に新規プロファイルの既定値で自動修復しない。null 許容フィールドには明示的に null を入れる。継承は省略から推測せず明示する。

各ルートは一意な文字列の配列 `requiredFeatures` も持つ。v1 では空配列とする。未知の必須機能は拒否する。同じ対応バージョンで保存する際は、各オブジェクト階層の未知の任意プロパティを上限付き JSON として保持する。実行や新しいスキーマのダウングレードは行わない。フィールド順に意味はなく、配列順には意味がある。整形時に空白を保持する必要はない。

すべての読み込みに構造検査とリソースおよび型の制限を適用する。詳細な設定の整合性、正規表現の妥当性、設定ガイダンスは、エディターを開くとき、編集時、保存時に適用する。プロファイルの信頼確認は接続時に行い、許可後にログの準備とトランスポートの開始に進む。接続時にはポートの可用性、対応する上限、認証情報、ファイルアクセスなども検査する。

## プロファイル v1 のフィールド

表のフィールドはすべてエディターが出力し、特記がなければ必須。既定値は新規プロファイルに適用する。欠落したフィールドの修復には使わない。

| オブジェクト | フィールドと解釈 |
| --- | --- |
| ルート | `schemaVersion`、`requiredFeatures`、`profileId`、`displayName`、`connection`、`terminal`、`logging` |
| connection | `type` は `ssh`、`telnet`、`serial` のいずれか。`waitSeconds` は既定 30、範囲 1～300。以下のうち該当するトランスポートのフィールドだけを含む。 |
| SSH | `host`、`port`（既定 22）、`username`、`authentication`、`liveness` |
| authentication | `methods` は `publicKey`、`password`、`keyboardInteractive` の順序付きで重複のない部分集合。初期値は `[password]`。`privateKey` と `password` はそれぞれ null または認証情報参照。未保存で取得できない入力は認証時に求める。 |
| 認証情報参照 | `vaultId`、`entryId`、`kind`（`privateKey` または `password`）。秘密情報、パス、インポート元のパスフレーズを含まない。 |
| liveness | `enabled` は既定 false、`intervalSeconds` は既定 30、範囲 1～3600。`unansweredWindows` は v1 で 3 に固定。 |
| Telnet | `host`、`port`（既定 23）、`initiateBinary`（既定 false）。ユーザー名、認証情報、ログイン照合フィールドは含まない。 |
| シリアル | `portName`、`baudRate`（既定 9600）、`dataBits`（既定 8、7/8）、`parity`（既定 `none`、`odd/even/mark/space`）、`stopBits`（既定 1、1/2）、`flowControl`（既定 `none`、`xonXoff/rtsCts/dsrDtr`）、`dtr`（既定 true）、`rts`（既定 true） |
| terminal | `advertisedType`（既定 `xterm`）、`receiveEncoding`（既定 `utf-8`）、`sameEncoding`（既定 true）、`transmitEncoding`（既定 `utf-8`）、`jis`、`ambiguousWidth`（既定 1、1/2）、`enter`、`backspace`、`localEcho`、`font`、`retainedRows`、`highlightSetId`（null または UUID） |
| jis | `kanjiIn`（既定 `B`、`@/B`）と `kanjiOut`（既定 `B`、`B/J`）はファイル互換性のために保持する。`receiveKana` と `transmitKana`（既定 `eightBit`、`eightBit/soSi`）はコーデックの契約に従う。 |
| font | `mode` は `inherit` または `override`。`family` は継承時 null、それ以外は指定されたインストール済みフォント名。`sizePoints` は継承時 null、それ以外は 6～72。 |
| retainedRows | `mode` は `inherit` または `override`。`value` は継承時 null、それ以外は 100～100000 の整数。 |
| logging | `raw`、`text`、`terminal` は既定 false。`directory` は既定 `Logs`。 |

`enter` は `cr`（SSH/シリアルの既定）、`lf`、`crlf`（Telnet の既定）のいずれか。`../drafts/terminal-interaction-issue.md` の合意どおり、`backspace` は `del`（SSH/Telnet の既定）か `bs`（シリアルの既定）。`localEcho` は SSH で `off`、Telnet で `followRemote`（既定）または `off`、シリアルで `off`（既定）または `on`。対象外の保存済み端末フィールドは動作に影響せず、関連する場合だけ編集できる。sameEncoding=true の場合、実効送信エンコーディングは receiveEncoding に等しい。明示的に保存した送信設定は後で使えるよう保持する。

エンコーディング ID は `utf-8`、`cp932`、`euc-jp`、`jis`、`cp949`、`cp936`、`cp950`、`koi8-r`、小文字の `cp` に合意済みの OEM/Windows 番号を付けたもの、または `iso-8859-` に 1～11、13～15 のいずれかを付けたもの。対応は47種類。プロファイル ID はコンテンツの識別子であり、ローカル登録の識別子は別に管理する。

## アプリケーションストア

| ファイル | 共通のバージョンフィールド以外の必須データ |
| --- | --- |
| settings.json | `language` は既定 `system`（`en/ja/system`）、`theme` は既定 `system`（`system/light/dark`）、`bell` は既定 `visual`（`visual/off`）。`defaultTerminalFont` は family が Consolas、sizePoints が 12。`defaultRetainedRows` は 5000。任意の `autoCloseDisconnectedTabs` は真偽値、既定 `true`。任意の `credentialVaultPath` は絶対 `.tttykey` パスまたは既定位置を示す null。任意の `broadcastAcrossWindows` は真偽値、既定 `false`（同時送信の拡張）。任意の `maxPasteTextBytes` は正の整数バイト数、既定 `536870912`（512 MiB）。 |
| highlighting.json | `sets` は順序付き配列で初期状態は空。各セットは `setId`、`name`、`enabled`、`rules` を持ち、各ルールは `ruleId`、`name`、`enabled`、`pattern`、`ignoreCase`、`style` を持つ。 |
| style | null 許容の `foreground`/`background` は `#RRGGBB` 形式。`bold` と `underline` は null 許容の真偽値。null は端末属性を継承する。優先順位の低いルールからは継承しない。 |
| state.json | `registrations`、`lastWindow`、vault パスのフィールド導入前の設定用の旧 `selectedVaultPath`。アプリケーション状態のみを含む。 |
| registration | 独立した `registrationId`、開いたパスの正規形と表示用表記、`favorite`、UTC の null 許容 `lastUsed`。ファイルの不在はローカルで観測し、プロファイルを書き換えない。 |
| lastWindow | DIP 単位の通常時の位置とサイズ、モニター ID、作業領域、DPI の観測値、最大化フラグ。最小化状態では復元しない。 |
| host-keys.json | トランスポート契約で定義するバージョン付きのホストレコード。vault やポータブル設定から独立する。 |

明確化した全体アーキテクチャ Q26 は、既存予算での不変原文の共有とともに、接続プロファイルから独立したアプリ全体のユーザー設定 `maxPasteTextBytes` を維持する。1回の貼り付けで選択した実際の Unicode 本文を、送信先文字コードへの変換前に UTF-16 コード単位あたり2バイトで測る。元の CR/LF を含み、終端 NUL、割り当ての余白、メタデータ、他のクリップボード形式は除く。この任意フィールドがない既存の対応ファイルは 536,870,912 バイトを使う。正の有限な整数バイト数を検査付きで受け付け、ゼロ・負数・小数・オーバーフローは無効とし、無制限の指定にはしない。単位表示で保存バイト数を黙って丸めない。既存の検証付き保存・キャンセルと保存失敗時の挙動を使い、元の本文サイズと1操作ごとの上限であることを英語・日本語のリソースで説明する。

保存成功後に開始する貼り付け操作から新しい値を使う。取得・プレビュー・送信中の操作は開始時の上限を保持し、設定を下げても切り詰めたり取り消したりしない。キャンセルや保存失敗で実効値を変えない。設定上限内でも通常の検証と[資源受付](resources-and-validation-ja-jp.md)は必要。Q28-Q29 の独立した合計方針は置き換え、合計上限・メモリ割合のフィールドや設定項目は追加しない。貼り付け間隔と記憶チェックは下記のとおり起動中だけ保持する。候補6の最終 Q23 確認は 2026-11-18 に完了した。この文書変更によるファイル移行の実装は行わない。

言語、テーマ、ベル、保存したルールは保存成功後ただちに適用する。自動で閉じる設定は、保存後に発生した切断から適用する。同時送信の範囲は Q181 に従い開始時に確定する。Q187 で対象を拡大した通常の終了コマンドは、保存した全ウィンドウ設定にただちに従う。Q197 は範囲モードの変更時に全選択へリセットする。次回開始時というタイミングは Q199 で確認済み。実行中の同時送信モード、送信先のチェック、ウィンドウ単位の初回利用やリセット待ちの状態、分割レイアウトは永続化しない。[同時送信と分割ビュー](broadcast-and-split-views-ja-jp.md)を参照。

保持された切断済みタブは、接続名の前に切れたリンクのアイコンを表示する。ツールヒントとアクセシブルなタブ名に、ローカライズした切断状態を含める。現在のウィンドウにある切断済みタブは、タブバーのコンテキストメニューから閉じられる。端末・設定・エディターの最後のタブを閉じても、ウィンドウは開いたままにする。手動、自動、一括のいずれの閉鎖にも適用する。グループが一つの場合はようこそ画面に戻り、分割済みの場合はレイアウトを保持する。新規タブボタンは引き続き使える。

2026-11-16 に改訂したアーキテクチャ Q10 で、ユーザーによるこの一括コマンドと切断済みタブの自動削除は、いずれも対象タブに関連する転送ウィンドウを、個別タブ／ウィンドウの明示閉鎖と同じ後処理・報告方針で閉じると合意した。すでに切断済みの対象には接続終了の警告を出さず、必要な後処理、報告、待機・損失の選択は既存方針に従う。切断や接続先の喪失後に端末タブを保持する場合は、転送結果も保持する。[閉鎖設計](tab-and-window-closure-ja-jp.md)を参照。一括処理と自動削除の動作変更は未実装である。

フォントと保持行数の既定値、プロファイルから解決した値は次回接続時に確定する。`system` のような選択値を保存する。貼り付け間隔と記憶チェック、一時ズームとエコー、ロック解除状態、タブの内容はどのストアにも保存しない。翻訳は安定した識別子を持つ言語別リソースで管理する。初期対応は英語と日本語。システム言語は Windows の表示言語の優先順に従い、英語にフォールバックする。テーマは Windows のアプリ用設定に即時追従し、周囲の UI だけに適用する。

上限はプロファイル 1 MiB、設定 64 KiB、強調表示、状態、ホストレコードは各 16 MiB、JSON の深さは 16。表示名は 256 スカラー値、ホスト名は IDNA 変換後の ASCII で 253 バイト、パスは UTF-16 で 32760 コード単位、通知する端末種別は印字可能な ASCII で 64 バイト。強調セットは 1000、セットごとに 100 ルール、パターンは UTF-16 で 4096 コード単位。登録済みプロファイルとホスト接続先は 10000。必須機能は 32 個、各 ASCII で最大 64 バイト。未知のプロパティの内容も同じサイズと深さの制限に含める。これは読み込み時の内部上限であり、すべての最大値を同時に使ったときの実用性能は保証しない。

## 開いた場所と登録

ローカルアプリデータの場所は Windows から取得する。非パッケージ版のストアはその下の `TabTty` ディレクトリに置く。新規プロファイルには既知の「ドキュメント」フォルダーの `TabTty\Profiles` を提案する。外部のプロファイルは元の場所で開く。ログディレクトリはプロファイルを開いたディレクトリからの相対位置として解決する。通常の絶対 DOS/UNC パスと通常の相対ログパスを許可し、区切り文字とドット構成要素を正規化する。ドライブ相対の `C:Logs`、ルート相対の `\Logs`、デバイス名前空間、代替データストリーム、埋め込み NUL は拒否する。環境変数やチルダは展開しない。長いパスには内部で拡張プレフィックスを使えるが、ユーザー向けの新しいパス構文は設けない。

記録が有効な場合、端末への接続前にログ保存先を開くことをプロファイル編集画面に明示する。UNC パス、ネットワークドライブ、共有フォルダーにあるプロファイルを基準とした相対パスでは、Windows が共有先で認証を行い、受信した出力もそこに保存される場合がある。エクスプローラーの［編集］なら、接続やログ記録を開始せずに設定を確認できる。

登録は、正規化した開いた場所で識別する。リンクの最終リンク先、ファイル ID、保存されたプロファイル UUID は登録の識別に使わない。大文字と小文字を区別するディレクトリの区別を保持し、一律に小文字化せず、所属ディレクトリの Windows の規則で名前を比較する。ファイルシステムから取得できる場合は短い表記と長い表記の等価性を解決し、別々のリンクパスは統合しない。同じ場所と確認できない場合は登録を分け、履歴を保持する。相対ログは引き続き開いた場所を使う。

外部コピーや新しい場所には、新しい登録 ID を割り当て、お気に入りや履歴は引き継がない。profileId が重複しても移動と判断しない。明示的に分かっている移動では古い登録を削除し、新規登録する。場所をまたぐ登録の連続性は設けない。移動追跡がない場合、アクセスできない旧パスは削除されるまで不在と表示されることがある。識別情報は別のパスに移さない。ファイルハンドル ID とダイジェストは編集競合の検出に使える。

新規登録が成功した時点で、その登録対象の版を自動的に信頼する。未登録のプロファイルへ手動で接続する際は、読み込んだ版がすでに信頼済みであっても三つの選択肢を提示する。編集・保存・登録の際に信頼確認は行わない。登録解除時には、開いた場所に対応するプロファイルの信頼をすべて削除する。[プロファイルの信頼仕様](profile-trust-ja-jp.md)

## 保存と復旧

編集の下書きと元ファイルの識別情報、ダイジェストを保持する。保存では検証、元のスナップショットとの比較、同一ディレクトリへの候補ファイルの書き込みとフラッシュ、置き換えまたは上書き禁止の新規作成、実際の結果の確認を順に行い、実効リビジョンを公開する。検証済みの前世代を一つ `.bak` に保持する。外部変更を検出したら再読み込みと確認を求める。自動での統合や上書きは行わない。失敗した場合は下書きと最後の有効な設定を保持し、実際の結果を報告する。誤って保存済みと表示しない。ファイルの置き換えは単一ファイルに限る。

置き換えの結果が不明な場合は、対象、候補、バックアップのバイト列を期待値と比較し、以下の契約に従って保存結果と必須の退避の状態が解決するまで関連する書き込みを凍結する。エラー時に名前と内容が維持されたとは限らない。破損ファイルは、明示的なバックアップ復元、一時的な既定値の利用、終了のいずれかを選べるようそのまま保持する。一時的な既定値を使うストアは、元ファイルを重複しない名前で保持した上で明示的に復旧または再作成するまで読み取り専用とする。新しいスキーマを破損として暗黙に復旧しない。初回利用でファイルが存在しない場合は既定値を使う。強調表示の失敗は致命的に扱わない。ローカル状態の保存エラーはまとめて扱い、切断しない。

一時的な既定値と初回利用時の既定値は、アプリ設定、強調表示、ローカル状態のストアだけに適用する。プロファイルが存在しない、破損している、または未対応の場合は接続や再接続ができない。有効なプロファイルを復元するか明示的に保存する。ホストストアの障害は明示的に復旧する。既知のホストを暗黙に未知のホストに変えて初回承認の対象にしない。

### 結果を検証するファイル操作

プロファイル、アプリケーションストア、暗号化した vault の保存では、共通モジュールが物理的な操作全体を所有する。同一ディレクトリへの候補作成、アクセス規則、必要な書き込み排他、書き込みとフラッシュ、元の編集基準の再確認、作成または置き換え、対象・候補・バックアップの調査、自分が所有する成果物の後処理を含む。interface は、上書き禁止の新規作成、既存ファイルの更新、明示的に許可された復元を、型で区別した完了操作として受け付ける。形式の所有者は、シリアライズ、スキーマ検証、未知のプロパティ、許可する場所、退避方針、有効リビジョンの採用を担う。vault の所有者は暗号処理、秘密情報の所有、資格情報の利用判断を担う。ストリーミングのログと SFTP のファイル操作はそれぞれの契約に従う。プロファイル保存と登録・設定保存は独立した結果であり、複数ファイルのトランザクションにはならない。

受付は同期的に行い、ファイルシステム I/O を待たない。上限内の容量を予約し、観測待機をキャンセルできるようになる前に、操作 ID と読み取り専用の操作ビューを返す。拒否時は所有権を移さず、ファイルを変更しない。識別情報の解決、検証、I/O は受付後に所有権を持つ処理として実行し、受付だけでは変更を許可しない。要求を元の編集基準と不変の候補バイト列に結び付け、形式の所有者が規則、識別情報・リビジョン、長さ、ダイジェストの検証根拠を与える。後の下書き変更や別の保存でこの基準を変えない。必要なコピーとバッファーを上限に計上する。呼出元が段階的に書き込みや後処理を指示する手順や、別の公開ファイル所有者は設けない。通常の呼出元は最初の観測を一度待つ。上限付きの現状、照合、実資源の解放は別々に観測でき、監視ループを必須にしない。操作ビューを捨てても所有する作業は終了せず、呼出元に後処理の義務を課さない。

変更前に、正規化した開いた場所、親の名前空間、最終ファイル名で操作を調整し、置き換えと未解決状態を通じて対象名の予約を維持する。既知の別名や観測した物理的な識別情報も調整するが、登録を統合したり開いたパスの意味を変えたりしない。置き換えでファイル ID が変わり得るため、旧ファイルと配置されたファイルの識別情報は別に追跡する。競合し得る操作を安全に調整できなければ変更を拒否または延期する。ディレクトリの大文字・小文字と短い名前の規則、形式ごとのアクセス・ロック・場所の規則を維持する。任意の外部書き込み元に対する原子的な比較交換は保証しない。

各成果物のダイジェストと検証は、上限付きで取得した同じ一つのイメージに対して行う。異なる読み込みの事実を一つの観測として結び付けない。三つのファイルは原子的なスナップショットではなく、変更を検出したら関連する根拠を無効にする。以前に認証した暗号化イメージとの一致で vault の世代を識別できる場合は、追加のロック解除は不要。別途選んだ復元元には独立した認証とスキーマ検証が必要。共通モジュールに鍵、マスターパスワード、平文の資格情報を渡さない。再取得が必要になる mutex を保持したまま検証や形式の所有者による結果処理を実行しない。論理的な操作の受付制限は維持する。

対象の状態、必須の退避、操作全体の結果、残っている資源と成果物を分け、操作 ID と単調増加する観測リビジョンを付けて報告する。所有者は古い観測を無視し、新しい有効状態を巻き戻さない。ファイルシステムの戻り値だけでは保存結果を決めない。

| 関連する発行済み処理の終了後に確認できた事実 | 結果と採用 |
| --- | --- |
| 候補が対象にあり、必須の退避もすべて検証済み | 保存が完全に成立。形式の所有者が有効リビジョンを採用できる。後処理は未完了でもよい。 |
| 候補が対象にあるが、必須のバックアップや復旧コピーが欠落または不一致 | 部分成立。以前の有効状態と下書きを保持し、通常の書き込みを停止する。対象の変更と退避の失敗を報告する。 |
| 候補が対象にあるが、必須の退避を読み取れない、または検証できない | 対象への反映は判明、退避は未解決。同じ採用制限を維持し、対象について判明した事実を隠さない。 |
| 更新・復元の元ファイルが無傷、または新規作成先が存在しない | この操作による有効な保存は成立していない。元ファイルの維持と新規ファイルの未作成を区別し、候補やバックアップへの副作用も報告する。 |
| 予期しないリビジョンや外部変更を検出 | 競合。観測した外部データと必要な自分の復旧素材を保持する。自動で統合や上書きをしない。 |
| 対象が欠落・破損、または根拠を取得できない | 欠落・破損と調査不能を区別し、停止と復旧の制限を維持する。自動復元や空への初期化をしない。 |
| 後処理だけが失敗または未完了 | 検証済みの保存結果を維持し、残る成果物と実資源の寿命を報告する。変更なし、何も保存されていないとは扱わない。 |

通常のバックアップには前の検証済み世代を残す。明示的な復元では、破損していても観測した元のバイト列を一意の復旧名でそのまま保持する。そのコピーを有効なバックアップとは呼ばない。部分成立を通常の成功や変更なしとして扱わない。取得不能だった根拠は再調査できるが、欠落が確定した成果物を繰り返し調べたり再作成したりしない。明示的な復旧か次回のアプリ起動で次の利用可能な状態を確立し、通常の開き直しだけでは部分成立・未解決の制限を解除しない。復旧は別の許可された操作とする。以前の変更可能な処理がすべて終了し、必要な根拠と成果物を所有した状態で形式の所有者が復旧を選んだ場合だけ、対象名の予約を途切れなく引き継ぐ。復旧失敗で以前の制限を解除しない。次回起動では実際のファイルを通常どおり検証し、以前の保存を遡って成功に変えない。

観測待機のキャンセルは、その待機だけを終了する。実作業のキャンセルと保存処理の発行を直列化する。キャンセルだけを根拠に反映なしと判断できるのは、発行を防げた場合だけ。変更が発行された可能性があれば実作業を保持して結果を調べる。発行済み処理が後から変更し得る間は、旧ファイルや作成先の不在を観測しても最終結果とはしない。同時の照合要求は同じ調査回に合流し、保存の再実行、編集基準の更新、復元を暗黙に行わない。後続の照合では新しい調査回を受け付け得るため、過去の回の I/O と検証資源の解放は、現在の静止を保証しない。追跡を終了した操作だけが、以後の調査受付を恒久的に終える。

実 I/O または所有者を必要とする検証の実行中は、既存の操作・閉鎖保護を維持する。両方が終了したら、部分成立や未解決の事実、対象と復旧ファイルのパスを既存の閉鎖判断に表示した上で、編集ウィンドウの閉鎖やアプリ終了を許す。静止の確認と所有者の終了を、追加の調査・検証の受付に対して直列化し、遅れたコールバックが解放済みの所有者を使わないようにする。退出で下書きを保存済みにしたり、復旧ファイルを削除したり、不完全な状態の採用を承認したりしない。アプリが続く間は、画面を閉じても簡潔な根拠と書き込み制限を維持する。後の調査には保持した秘密でない根拠か、通常どおり許可され生存している形式の所有者を使う。終了時の秘密情報は通常の寿命に従って解放する。操作 ID は永続化せず、ジャーナル、自動復旧、隠れたプロセス寿命、プロセス終了後の後処理保証は加えない。セッション記録の5秒・10秒の規則は適用しない。

操作記録数、所有バイト数、保持する成果物の数とバイト数に、バージョン管理した内部の有限上限を設定する。受付と割り当ての前に容量を予約し、不足時は新しい作業を副作用なく拒否または延期する。明示的な復旧への引継ぎを除き、競合する一つの対象に対して変更可能または未解決の操作は一つまでとする。実作業が終わり簡潔な根拠で十分になったら、大きなバッファーを解放する。TTL、キャンセル、メモリ圧迫で未解決の制限を消さない。復旧所有権の移転は計上も明示的に引き継ぐ。通常のユーザーファイルと検証済み `.bak` は、一時・未解決の成果物と区別する。候補パスが再利用されていても、所有を立証できない別のファイルを削除しない。解決済みで実資源のない記録だけを追跡から外し、不明・追跡終了の ID で保存を再実行しない。完了履歴にも上限を設ける。既存の準備処理の上限だけでは保存・成果物全体の予算にならない。新しい具体値は実装開始時に内部方針として固定し、上限時と超過時を検証する。応答しない OS I/O の完了期限は保証できない。

[合意済みの15ケースの検証計画](../drafts/whole-codebase-architecture-deepening.md#candidate-3-verification-plan)は、通常の interface、実際の形式・暗号検証、制御可能なファイルシステム・時刻の adapter、実ファイルの統合検証を使う。UNC は対応する形式だけで検証する。これは今後必要な検証であり、実行済みの証拠ではない。同レビューの Q7～Q11 により本設計は実装に進める状態となった。実装とプロトタイプの開始には別途ユーザーの指示が必要。

## ウィンドウ、ファイル起動、モーダルの順序

Windows ユーザーごとの一つの `TabTty.exe` インスタンスが、端末ウィンドウと独立した編集ウィンドウを所有する。プロファイルと保管庫の起動には認証済みの同一ユーザー向けローカルチャネルを使い、操作種別とパスに上限を設ける。ディスパッチ時に世代を検査する。操作種別とパスの無効な組み合わせは拒否する。無効な［編集］の要求を接続として実行しない。
パスや引数を転送・受理する前に、双方のプロセスで相手が同じインストール先の TabTty であることを確認し、ユーザー、ログオン SID、Windows セッション、昇格状態、必須整合性レベルの SID を照合する。いずれかが異なる場合やトークンを照会できない場合は、パスの送信や操作の実行に進まず転送を終了する。

ファイルからの起動は[保留件数の上限](resources-and-validation-ja-jp.md)まで FIFO で受け付ける。処理をブロックするモーダルの表示中はキューに入れ、ファイル準備の期限を開始しない。接続要求は、存続中の端末ウィンドウのうち最後にアクティブだったものに送り、最小化されていれば復元する。端末ウィンドウがなく、終了も確定していない場合は新しく作る。非同期読み込みの前に、受信順に新しいタブの位置を確保する。ファイルごとに接続を判断し、許可された要求の接続準備を進める。失敗はそのタブに表示する。Q158 のプロファイルとログの独立した 30 秒の期限は、それぞれの段階で計測を始める。接続先の端末ウィンドウを選ぶ際は独立した編集ウィンドウを候補に含めない。

エクスプローラーから編集で初回起動したときは、指定された編集ウィンドウを表示する。編集ウィンドウだけが開いている状態でファイルを指定せずに通常起動すると、端末ウィンドウにプロファイル選択を表示する。アプリの終了判定には端末ウィンドウと独立した編集ウィンドウを数え、すべて閉じた時点で終了する。

同じ保管庫ファイルのロック解除操作は一つを共有し、待っているすべての試行が同じ結果を受け取る。キャンセルや失敗では待機中の試行を終了し、確認を繰り返さない。ダイアログの所有元が閉じた場合は、同じコーディネーターで操作を完了するか、存続中のウィンドウに引き継ぐ。[保管庫の所有権と後処理](vault-format-ja-jp.md#秘密情報の所有者と後処理)を参照。

タブの移動では、移動先への挿入を確定できるまで元の所属を維持する。確定時に変更するのは表示上の所属だけで、続けて空になった元ウィンドウを閉じる。失敗やドラッグの取り消しでは元の状態を保つ。移動中の保護により、所属先を切り替える間に最後のウィンドウが終了するのを防ぐ。ファイル起動、閉鎖、移動の確定はコーディネーターの順序に従う。各セッションは一つの端末タブに属し、移動中の保護下にある場合を除き、そのタブは一つのタブグループとウィンドウに属する。同じタブ内の複数ペインは同じセッションのビューとして扱う（2026-11-13 に Q165/Q170/Q172 で合意）。閉鎖の確認をキャンセルすると、保留中のファイル起動を再開する。最終終了の確定後は新しい起動を拒否し、保留中の要求をキャンセルする。通知領域に隠れて動き続けることはない。

[転送ウィンドウ](file-transfer-ja-jp.md#transfer-window-and-operation-ownership)は SSH 端末タブと現在の接続世代に結び付く。タブを分離または移動しても、転送ウィンドウと作業を維持する。タブや端末ウィンドウを閉じる確認には進行中のファイル操作を含める。切断や接続先の喪失後に端末タブを保持する場合は、転送結果も保持する。自動削除を含む実際のタブ削除では、上記の閉鎖方針に従い、関連する転送ウィンドウを閉じる。

モニターごとの DPI に対応した WPF ウィンドウを使う。通常時の位置とサイズを DIP で保持し、対象モニターの現在の倍率と作業領域に合わせて変換し、画面内に収める。初期の通常サイズは 1000×700 DIP。モニターが許す場合の最小値は 480×320 DIP。必要に応じて作業領域まで縮める。最大化は別に復元する。分離したウィンドウは元の通常サイズでドロップ位置の近くに開く。レイアウト通知はトランザクション単位で最終グリッドにまとめ、変更されたグリッドにはセッションのサイズ変更契約を適用する。

## エクスプローラーと編集ウィンドウ

現行の非パッケージ版 Windows 11 向け配布では、設定タブの［メンテナンス］で［TabTty のファイル形式を Windows に登録］を押したときだけ、現在の Windows アカウントにファイル形式を登録する。もう一度押すと、登録内容を更新する。

`.ttty` と `.tttykey` には［開く］と［編集］を登録する。拡張子ごとの既定のアプリは Windows の設定に従う。TabTty が選ばれている場合は以下の動作を提供する。［編集］は［その他のオプションを表示］から使えればよい。複数選択では、Windows の選択件数の制限内でエクスプローラーが渡すファイルを処理する。

| ファイル | ［開く］、ダブルクリック、Enter | ［編集］ |
| --- | --- | --- |
| `.ttty` | ファイルごとに手動接続の規則を適用する。利用者が登録を選んだ場合は開いた場所で登録し、接続を許可したファイルについて接続を開始する。 | ファイルごとにプロファイルの編集ウィンドウを開く。複数選択に対応する。 |
| `.tttykey` | 既存の一ファイルを保管庫の編集ウィンドウで開く。 | 既存の一ファイルを同じ保管庫の編集ウィンドウで開く。 |

受け付けた各プロファイルの処理は独立する。一つの読み込みが失敗したら対象パスのエラーを表示し、他のファイルの編集や接続は続ける。エクスプローラーが別々に起動要求を送る場合も、アプリが受け取った順序に従う。保管庫は起動要求ごとに一ファイルを受け付ける。

TabTty 内のプロファイルの新規作成と編集には独立したウィンドウを使う。エクスプローラーの［編集］では既存ファイル用のフォーム、レイアウト、詳細な検証、明示的な保存手順を共有する。そのファイルを元の場所で編集・保存する。プロファイルの登録と接続は［開く］の操作で行う。保存済みの資格情報を選ぶ操作では、必要に応じて選択中の既存の保管庫をロック解除し、参照を選ぶ。プロファイルを開くときと保存するときにはロック解除を求めない。すべての資格情報選択で、保管庫が空または不在の場合はその旨を表示し、作成しない。通常のロック解除や認証用の取得でも初期化しない。新規作成または保護付きの空ファイル初期化には、[保管庫の完了操作契約](vault-format-ja-jp.md#保管庫管理の完了操作)に従う明示的な管理操作が必要。

ファイルの種類ごとに、正規化した開いた場所につき独立した編集ウィンドウを一つ使う。同じ場所を再度開くと、下書きを保持したまま既存ウィンドウを復元し、前面に出す。プロファイル一覧とエクスプローラーからの編集には、プロファイルの登録と同じ場所の識別規則を適用する。別の場所へのコピーは、内部 ID が同じでもそれぞれのウィンドウで編集できる。各ウィンドウの編集対象は開いたときの場所に固定する。

保管庫の管理タブと独立した編集ウィンドウは、フォームと管理操作を共有する。管理タブでは選択中の保管庫を扱う。エクスプローラーからは指定ファイルを開き、必要に応じてマスターパスワードを求める。指定ファイルが選択中の保管庫なら、タブ、別ウィンドウ、接続でロック解除状態と確定したリビジョンを共有する。別のファイルは個別にロック解除して編集し、選択中の保管庫の設定を維持する。空、不在、破損、未対応のファイルはエラーとし、エクスプローラーからの起動では初期化しない。`.tttykey` として保存された有効な暗号化手動バックアップは通常のファイルとして開ける。

設定で選択中の保管庫を変更しても、開いている編集ウィンドウは同じファイルを扱う。管理タブと次回以降の接続には新しい選択を使う。新たに選んだ保管庫が編集ウィンドウでロック解除済みなら、その状態を引き継ぐ。影響する作業が実行中なら、設定保存前に Busy として拒否する。後述のとおり、作業終了後の明示的な保存で切り替えられる。［復元］と［退避］の確認には対象パスを表示する。独立した編集ウィンドウで退避に成功したら、退避先を表示し、確認後にウィンドウを閉じる。復元やマスターパスワード変更の完了後は、同じパスで編集ウィンドウを維持し、表示を更新する。

### 保管庫の選択と操作の表示

管理タブと独立した編集ウィンドウは、秘密を持たずファイルに固定した操作コンテキストを通して、保管庫モジュールの用途別の完了操作を使う。UI は翻訳されたフォーム、入力、ファイル選択、必要な確認と影響表示、ウィンドウの所属を担う。ロック解除済みの所有者を取り出したり、変更処理を直列化で包んだり、保存後に別の再読込みを呼んだりしない。共有する保管庫所有者が、有効なスナップショット・ルート・リビジョンと共に確定済みの一覧情報を公開する。通知に失敗した画面は、操作を繰り返さず現状の観測で追い付ける。コンテキスト、購読、操作ビューはルートを所有せず、その寿命を延ばさない。コンテキストは開いた場所と選択中・編集用の役割の世代に結び付く。A→B→A と選択しても最初の A のコンテキストは復活せず、別の役割がファイル所有者を維持していても、閉じた編集ウィンドウのコンテキストは無効になる。

選択パスの変更が旧・新保管庫の実行中の作業に影響する場合は、設定保存前に Busy を返す現行動作を維持する。設定の下書きと有効な選択を保持し、後から自動適用する予約は作らない。関連する作業が終わったら、役割変更を予約して設定リビジョンを検証してから、設定の所有者による保存を許可する。予約は完了まで新しい競合作業を防ぐ。選択パスが変わらない設定保存では、それだけを理由に役割変更を起こさない。

設定の所有者はシリアライズ、ファイルの結果、有効な設定の採用を担う。設定保存の失敗・部分成立では、以前の有効な選択と設定ストアの制限を維持する。検証済みの設定採用と、予約済みのメモリ内の役割・選択世代の更新は、新規の資格情報取得から見て一つの順序で公開する。新しい有効パスと古い資格情報所有者が同時に見える区間を作らない。採用後は、画面の閉鎖や観測待機の取消で役割移譲を放棄しない。設定ファイルと保管庫ファイルの物理的な結果は別であり、複数ファイルのトランザクションにはしない。

通常の設定保存だけでなく、設定の復元・既定値への復旧や、設定保存の照合後に採用する場合も同じ調整を使う。初回起動の設定読込みは、既存所有者の役割変更と区別する。設定結果が未解決なら秘密でない移行の根拠を残し、後の採用では失効した所有者を使わず、通常の有効な役割を取得する。受付済みの移行は、途中で編集ウィンドウが閉じても実作業に必要な旧・新所有者を維持する。成功時には利用可能な既存の編集用所有者を昇格し、失敗時には変更前の役割に従って解放条件を再評価する。静止した未解決記録だけで編集専用の秘密の寿命を延ばさない。別の保管庫へ切り替えて戻っても外部変更による場所の制限を維持し、独立した編集ウィンドウは元の対象を扱い続ける。

共有ロック解除の利用者は、受付済みの操作や接続であり、それらを観測するビューではない。観測の取消や購読の破棄で利用者を取り除かず、一人の明示的な操作停止で他の利用者を取り消さない。対話コーディネーターは、操作と対象の識別を維持して存続中のウィンドウへ入力画面を移すか、対話を終了できる。以前の表示元からの返答は無効にする。共有入力画面の失敗・取消では参加した試行を終了し、入力画面を繰り返し開かない。遅延・重複した入力の後処理責任は一つとし、別対象への同意には使わない。UI 入力や確認を待つ間、再入が必要になる物理 mutex や高コスト KDF・インポートのワーカーを占有しない。

選択中の保管庫を使う資格情報取得は、受渡し直前に正確な参照、役割の世代、現在の利用可否を確認する。受渡し前に無効になった結果は清掃し、別の保管庫で自動再試行しない。有効な受渡しでは既存の認証所有者と寿命へ移し、選択変更のためにすべての確立済み端末接続の終了を待ったり切断したりしない。保管庫への入力と実際のネイティブ処理の清掃は、[保管庫操作契約](vault-format-ja-jp.md#保管庫管理の完了操作)に従う。

編集ウィンドウ・アプリの終了は、入力画面の所属、操作停止の要求、実 I/O・ネイティブ処理・所有者を必要とする検証、新しい調査の受付と調整する。実行中の作業は必要な所有者を維持する。静止した部分成立・未解決状態では、対象パスと保持した成果物を示す既存の閉鎖判断を使える。コンテキスト解放だけで使用中のルートを破棄しない。アプリが続く間は、画面が閉じても秘密でない結果と制限を保持する。退避が成功したら、関連する作業の終了後に旧所有者の利用可能な状態を終える。検証済みの退避後の表示失敗で移動を取り消した扱いにしたり、別の移動を許可したりしない。既存の退避先確認・独立編集ウィンドウの閉鎖と通常の最終終了を維持する。隠れた寿命やセッション記録のタイムアウトは加えない。

### 編集機能の受け入れ条件

| 場面 | 期待する動作 |
| --- | --- |
| `.ttty` を二つ選択して［開く］を選ぶか Enter を押す | ファイルごとに独立して判断し、一方の接続・登録の選択をもう一方に適用しない。接続を許可したファイルはそれぞれの端末タブで開く。 |
| `.ttty` を二つ選択して［編集］を選ぶ | 二つの編集ウィンドウで個別に保存できる。未起動なら編集ウィンドウのみを表示する。編集による登録や接続は発生しない。 |
| 編集中のプロファイルを別の入口から開く | 下書きを保持した既存ウィンドウを復元して前面に出す。別の場所にあるコピーは別ウィンドウで開く。 |
| 複数選択のうち一つの読み込みに失敗 | 対象パスのエラーを表示し、他の受け付け済みの処理を続ける。 |
| `.tttykey` を一つ開くか編集する、または複数を指定する | 一ファイルの場合は編集ウィンドウを開く。複数パスを含む保管庫の起動要求は、開いたりロック解除したりする前に拒否する。 |
| 選択中の保管庫の項目を別ウィンドウで変更 | 管理タブと次回の資格情報取得で同じ確定済みの内容を使い、再度ロック解除を求めない。 |
| 別の場所に置いた保管庫のコピーを編集 | コピーに保存し、接続では選択中のファイルを使う。コピーの編集ウィンドウを閉じると、そのロック解除状態を破棄する。 |
| A と B を開いた状態で選択を A から B に変更 | A と B の編集対象はそれぞれ維持する。管理タブと次回以降の接続では B の既存のロック解除状態を使う。 |
| プロファイル編集中に最後の端末ウィンドウを閉じる | 編集ウィンドウと下書きを維持する。通常起動でプロファイル選択を表示する。最後の編集ウィンドウを閉じて終了すると、共有していたロック解除状態も破棄する。 |
| 空または不在の保管庫を開く、または有効な保管庫を編集ウィンドウで退避 | 空・不在の場合はエラーを表示する。退避に成功した場合は退避先を表示し、確認後に編集ウィンドウを閉じる。 |

今後の検証対象は、すべての保存と復旧の結果、未知のフィールド、重複 ID とキー、同じ ID のコピー、不在または取り外し可能なプロファイル、リンク経由の相対パス、大文字と小文字を区別するフォルダー、モーダル中の起動、最後のタブの移動と閉鎖の競合、最小化時の起動、モニター取り外しと DPI 変更。この時点で実行時の検証は未実施。
