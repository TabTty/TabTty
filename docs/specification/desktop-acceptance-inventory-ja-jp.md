### 用意をお願いする Hyper-V ゲスト

VM の作成と OS のインストールは利用者が担当する。対向の OS は Ubuntu Server 24.04 LTS（amd64）に決定した。Windows ゲストはクリーン起動・容量不足・仮想 COM 用、Ubuntu ゲストは独立した接続先と SMB 共有用で、同じ Hyper-V ホストに用意する。名前とサイズは機能試験向けの推奨例。

| VM 名の例 | OS と割り当ての目安 | 引き渡し状態 |
| --- | --- | --- |
| `TabTty-W11` | サポート中の Windows 11 Pro x64 日本語版。第2世代、Secure Boot オン、仮想 TPM 2.0 オン。2 vCPU、RAM 6 GiB、OS 用 VHDX 80 GiB。 | OS 更新後、試験用アカウントでデスクトップにサインインできる状態。開発ツールを追加する前の状態を使う。[Windows 11 の VM 要件](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements#virtual-machine-support) |
| `TabTty-Peer` | Ubuntu Server 24.04 LTS（amd64）。第2世代、2 vCPU、RAM 3 GiB、OS 用 VHDX 32 GiB。Linux の Secure Boot を使う場合は Microsoft UEFI Certificate Authority テンプレート。 | OS 更新後、試験用アカウントでコンソールにログインできる状態。検証担当が Windows ゲストとの疎通を確認し、SSH・SFTP・Telnet・SMB を準備する。[Ubuntu 24.04 LTS](https://documentation.ubuntu.com/release-notes/24.04/) · [Hyper-V の Ubuntu ゲスト表](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/should-i-create-a-generation-1-or-2-virtual-machine-in-hyper-v#ubuntu-guest-operating-system-support) |

引き渡しは実際の VM 名と、検証担当が VMConnect を使える Hyper-V ホストを知らせればよい。サインインや権限の承認が必要な場合は対象の画面で行う。検証担当がクリーン状態のチェックポイントを取り、専用ディスク・仮想 COM・対向サービスを準備する。試験時の2台はプライベート仮想スイッチで接続し、OS 更新や試験パッケージ取得に使った外部向け接続を外す。[仮想スイッチの接続範囲](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#virtual-switch)

**仮想 COM は実測で可否を決める。** Microsoft の機能表は第2世代の COM に対応すると記載し、機能概要は名前付きパイプ経由のアプリ用 COM を第1世代に限定している。Secure Boot を有効にした第2世代ゲストで、TabTty が通常の COM を開き、ホストの名前付きパイプと双方向に通信できた構成を記録する。標準機能で成立しない場合は、使い捨てのゲスト複製上で、署名と利用条件を確認した仮想 COM ペアを代替候補とする。ゲスト内で一方を TabTty、他方を検証プログラムが開く。この場合も物理信号の項目は未実施のまま扱う。[Microsoft の機能表](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/hyper-v-feature-compatibility-by-generation-and-guest#development-and-test) · [Microsoft の機能概要](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#controllers-and-ports) · [検証手順と代替候補](../drafts/hyper-v-serial-validation.md)

**障害試験は VM 内に限定する。** 容量不足、権限剝奪、ファイル破損・削除、共有停止、通信遮断、強制終了、資格情報やホスト鍵の破壊的な復旧は、チェックポイントから復元できるゲストの専用データで実施する。容量不足の開始前に、対象ボリュームのラベル・ディスク識別子・容量と、VHDX を置くホストの空き・チェックポイント差分の余裕を確認する。ホストやゲストの OS ボリューム、リダイレクトしたドライブ、業務用共有には書き込む負荷を向けない。試験後は証跡を確保してゲストを復元する。[仮想ディスクの種類](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/hyper-v-server/storage-io-performance#virtual-disks) · [チェックポイントの格納と統合](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints#deleting-checkpoints) · [VMConnect の共有設定](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enhanced-session-mode)

検証担当が、配布 ZIP を一時的な受け渡し用ドライブ、または仮想 DVD に接続した ISO で渡す。ZIP をゲスト内のローカルディスクにコピーし、ホスト側と SHA-256 を照合する。受け渡し用ドライブを切断するか ISO を取り出してから、ゲスト内で展開し起動する。ホストドライブがゲストに見えていると、別ビルドの起動や障害試験の対象パスの取り違えが起こり得るため、実行前に切り離す。[VMConnect のローカルリソース](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/use-local-resources-virtual-machine-connection) · [VMConnect の仮想メディア](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/virtual-machine-connection)

| 10　仮想 COM | ゲストが列挙した COM を保存済みプロファイルで 9600/8N1・フロー制御なしで開く。方向別に異なる既知データを流し、対向と Raw を照合する。排他オープン、解放後の再接続、古い入力の再送の有無を確認する。XON/XOFF は停止・再開を対向で観測できた条件だけを記録する。機器依存の baud／パリティ／ストップビット、RTS/CTS・DTR/DSR、約1秒の BREAK 波形、物理オーバーランと USB 抜き差しは未実施として残す。 | E2・E5 |
| 11　資格情報 vault | 空の vault は明示的な管理操作で初期化する。暗号化した試験用秘密鍵を取り込み、元鍵ファイルのない別 Windows にプロファイルと vault をコピーしてログインする。初回解除を複数窓・編集画面で共有し、アプリ終了後は再度解除を求める。ホスト鍵の信頼は移行先で確認する。マスター変更、旧バックアップからの復元、退避・再作成、同名項目、外部変更、取消を試す。原本・参照の整合性と、ダミーの秘密がプロファイルや診断ログに入らないことを確認する。 | E1・E2・E4・E6 |
| 12　SFTP | 非選択の SSH タブから、そのアカウントを指す転送窓を開く。左右ペイン間のドラッグ・ボタンで、空フォルダー・日本語名・大きなファイルを双方向に転送し、ハッシュを比較する。作成・改名・削除、上書き／スキップ／取消、権限拒否、ローカルのごみ箱、転送中のタブ移動と切断後の結果・再試行を確認する。サブシステム拒否後もシェルが使え、Raw にファイル内容が混ざらない。 | E1・E4・E6 |
| 13　記録と保存障害 | 記録 Off と3形式の各組合せで既知データを流す。Raw は受信バイト、Text は CR/BS による編集後の受信行、Terminal は有効なローカルエコーを含む表示操作として照合する。初期保存失敗は接続開始前に表示し、記録中に E6 のゲスト専用 NTFS ボリュームを満杯にする場合と、対向 VM の試験用共有を切断する場合の両方で、端末操作を続けられる。一時停止・再開・再試行は新しいパートへ進み、古い内容を重複させない。終了が5秒滞った時の「待つ」と後から損失を了承する経路を両方試す。 | E1・E4・E6 |
| 14　AI 協業対応ビルド | 実際の Codex 会話で共有タブを列挙し、照合コードを確認する。使い捨てタブを共有し、現在画面と保持履歴の固有文字列を読む。操作権を明示付与して無害な文字列を送り、対向が期待するバイト列を1回だけ受信したことを確認する。操作権の返却・共有終了後の閲覧可否、入力拒否、未共有タブの非開示を確かめる。top・Vim、ブリッジ喪失、別ログオン・昇格差は[AI 検証計画](ai-collaboration-validation-ja-jp.md)で扱う。 | E1・E2・E4・E7 |
| 15　マクロ対応ビルド | 初版では対象外のマクロについて、実装済みビルドを評価する場合に実施する。Explorer・アプリ・CLI から試験用 .tttym を起動し、新しいタブ、引数・相対パス、待機・対話、Pause・Resume・Stop、記録失敗後の明示再開を試す。停止後に健全な接続へ手動入力でき、移動・切断後に古いマクロが送信しない。 | E1・E4、COM 使用時は E5 |
| 16　複合負荷 | 複数のペインを表示し、スクロール・窓移動・最小化・復元中も各タブの受信と記録が続くかを測る。AI 対応では独立した2本のブリッジ接続で20タブ共有・10万行の履歴・過負荷中の引き継ぎ、マクロ対応では16マクロ＋通常4接続の Pause・Stop を追加する。通常操作 p95 ≤100 ms、該当する過負荷時の制御受付 p95 ≤250 ms。画面の停止時間、最大値、後処理完了時間、ログ一致も個別に記録する。 | E3・E4・E8 |

判定根拠は、[プロファイル・Windows](persistence-and-windows-ja-jp.md)、[端末](terminal-and-encodings-ja-jp.md)、[分割・同時送信](broadcast-and-split-views-ja-jp.md)、[接続と認証](transports-and-authentication-ja-jp.md)、[vault](vault-format-ja-jp.md)、[SFTP](file-transfer-ja-jp.md)、[記録と貼り付け](session-and-recording-ja-jp.md)、[AI 検証](ai-collaboration-validation-ja-jp.md)、[マクロ検証](../drafts/macro-validation.md)、[受け入れ条件](resources-and-validation-ja-jp.md)。

## 利用者に依頼が必要になる条件

| 条件 | 依頼する最小限のこと | その後の検証担当の作業 |
| --- | --- | --- |
| Hyper-V ゲストを引き渡す | 上記の VM 作成・OS 導入と、対象ホスト・VM 名の連絡。必要な場合のみ、試験用セッションへのサインインまたは権限の承認。 | チェックポイント、仮想 COM、専用ディスク、対向サービス、ダミー資格情報・データ、障害の再現と復元を担当する。 |
| E3 の異なる DPI の実画面や、E7 の試験用 Codex セッションに所有者の操作・権限が要る | 必要なアクセスを許可し、実画面の接続・取り外しや試験用セッションへのサインインが必要な場合のみ協力する。 | 設定・操作・計測・証跡の比較を実行する。物理 COM を必要とするケースの扱いは項目10に記録した。 |
| 入力注入・録音では物理動作や発話を判定できない | 必要な場合だけ、指定した1回のボタン保持・解放、または指定箇所で聞こえた読み上げの報告を依頼する。 | それ以外の画面遷移、候補位置、対向バイト、フォーカス、再現性を記録する。 |

各ケースの記録には、対象 ZIP の SHA-256、Windows・IME・DPI・対向の構成、操作と期待値、実際の画面・音声・受信バイト・生成ファイルのうち判定に必要なもの、合格／不合格／未実施と理由を残す。試験用の鍵・パスワード・OTP は検証担当が生成する。独自 SSH・vault・ネイティブの秘密処理に対する独立レビューは別のリリース条件で、検証担当がレビュー資料を準備し、独立した担当者の確保が必要な場合のみ調整を依頼する。[リリース条件](resources-and-validation.md#implementation-and-release-gates)
