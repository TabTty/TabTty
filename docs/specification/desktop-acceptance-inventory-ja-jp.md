## 現行候補での実施順と重点項目

今回の合否判定から負荷試験（項目16・環境 E8）を除外する。実施済みの短時間測定は参考記録として残す。測定値が基準を超えた原因は特定していない。

利用者による VM 準備は完了した。実施前に VM 名、コンソールへのアクセス、ゲスト間の隔離ネットワークを確認する。現行のソースから作った配布 ZIP と、使用する場合は VSIX のコミット・SHA-256 を記録する。過去の配布物にはそこで観測した結果を紐づける。

### ホストでの回帰・連携試験

現行 Release のテストビルドで Core 98件、基本 WPF 34件が合格した。プロファイルの信頼とログ衝突、ブロードキャストと分割、AI 連携、マクロ起動とプロファイル接続、保管庫の初回利用と名前変更、エディター、切断済みタブ、端末の終了、実際の Vim、マクロの SMB・Cloud Files 定数、貼り付け制御、SFTP バッチの個別試験も合格した。独立した Microsoft OpenSSH で公開鍵ログイン、シェル、SFTP、鍵再交換を確認した。Release 配布検証に合格し、別コピーで DLL 欠落、Debug メタデータ、ターゲット不一致、DLL ハッシュ不一致が拒否された。配布版 MCP ブリッジの7ケースが合格した。VSIX のプロバイダーは `a77d137` の同梱パーサーを使った再試行で合格した。エディターのソースは `13cb898` まで同じだった。実際の VS Code CLI で試験専用プロファイルに導入し、拡張一覧に `tabtty.tabtty-macro@0.2.0` が出ることを確認した。エディター画面での操作は未確認。

- SFTP 転送ウィンドウの終了試験は、一覧パスとドロップ時の確認の検証を通過した後、`CheckDisconnectedTransferAsync` で2回タイムアウトした。別の SFTP バッチ試験は合格した。終了試験がタイムアウトした原因は未確定。
- 20接続・30秒の負荷試験では20接続すべてで Raw の照合が通り、サーバー側の鍵再交換を記録したが、SFTP の完了は0件だった。他の回帰試験を並行させずに120秒で再実行すると、操作40回、SFTP 6件が完了し、Raw は20接続すべてで一致し、切断は0件だった。操作と停止の p95 はそれぞれ 737.95 ms、937.56 ms で、目標の100 ms、250 msを超過した。実行スクリプトは正常終了したが、両方の性能判定は不合格だった。測定値は今回の合否判定に含めない。
- 同じ Windows ログオンで配布版の GUI を起動すると、一時的な Codex App Server スレッドが全7ツールを検出した。直接呼び出しで共有0件を確認し、Codex モデルも `tabtty_list_shared_sessions` の実行を完了した。GUI が起動していないと旧版・現行版とも MCP 初期化時に切断された。現行配布版でのペアリングと、モデルによる画面・履歴の読み取り、入力、共有解除は未確認。
- このほか、オフラインでの完全な初回起動、関連付け解除、IME・ナレーター、隔離クリップボード、実 SMB 共有2箇所を使うログ試験、COM 通信、異倍率マルチディスプレイが残る。ホストの隔離クリップボード試験は専用ウィンドウステーションを開くときにアクセス拒否になった。

Ubuntu 24.04 の対向 VM に、別々のディレクトリを使う認証付き Samba 共有 `tabtty-log-a` と `tabtty-log-b` を用意した。Samba の TCP 445 は内部インターフェースとループバックで待ち受ける。設定検証では両共有について Windows 試験ゲストを許可し、ホストを拒否した。ループバック経由の認証付き SMB 接続で各共有に異なるマーカーを書き込み、サーバー側のファイルを照合した。

### 残項目の確認（配布版 `13cb898`）

- **ディスク復旧後の記録は合格。** ディスク満杯の書き込み失敗後に同じ接続で記録を再開したところ、新しい Raw パートの 40,993 バイトと SHA-256 が再開後に送ったデータに完全一致した。それ以前のデータは新しいパートに入らず、前パートの 64,540 バイトは送信データの先頭と一致した。試験用 VHDX と ISO は取り外した。
- **仮想 COM の Raw は合格。** NUL、UTF-8 の `£`、CRLF を含むホスト送信27バイトと記録ファイルが完全一致した。XOFF 中に対向への送信は0バイトで、XON 後に送信された。長く止めた回では保留したマーカーの先頭2バイトが欠け、XON 後に改めて送った同じマーカーは完全一致した。実装の COM 書き込みタイムアウトは5秒で、短い停止での全バイト保持は今回の測定では判定していない。物理フロー制御・信号は機器がないためスキップした。
- **ペイン間の IME は不合格。** 基本セッションで左ペインに `nihongo` を入力し、候補一覧で「にほんご」を選んだ状態のまま、確定せず右ペインをクリックした。仕様では未確定文字を破棄して送信しない。Ubuntu 対向では2回とも「にほんご」を受信した。2回目はペイン移動後に新しい変換を始めず Enter を1回押し、期待値 `tabtty-qa-recheck-<CR><LF>` に対して実測は `tabtty-qa-recheck-にほんご<CR><LF>` だった。[IME の仕様](terminal-and-encodings.md)
- **ナレーターの音声はスキップ。** 前の試験でフォーカス枠の追従を確認した。今回の試験セッションでは実際の読み上げを収録できなかった。

### 未完了 Issue の追加試験

- 専用の Windows ウィンドウステーションで実際の Unicode クリップボードを使った。ASCII、日本語、補助文字のいずれも UTF-16 で1,024バイトなら直送され、対向で内容が一致した。1,023バイトを上限とすると、1,024バイトの内容全体を拒否した。1,026バイトでは確認が一度だけ表示され、キャンセルで送信ゼロ、送信操作で元の内容がすべて届いた。CR と LF もそれぞれ確認が出た。日本語設定画面はゼロ・負数・範囲外の上限値を拒否し、変更の破棄で保存値を維持した。[#66](https://github.com/TabTty/TabTty/issues/66)
- 複数グループの選択を表示順に開き、起点の分割グループに A・B・C が並んだ。A の実 SSH ホスト鍵確認が開いている間に B と C が接続し、キャンセルで A だけが閉じた。以前から開いていた B は接続を維持した。グループ絞り込み、英日件数表示、未選択行のコンテキストメニュー、ダブルクリックでの編集を確認した。ホバー、矢印のクリック、右矢印キーでサブメニューが開いた。グループ名のクリックか Enter では表示順に全件が開き、サブメニューで選ぶと個別に開いた。[#83](https://github.com/TabTty/TabTty/issues/83)
- 登録済み SSH プロファイルの確認中に接続先を変更した。承認後は確認済みの接続先を使用し、ホスト鍵承認の後にパスワードが求められた。日本語で一覧から開き直すと変更が再確認され、キャンセルで変更先には接続しなかった。変更済みの登録済みシリアルプロファイルもキャンセルが既定で、取り消すとポートを開かなかった。英日の CLI 引数からの WPF 起動処理では、繰り返しの「今回だけ接続」、登録した接続の再接続、変更後の再確認を試験した。接続拒否の後も登録が残った。実 SMB 経由で UNC 上の試験用プロファイルを読み取ると、読み取り許可の後に独立した接続確認が出た。[#69](https://github.com/TabTty/TabTty/issues/69) · [#70](https://github.com/TabTty/TabTty/issues/70)
- Telnet 切断後にタブの保持出力を解放しても、取得済みスナップショットには対向のマーカーが残った。[#39](https://github.com/TabTty/TabTty/issues/39)
- Windows ゲストで信頼済み COM1 プロファイルを一覧から開いた。Hyper-V のパイプ対向は、600 ms の XOFF 中に送信を受け取らず、XON 後に全バイトを一度受け取った。パイプ対向と端末の再接続後には新しいマーカーだけが届いた。ファイル変更後は英日で再確認が出て、キャンセルで開かず、承認で COM1 を再開した。初回の Raw ログに対向の確認マーカーが残った。以前の長時間停止で欠けた2バイトの原因は未確定。[#45](https://github.com/TabTty/TabTty/issues/45) · [シリアル試験手順](../drafts/hyper-v-serial-validation.md)
- 同一ディスプレイで端末内の実マウスドラッグを開始し、ボタンを押している間に試験プログラムから通常のタブ移動を実行した。2つの Telnet 対向は押下と解放を各1回受け取り、移動後も両方の接続は維持された。[#14](https://github.com/TabTty/TabTty/issues/14)

| `TabTty-W11` | サポート中の Windows 11 Pro x64 日本語版。第2世代、Secure Boot オン、仮想 TPM 2.0 オン。2 vCPU、RAM 6 GiB、OS 用 VHDX 80 GiB。 | OS 更新後、試験用アカウントでデスクトップにサインインできる状態。開発ツールを追加する前の状態を使う。[Windows 11 の VM 要件](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements#virtual-machine-support) |

引き渡しは実際の VM 名と、検証担当が VMConnect を使える Hyper-V ホストを知らせればよい。サインインや権限の承認が必要な場合は対象の画面で行う。検証担当がクリーン状態のチェックポイントを取り、専用ディスク・仮想 COM・対向サービスを準備する。試験時の2台はプライベート仮想スイッチで接続し、OS 更新や試験パッケージ取得に使った外部向け接続を外す。[仮想スイッチの接続範囲](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#virtual-switch)

**仮想 COM は実測で可否を決める。** Microsoft の機能表は第2世代の COM に対応すると記載し、機能概要は名前付きパイプ経由のアプリ用 COM を第1世代に限定している。Secure Boot を有効にした第2世代ゲストで、TabTty が通常の COM を開き、ホストの名前付きパイプと双方向に通信できた構成を記録する。標準機能で成立しない場合は、使い捨てのゲスト複製上で、署名と利用条件を確認した仮想 COM ペアを代替候補とする。ゲスト内で一方を TabTty、他方を検証プログラムが開く。この場合も物理信号の項目は未実施のまま扱う。[Microsoft の機能表](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/hyper-v-feature-compatibility-by-generation-and-guest#development-and-test) · [Microsoft の機能概要](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#controllers-and-ports) · [検証手順と代替候補](../drafts/hyper-v-serial-validation.md)

**障害試験は VM 内に限定する。** 容量不足、権限剝奪、ファイル破損・削除、共有停止、通信遮断、強制終了、資格情報やホスト鍵の破壊的な復旧は、チェックポイントから復元できるゲストの専用データで実施する。容量不足の開始前に、対象ボリュームのラベル・ディスク識別子・容量と、VHDX を置くホストの空き・チェックポイント差分の余裕を確認する。ホストやゲストの OS ボリューム、リダイレクトしたドライブ、業務用共有には書き込む負荷を向けない。試験後は証跡を確保してゲストを復元する。[仮想ディスクの種類](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/hyper-v-server/storage-io-performance#virtual-disks) · [チェックポイントの格納と統合](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints#deleting-checkpoints) · [VMConnect の共有設定](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enhanced-session-mode)

検証担当が、配布 ZIP を一時的な受け渡し用ドライブ、または仮想 DVD に接続した ISO で渡す。ZIP をゲスト内のローカルディスクにコピーし、ホスト側と SHA-256 を照合する。受け渡し用ドライブを切断するか ISO を取り出してから、ゲスト内で展開し起動する。ホストドライブがゲストに見えていると、別ビルドの起動や障害試験の対象パスの取り違えが起こり得るため、実行前に切り離す。[VMConnect のローカルリソース](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/use-local-resources-virtual-machine-connection) · [VMConnect の仮想メディア](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/virtual-machine-connection)

## 利用者に依頼が必要になる条件

| 条件 | 依頼する最小限のこと | その後の検証担当の作業 |
| --- | --- | --- |
| Hyper-V ゲストを引き渡す | 対象ホストと実際の VM 名の連絡。必要な場合のみ、試験用セッションへのサインインまたは権限の承認。 | チェックポイント、仮想 COM、専用ディスク、対向サービス、ダミー資格情報・データ、障害の再現と復元を担当する。 |
| E3 の異なる DPI の実画面や、E7 の試験用 Codex セッションに所有者の操作・権限が要る | 必要なアクセスを許可し、実画面の接続・取り外しや試験用セッションへのサインインが必要な場合のみ協力する。 | 設定・操作・計測・証跡の比較を実行する。物理 COM を必要とするケースの扱いは項目10に記録した。 |
| 入力注入・録音では物理動作や発話を判定できない | 必要な場合だけ、指定した1回のボタン保持・解放、または指定箇所で聞こえた読み上げの報告を依頼する。 | それ以外の画面遷移、候補位置、対向バイト、フォーカス、再現性を記録する。 |

各ケースの記録には、対象 ZIP の SHA-256、Windows・IME・DPI・対向の構成、操作と期待値、実際の画面・音声・受信バイト・生成ファイルのうち判定に必要なもの、合格／不合格／未実施と理由を残す。試験用の鍵・パスワード・OTP は検証担当が生成する。独自 SSH・vault・ネイティブの秘密処理に対する独立レビューは別のリリース条件で、検証担当がレビュー資料を準備し、独立した担当者の確保が必要な場合のみ調整を依頼する。[リリース条件](resources-and-validation.md#implementation-and-release-gates)
