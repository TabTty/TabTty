# トランスポートと認証の契約

2026-11-10 時点の仕様に、2026-11-18 の Q17～Q19 で合意した SSH チャネルの共通契約を反映する。既存の SSH/OpenSSL ADR と Q131～Q143、Q161 は引き続き判断基準とする。アルゴリズム名と順序は `../drafts/ssh-transport-policy-proposals.md` に記載する。この文書では弱いフォールバックを追加せず、フレーミング、状態、識別情報、リソースの契約を確定する。実行時の証跡は[実装状況](implementation-status-ja-jp.md)を参照。

## 接続先とホストレコード

DNS 解決と信頼の照会で同じ正規接続先を使う。DNS 名または明示的な IPv4/IPv6 を受け付け、ポートは別に指定する。IPv4 は 0～255 の十進オクテット四つに限る。8 進数、16 進数、単一整数の省略記法は使えない。角括弧付き IPv6 は完全なホストリテラルとしてのみ解析する。識別には括弧を外し、アドレスのバイト列を正規化して数値スコープ ID を保持する。IPv4 マップド IPv6 は IPv6 のままとする。ホスト欄では URI スキーム、認証情報、パスやクエリ断片、空白や制御文字、曖昧な host:port の組み合わせを拒否する。

DNS には Win32 IdnToAscii を直接使う。UTF-16 入力長を明示し、IDN_USE_STD3_ASCII_RULES だけを設定する。IDN_ALLOW_UNASSIGNED、IDN_RAW_PUNYCODE、IDN_EMAIL_ADDRESS は設定しない。環境によって ICU と NLS を選ぶ .NET IdnMapping を使わず、Windows NLS に固定する。Unicode の区切りはその処理系に従って変換し、明示的な末尾ドット一つを除いてラベルごとに 63 バイト、全体で 253 バイトの上限を適用し、結果を ASCII の小文字にする。末尾ドットの有無は保持する。DNS 検索、別名、正規名の結果を信頼キーに反映しない。別のマッピングを自作せず、この処理系を使う。得られた ASCII の接続先をセッションに記録する。サポートする Windows とランタイムの組み合わせごとにラベルと正規化のベクトルを検証する。OS の変換に変更があれば信頼上の識別の互換性を確認し、既存レコードを黙って別の接続先へ移行しない。

`host-keys.json` は共通のバージョンフィールドと `destinations` を持つ。各項目は `kind`（`dns/ipv4/ipv6`）、正規の `host`、null 許容の `scopeId`、`port`、`keys` を含む。鍵ごとに `format`、正規 Base64 の `publicBlob`、SHA-256 フィンガープリント、UTC の `approvedAt` を持つ。接続先ごとに同じ形式の鍵は一つ。ECDSA は曲線ごとに形式が異なり、RSA SHA-2 署名は `ssh-rsa` 鍵ブロブを共有する。読み込み時にブロブの種類、サイズ、フィンガープリントを検証する。ホストレコードは vault から独立する。

ホスト署名の優先順は ssh-ed25519、ecdsa-sha2-nistp256、ecdsa-sha2-nistp384、ecdsa-sha2-nistp521、rsa-sha2-512、rsa-sha2-256。その接続先で承認済みの鍵形式を未知の形式より前に移し、グループ内の相対順は保持する。別の鍵や新しい鍵が提示された場合は、合意済みの初回または変更時の承認を要する。信頼の提示や認証情報の使用前に交換署名を検証する。RSA は PKCS#1 v1.5 と SHA-2 を使う。SHA-1 と RSA-PSS は使わない。ホストの別名に信頼を継承せず、機会に応じた鍵の自動学習を行わない。

接続時や鍵再交換時に登録済みの接続先が別形式の鍵を提示した場合、承認画面には登録済みのホストであることを明示する。保存済みの鍵の形式とフィンガープリントを、提示された形式とフィンガープリントとともに表示する。既定はキャンセルとする。利用者が別経路で照合して追加を承認した場合は、その鍵だけを追加し、既存の形式を保持する。[RFC 4251 第 9.3.4 節](https://www.rfc-editor.org/rfc/rfc4251.html#section-9.3.4)

## SSH トランスポートのフレーミングと鍵世代

SSH 2.0 または互換の 1.99 の識別を受け付ける。SSH1 パケットは受け付けない。識別行は CRLF を含めて 255 バイトまで。先行するサーバー行は 64 KiB と 256 行まで。端末データより前にあり、Raw/Text/Terminal には出力しない。通常の接続期限を適用し、バイナリや NUL を含む不正な識別は拒否する。

受け付ける完全なバイナリパケットの最大値は、長さと MAC またはタグを含めて 256 KiB。割り当てやディスパッチの前に整数加算、利用可能バイト、暗号のアラインメント、4 以上のパディング長、ペイロード範囲、アルゴリズム固有のフレーミングを検査する。RFC 4253 が求める 32768 バイトのペイロードと 35000 バイトのパケットの処理能力を満たす。より大きな上限は TabTty の防御上の選択。未認証の平文をディスパッチしない。成立しない状態、種別、長さの組み合わせは拒否し、MAC やタグに失敗した後に再同期を試みない。

GCM と CTR+EtM には別の保護アダプターを使う。OpenSSH GCM では平文の長さを AAD とし、暗号化本体にパディング長、ペイロード、パディングを含める。ノンスは SSH で導出した固定の 4 バイトの接頭部と 8 バイトの呼び出しカウンター、タグは 16 バイト。再利用せずに進め、カウンターが枯渇する前に失敗とする。MAC リストに共通項目がないことだけで GCM を拒否しない。EtM では内容の復号や公開より先に、シーケンス番号、平文のパケット長、暗号化本体を選択済みの HMAC で認証する。OpenSSH の厳密な構成に従う。

KEXINIT はカテゴリと方向ごとに許可済みアルゴリズム一つを交渉する。first_kex_packet_follows は必要に応じて誤った推測パケットを厳密に一つ破棄する。最初の交換ハッシュをセッション識別子として保持し続ける。NEWKEYS 自体には旧保護を使う。送信後は TX だけ、受信後は RX だけを切り替える。旧方向の状態は必要な間だけ保持し、その後消去する。

ext-info-c と、合意済みの strict KEX のクライアント名二つを通知する。厳密な初回 KEX では接続先の最初のバイナリパケットが KEXINIT であることを確認し、禁止される非 KEX メッセージや重複メッセージを拒否する。鍵再交換では RFC のトランスポート順序に従い、合法な送信済み通信も処理する。初回専用の厳密な除外をすべての再交換に適用しない。strict KEX を交渉した場合は初回も含め、各 NEWKEYS の後でその方向のシーケンス番号をリセットする。それ以外ではプロトコルどおり 2^32 を法として連続させる。

EXT_INFO は任意。NEWKEYS 後と認証成功前の許可された位置で解析する。正しい形式はパケット上限まで受け入れ、残りバイト数から個数の上限を求める。拡張や値に任意の小さい上限は設けない。未知の値は NUL を含めてバイナリとし、読み飛ばせる。server-sig-algs 拡張はユーザー署名に適用する。ホスト鍵の交渉には使わない。

保護バイト数は方向と鍵世代ごとに長さ、暗号化本体、MAC またはタグの合計を数える。NEWKEYS は旧世代に計上する。交換完了から 1 GiB または 1 時間で鍵再交換を開始する。KEX が必要とする間は通常の送信ペイロードを止め、上限付きの入力キューを維持する。世代ごとの厳格な上限は保護データ 2 GiB、2^31 パケット、2^32 AES ブロック、GCM 呼び出しカウンターが周回しないこと。最初に達した上限を適用する。厳格な境界に達する前に最大サイズのパケット一つと KEX 作業を予約する。残り予算で交換を完了できなければ切断する。1 GiB の開始条件を満たしても厳格な上限は適用する。双方の同時または接続先からの鍵再交換に対応し、既存の期限と信頼ダイアログの除外を適用する。

共有秘密には SSH 固有の符号化を使う。ハイブリッドの mlkem768x25519-sha256 は HASH(K_PQ || K_CL) を RFC の厳密な長さと順序に従って SSH 文字列にする。TLS ハイブリッドの符号化や mpint への代用は行わない。X25519 の共有秘密がすべてゼロの場合や長さが違う場合は拒否する。ECDH の名前付き曲線上の点と有限体の公開値は、固定グループごとの要件で検証する。暗号プリミティブは OpenSSL が実行し、アダプターがすべての戻り値を確認して不要な秘密情報を消去する。両方向とも圧縮は none。

## 認証とユーザー向けメッセージ

SSH ホスト鍵の初回承認と置き換えの画面では、管理者から別経路で入手したフィンガープリントとの照合を案内する。キーボード対話認証では毎ラウンド、スクロールする質問欄の上に、検証済みの接続先ホストとポートを固定表示する。質問はそのサーバーが提示し、回答もそこへ送られること、TabTty の保管庫のマスターパスワードはこの画面に入力しないことを示す。送信ボタンにも回答がサーバーに送られることを明記する。[RFC 4256 第 3.3 節](https://www.rfc-editor.org/rfc/rfc4256.html#section-3.3)

今後の実装では、読み込んだ版の SSH 接続先、アカウント、資格情報の参照を使う前に、接続時のプロファイル信頼規則を適用する。接続が許可された場合はホスト鍵を検証してから、選択中の vault から認証情報を取得する。パスワード認証では、そのサーバーにそのアカウント用のパスワードを送る。この動作を SSH プロファイルの編集画面と保存済みパスワードの選択画面に明示する。エクスプローラーの［編集］では接続せずに内容を確認できる。[プロファイルの信頼仕様](profile-trust-ja-jp.md)

SSH ユーザー名は読み込んだ版の接続プロファイルから取得する。`none`、部分成功後、別方式への切り替えを含め、すべてのユーザー認証要求で同じ値を使う。vault の項目を選ぶと、認証情報の参照だけが変わる。[プロファイルのフィールド](persistence-and-windows-ja-jp.md#プロファイル-v1-のフィールド)

ホスト鍵を検証した後、最初の SSH ユーザー認証要求を送る前に、有効な方式の保存済み参照を選択中の vault で確認し、名前の完全一致と期待する種類を検証する。種類が異なる場合は接続試行を終了する。秘密情報の受け渡し時にも、既存の規則に従って参照と vault のリビジョンを照合する。[RFC 4252 第 5 節](https://www.rfc-editor.org/rfc/rfc4252.html#section-5)

SSH 認証で vault が必要になったときに、設定先が不在または 0 バイトと確認できた場合は、設定先のパスと状態を表示し、その vault を必要とする方式を今回の試行では利用不可とする。保存済みの項目を指定している場合は、目的の項目がある vault の選択またはバックアップからの復元を案内する。接続時に鍵を選ぶ場合は、［vault の管理］で使用する鍵を取り込むよう案内する。選択中の有効な vault に指定した名前の秘密鍵が見つからない場合は、その理由を表示し、今回の試行では公開鍵認証を利用不可とする。いずれも、設定先のパス、ファイル、参照は維持する。

理由を表示した後、プロファイルで許可され、サーバーが現時点で提示している、利用可能な次の方式へ進む。例えば手入力に設定したパスワード認証は続行できるが、同じ不在の vault を参照する保存済みパスワードは利用できない。次の方式がなければ、エラーダイアログを表示して接続試行を終了する。不一致、キャンセル、その他の vault エラーには既存の扱いを適用する。

プロファイルに鍵の参照がなく SSH 認証中に鍵を選ぶ画面では、検証済みのホストとポート、確定した SSH ユーザー名を表示し、選択中の vault にあるすべての秘密鍵を候補にする。有効な vault に秘密鍵がなければ、その旨を表示する。現在の段階では公開鍵認証を選択肢から外し、プロファイルで許可され、サーバーが現時点で提示している次の方式へ進む。該当する方式がなければ接続試行を終了する。

候補がある場合、現在の段階で使える別の方式があれば、鍵の選択画面に［別の認証方式を試す］を表示する。この操作を選ぶと、現在の段階で公開鍵認証をスキップする。［接続をキャンセル］は接続試行を終了する。候補には一意な名前、公開鍵の種類、SHA-256 フィンガープリントを表示する。項目名と候補の上に表示する SSH ユーザー名に含まれる制御文字や書式制御文字は可視化し、同じように見える項目も区別できるようにする。[RFC 4252 第 5.1 節](https://www.rfc-editor.org/rfc/rfc4252.html#section-5.1)・[第 7 節](https://www.rfc-editor.org/rfc/rfc4252.html#section-7)

暗号化とホストの検証の後でのみ ssh-userauth サービスに入る。方式固有のメッセージ 60 は未完了の方式と要求に対応付けて処理する。認証の各段階で、サーバーが提示し、試行回数の上限内にあるパスワード認証と公開鍵認証を、プロファイルで設定した優先順に試す。使用する鍵は選択した一つとする。キーボード対話認証は既定で有効とし、その段階で利用できる方式のうち優先順を最後に固定する。最初の段階を含め、それだけが利用可能ならその時点で使う。詳細設定で無効にした場合は、すべての段階で候補から外す。[RFC 4252 第 4 節](https://www.rfc-editor.org/rfc/rfc4252.html#section-4)

server-sig-algs があれば使う。ない場合は、選択した RSA 鍵で SHA-512、次に SHA-256 を一度ずつ試し、SHA-1 は使わない。PK_OK だけでは認証は成立しない。認証段階が変わらない限り同じ鍵や署名の試行を繰り返さない。部分成功では段階を進め、受理された静的要素を使用済みにする。別の識別情報として再送しない。

段階ごとにパスワード送信または対話の開始は 3 回まで。内部上限は要素成功の段階 8、異なる公開鍵の試行は合計 8、対話ごとのラウンド 32、要求ごとのプロンプト 32、プロンプトまたは指示ごとに UTF-8 で 8 KiB、要求または応答ごとの合計 64 KiB。プロンプト 0 件なら応答も 0 件とし、空の応答は空のままにする。未回答の対話要求は最大一つ。各プロンプトを失敗回数として数えず、認証応答のタイムアウトは追加しない。上限に達したら明示的に失敗とし、キャンセルは常に表示して使えるようにする。

パスワード変更要求は有効なサーバー手順だが初期段階では未対応。理由を表示し、設定済みの別方式またはキャンセルを選べるようにする。パスワード変更 UI は追加せず、旧パスワードを黙って再送しない。キーボード対話では、プロンプトの内容やエコーフラグから保存パスワードを自動入力しない。SSH のパスワードと応答はプロトコルの UTF-8 を使い、端末コーデックでは変換しない。合意済みの認証期間だけ秘密情報を所有する。

バナー、切断、デバッグ、指示の本文は端末ログの外で、効果を持たないネイティブ UI テキストとして描画する。通常のレイアウト用空白以外の制御はエスケープする。タブごとに最大 64 メッセージまたは 256 KiB、非対話の本文は最大 16 KiB を表示し、切り詰めは明示する。対話プロンプトの上限を超えた場合は、質問を黙って短縮せず失敗とする。任意のサーバー本文や秘密の応答を診断出力に永続化しない。ネイティブエラーの診断は上限付きのコードや分類を使い、秘密素材を除く。

パスワード認証要求とキーボード対話認証の各応答は、空の応答も含め、ペイロード、パディング長の 1 バイト、および最低 4 バイトのランダムパディングが収まる最小の 128 バイトの倍数まで暗号化本体を埋める。GCM と CTR+EtM ともにパディングは 4～131 バイトとなる。通信経路から分かるペイロード全体の長さは 128 バイト刻みの範囲に限られる。パケット上限と鍵ごとの使用量には、長さ欄とタグまたは MAC を含む実際の送信サイズを計上する。[RFC 4251 第 9.3.9 節](https://www.rfc-editor.org/rfc/rfc4251.html#section-9.3.9)、[RFC 4253 第 6 節](https://www.rfc-editor.org/rfc/rfc4253.html#section-6)

## チャネルと終了

起動時に対話端末用のセッションチャネルを一つ開き、want-reply=true で PTY、次にシェルを要求する。両方の成功、先行配信の正常完了、接続試行が現在も有効で未停止であることを確認して初めて Connected とする。exec や PTY なしへのフォールバック、自動起動コマンド、環境変数転送、転送機能、エージェントは追加しない。[ADR 0003](../adr/0003-reuse-the-tabs-ssh-connection-for-sftp.md)に従い、初期リリースにはタブの認証済み接続内で必要時に別サブシステムチャネルを使う [SFTP ファイル転送](file-transfer-ja-jp.md)を含める。以下で端末動作を定め、[SSH チャネルの共通所有](#ssh-チャネルの共通所有)で共通の SSH 規則を補完する。転送契約で SFTP のライフサイクル、チャネル分離、共有トランスポートのスケジューリングを定義する。PTY は取得した通知用端末種別、現在の文字単位の寸法、送信が UTF-8 の場合の IUTF8 を使う。確定したグリッド変更では window-change を送信する。合成した端末出力を生成せず、応答を待たない。

受信ウィンドウ 1 MiB、チャネルデータ最大 32768 を通知する。DATA と stderr の種類 1 は同じバイトウィンドウを消費する。下流の端末処理が受け付けたペイロードを解放した後でのみクレジットを返す。消費が 512 KiB に達したときか、残りが少なく進行が止まる場合にまとめて返す。ログの完了待ちでチャネルクレジットを保持しない。ログ障害は独立した方針に従う。未知の拡張データの種類はクレジットを消費し、端末とログに渡さず破棄してクレジットを戻す。ウィンドウ演算は検査付き uint32。相手の超過やオーバーフローはプロトコル障害とする。TX データは相手のウィンドウと最大パケットに従う。

未対応のチャネルの開設要求は拒否する。未知のチャネル要求やグローバル要求には want-reply が設定されている場合だけ失敗を返す。要求への応答は送信順で追跡し、新しい世代には対応付けない。SSH の死活監視には認証済みのグローバル要求 keepalive@openssh.com を応答ありで使う。成功や失敗の応答と他の有効な認証済み通信が生存の証拠になる。端末文字は送らない。合意済みの任意の間隔と回数を使う。

EOF はチャネルの受信方向全体を閉じる。一つの受信元だけを閉じることはない。一つのリデューサー境界で通常 DATA、次に stderr のデコーダーとパーサーを確定する。完了済み操作の順序を保ち、不完全な文字は一度だけ置換する。不完全な制御は破棄する。終了ステータスだけでは確定も閉鎖も行わない。CLOSE は EOF なしでも発生し得る。一度だけ確定し、最大一度応答する。双方の CLOSE でプロトコル上の閉鎖が決着しても、配信、実際の解放、識別情報の退役は下記の共通契約を満たす必要がある。ローカルの切断は未送信入力をキャンセルし、接続先の後処理に最大 2 秒を与える。exit や Ctrl+D は送らない。記録の排出には独自の所有権と待機の選択肢がある。再接続は明示的に新規接続する。

### SSH チャネルの共通所有

[アーキテクチャ検討](../drafts/whole-codebase-architecture-deepening.md#5-shared-ssh-channel-invariants)の Q17～Q19 で、既存の[端末トランスポートの interface](session-and-recording-ja-jp.md#端末ペイロードのトランスポート所有権)の内側に置く共通 SSH チャネル module を合意した。ADR 0001 と ADR 0003 に従い、一つの認証済み接続世代の中に適用する。再接続は新しい世代とし、旧コールバック、影響、容量計上は実際に決着するまで元の所有者に残す。設計は実装準備が整った状態だが、実装の許可や実行時の証跡を示すものではない。

| 所有者 | 責任 |
| --- | --- |
| 共通チャネル module | ローカルと相手の ID の組、接続世代、開設と状態の検証、独立したウィンドウとパケット上限、DATA と拡張 DATA の順序、要求応答 FIFO、方向別 EOF/CLOSE、操作結果と実際の解放。 |
| 接続の所有者 | チャネルの退役条件と連携する、衝突のない識別情報の割り当て、登録、ルーティング。単一のパケット reader と直列化 writer、公平で上限付きのスケジューリング、グローバル要求応答、鍵再交換、死活監視、接続障害。 |
| 端末トランスポートとセッション | PTY、次にシェル、確定した寸法、使用可能状態、終了情報。候補 2 の入力とエコーの方針、Rust 処理、記録の受け入れ。 |
| SFTP の所有者 | サブシステム、次に INIT/version、フレーム解析、SFTP 要求 ID と合法な応答順序の入れ替わり、[転送契約](file-transfer-ja-jp.md)に従うファイル操作結果と回復。 |

名前付きの完結した操作を使い、完了を待つ順序付き consumer と、有限で上限付きの同期 peer-request policy を OPEN より前に設定する。次の名前は interface の説明用であり、確定した型名ではない。

```text
OpenSession(options, receiveBinding) -> チャネルと開設の観測、または拒否
channel.RequestReply(preparedRequest) -> 要求操作、または拒否
channel.Notify(preparedNotification) -> 送信操作、または拒否
channel.Send(bytes, permittedStopOffsets) -> データ送信操作、または拒否
channel.Close(cause) -> そのチャネルの閉鎖操作
```

RequestReply は必ず応答を要求する。Notify はローカルの送信を報告し、相手の受理や描画を保証しない。通常の要求、通知、データは開設確認後だけ受け付ける。開設中も Close は使え、重複 Close は同じ終了処理に合流する。OPEN の受け入れ前に consumer 設定、受信、制御、閉鎖、識別情報の連携、操作と結果の容量を予約する。要求、バイト列、停止位置は受け入れ時に上限付きの不変コピーとして所有し、その後は呼び出し元が入力メモリを再利用できる。停止位置の範囲と順序を検証し、文字やフレームとしての意味は端末または SFTP の所有者が与える。拒否時は何も送信せず入力も保持しない。無制限の容量待ちキュー、呼び出し元によるクレジット返却や解放の手順、任意パケットの interface、公開のローカル EOF 操作は追加しない。

結果と進行の観測は上限付き、不変、単調かつ集約可能にする。受け入れ、プロトコルまたは送信の結果、停止状態、先行配信の決着、プロトコル上の閉鎖、チャネル所有分の実際の解放、識別情報の退役を区別する。後の配信障害によって既知のプロトコル成功を消さない。実際の解放には保留中の writer、制御、コールバック、割り当て、所有の引き渡しの決着を含むが、別途引き渡した parser/file I/O、記録、保持端末出力の解放は含めない。タイムアウト、CLOSE 交換の完了、画面の破棄だけでは解放を証明しない。待機のキャンセルは観測登録だけを解除し、module は所有作業と障害の観測を継続する。明示的 RequestStop は元の作業を対象とし、未コミット作業の送信を防いだり許可位置で止めたりできるが、コミット済み作業の撤回や閉鎖中チャネルの再開はできない。履歴を無制限に保持せず、退役済み操作の再実行や容量回収目的の未決着所有の追い出しを行わない。

#### パケットのコミットと送信

直列化 writer は、ソケットを呼ぶ直前ではなく、送信暗号、ノンス、シーケンスの最初の不可逆な変更より前にパケットをコミットする。操作単位の停止はコミットを防ぐか、コミット済みパケット全体を実完了まで writer の所有に残す。その順序の中で、相手が応答できる前に要求応答の対応付けとクレジットの予約を行う。未コミットと証明できる作業だけが予約を返せる。コミット済み暗号化や書き込みへ個別操作のキャンセルを渡さず、そのパケットを飛ばして暗号化ストリームを続けたり、暗号状態を巻き戻したり、パケットを再送したりしない。接続の終了や障害は独自の規則に従い、保留 I/O と不確定な影響は保持する。チャネルと制御パケットのコミットには鍵再交換中の制約も適用する。

チャネルごとの送信順序と、検査付きの相手およびローカルのウィンドウとパケット上限を保つ。ローカル送信が確定したバイト接頭部を速やかに単調増加で公開し、残りの未コミット部分と、コミット済み、保留中、不確定な部分を区別する。端末の所有者は新たに確定した完全な単位だけを一度ずつエコーとペーシングへ反映する。不完全な文字はエコーせず、ローカル完了を相手の受信証明としない。停止はコミット済みバイトより前へ戻れない。正常なチャネルではその後の次の許可位置まで進み、必要な接尾部をクレジット待ちの間も所有する。コーデックとブラケットの後処理は従来どおりセッションが所有する。

Close は新規作業を拒否し、不完全なアプリケーション単位も含めた未コミットの接尾部を、正確な未完了結果を残して破棄できる。現在コミット済みのパケットが決着したら、クレジット 0 の Send がフレームを完了するのを待たずに CLOSE を予定できる。停止した writer を強制完了したり期限到達だけで解放扱いにしたりはできない。途中の SFTP フレームは既存の所有者が安全に完了するか、そのチャネルの後続 DATA を止めて閉鎖する。破棄した接頭部へ新しいフレームを継ぎ足さない。最後のパケットが不確定なら、フレーム全体の送信が成功を返していなくても変更要求全体が届いた可能性がある。UnknownOutcome と回復規則は SFTP の所有者が適用し、共通 SSH 状態へファイル操作の意味を移さない。

#### 順序付き配信、要求、クレジット

reader はアプリケーションの消費を待たずにパケットを検証して振り分ける。チャネルごとに一つの順序付き、非再帰 consumer をトランスポートのロック外で実行する。I/O、クレジット、鍵再交換の待機中にセッションのリデューサーを占有せず、自身または後続コールバックを必要とする作業を待たない。停止中の consumer やクレジット 0 のチャネルが共通 writer を保持したり、他チャネルと許可された制御や鍵再交換を止めたりしてはならない。端末入力と制御を大量データより優先しつつ、転送にも上限付きの公平な進行を確保する。必須の制御は予約した上限付き容量を使う。

want-reply 要求は実際の通信上の順序で登録する。コミットを防いだ作業には通信上の応答枠を作らない。コミット済みまたは不確定な要求は、停止や待機キャンセル後も応答または安全な終了まで元の枠を保持する。Notify は枠を使わない。未要求または重複の応答はプロトコル障害の規則に従い、FIFO をずらして対応付けない。グローバル要求と SFTP 要求 ID は別の所有者が管理する。プロトコル結果は消費から独立して進む。各応答の不変な先行配信 fence は、その応答位置より前に受け付けた受信接頭部だけを対象とし、将来の全出力を待たない。端末起動は開設前に consumer を設定し、現在確定済みの寸法で PTY を要求し、成功後にシェルを要求する。使用可能状態にはシェル成功、先行配信の正常完了、現在有効で未停止の試行を必要とする。起動の失敗や停止でも候補 2 に従って安全な先行出力と元世代の排出を保持する。SFTP コールバック内ではサブシステム成功、INIT/version 完了、後続の完全フレーム、別の要求応答を待たない。

有限の peer-request policy は、I/O、UI、再入、データ待ちを行わず、上限内の端末 exit-status/signal 情報を認識し、未対応の SFTP 要求を拒否する。module は consumer とは独立して、必要な応答を受信順に最大一度所有する。未知の要求への失敗応答は want-reply がある場合だけとする。アプリケーションの事実情報はペイロードとログの外で順序付き配信を維持する。終了情報だけで EOF や既定の正常終了を意味したり、その後の有効なデータを拒否したりしない。未知の拡張データには既存の上限付き破棄とクレジット方針を適用する。

消費により返却可能になった量、予約またはキュー内の WINDOW_ADJUST、コミットされ相手へ届いた可能性のある通知、送信完了を別に管理する。キューに入っただけでは相手の送信許容量は増えない。コミット前に通知分の受信容量を予約する。送信中の通知はローカル完了前に相手へ届き得るため、受信検証は再度の通知をせずその可能性を考慮する。未コミットと証明できる通知だけがキャンセルと予約の再利用を行える。不確定な送信は接続の結果が決着するまで影響と所有を保持し、クレジットの二重返却や観測停止による送信取消の推定をしない。

端末クレジットの返却資格は、Rust 処理、別途容量を計上した記録の受け入れまたは限定的な記録失敗、生成応答の上限付き受け入れ、ペイロード割り当ての解放後に成立する。応答や WINDOW_ADJUST の実送信、ディスクのフラッシュ、描画は待たない。SFTP は別途上限管理する parser/frame 保存領域へ引き渡した接頭部だけを消費済みとする。割り当て前に長さを検証し、要求とともに応答容量を予約する。コールバック内でローカル file I/O や後続配信を待たない。コピー中の重複と上位所有者のバッファーは、チャネルクレジット返却後も計上を続ける。残りのアプリケーション規則は [SFTP フレーミングと再開設](file-transfer-ja-jp.md#sftp-チャネルの寿命と所有権)に従う。

stderr を含む DATA と拡張 DATA は従来どおりペイロードのバイト数でウィンドウを計上し、検査付き uint32、受信ウィンドウ 1 MiB、チャネルデータ上限 32 KiB を維持する。トランスポートのパケット上限はフレーミング分も独立に数える。これは SSH 文字列の長さフィールドも数える[検証済み正誤表 EID 3878](https://www.rfc-editor.org/errata/eid3878)と異なる、明示的な相互運用上の選択である。2026-11-18 の確認では [OpenSSH channels.c](https://raw.githubusercontent.com/openssh/openssh-portable/master/channels.c)（OpenBSD revision 1.478、2026-10-30）と固定した [OpenSSH 10.2p1 のソース](https://raw.githubusercontent.com/openssh/openssh-portable/V_10_2_P1/channels.c)はストリームにペイロードのみの計上を使い、4 バイトの追加はデータグラム形式に適用している。正誤表は [RFC Editor の参考用反映版](https://www.rfc-editor.org/rfc/inline-errata/rfc4254.html)で確認した。4 バイトを加えたり推測による計上方式の交渉を行ったりしない。この選択で OpenSSH コードの採用や依存関係例外の拡大は行わない。実装開始時とリリース前に指針を再確認し、独立したベクトルと実際の相手との相互運用で検証する。

#### 閉鎖、障害、上限付き所有

コミット前に防いだ OPEN は、ローカル作業の決着後に未公開の識別情報を退役できる。コミット済み OPEN は停止やタイムアウト後も登録を保持する。遅延した開設確認の相手 ID はその旧インスタンスの後処理と CLOSE にだけ結び付け、PTY、シェル、サブシステムの起動や代替インスタンスの有効化には使わない。遅延した拒否も元の試行だけを解決する。応答のないコミット済み OPEN は、安全なプロトコル終了または接続終了まで未決着として残る。レジストリはチャネルの退役条件に従い、閉鎖中の識別情報を独断で破棄したりタイムアウトだけで再利用したりしない。

EOF は方向別の事実であり、許可された逆方向の送信は残る。CLOSE は EOF なしでも到着し得る。受信を一度だけ確定し、応答も最大一度とする。同時 CLOSE や鍵再交換で遅延した制御を含め、プロトコル上の閉鎖、保留配信、実際の解放、識別情報の退役を区別する。最後の consumer コールバックが成功できなくても障害は独立して観測できる。個々の割り当ては所有者の実完了時だけ解放し、必要な未決着の識別情報と影響の記録は保持する。現在の接続世代ごとに、一つのタブに開設中、使用中、閉鎖中を通じて SFTP 枠を一つだけ持ち、安全な識別情報の退役とチャネル所有分の解放まで保持する。OPEN/CLOSE が完了しなければ明示的再開設を阻止し得るが、正常な端末は利用可能に保つ。既存の上限付き待機と受け入れ方針を維持し、追加枠や強制切断を導入しない。新しい接続によって旧世代の容量計上を消さない。

端末 Disconnect は、既存の最大 2 秒の相手側後処理猶予と接続終了を引き続き所有する。ローカル要求自体は受信の最終区切りではなく、この猶予は実際の I/O、consumer、記録の解放時間を制限しない。SFTP 全般に新しい閉鎖期限を適用せず、自動再接続や再送、新しい閉鎖確認を追加しない。

通常の SFTP チャネルやサブシステムの拒否、不正な SFTP フレーム、version、応答、SFTP consumer/file 障害は該当転送の方針に従い、正常な端末を維持する。不正な SSH フレーミングやパケット認証、チャネル識別情報や状態、過剰データ、ウィンドウのオーバーフロー、接続、鍵再交換、死活監視の障害は接続全体の障害として扱う。有効だが未知の要求と拡張種別は拒否または破棄の規則に従う。リソース枯渇を相手のプロトコル破損と偽らない。一部適用後の consumer 障害は安全な適用済み効果を保持し、通常配信を止める。再実行、偽のクレジット、最後のコールバックの成功を必要とせず障害を報告する。端末の記録だけの障害は従来の限定的で独立した方針を保つ。

使用中または閉鎖中チャネルごとに 2 MiB、アプリケーション全体で 32 MiB、フレーム本体 256 KiB という SFTP の既存ガードと、別枠の端末、ログ、要求、一覧と結果、ローカル provider の上限を維持する。相手へ与えた送信許容量、受け入れた読み取りとペイロード、コピー重複、準備済み送信、parser/reply 保存領域、実際に保留中の I/O を計上する。本当に共有している割り当てだけを一度数える。メタデータ、相手の要求と事実情報、必須応答、fence、FIFO 記録、遅延制御、観測者、スナップショット、停止と閉鎖状態、受け入れ待機者、閉鎖中の識別情報にも有限の上限を設ける。微小または 0 バイトの通信や停止の反復で無制限に記録を増やさない。開設前に制御と閉鎖の容量を予約するが、無制限の要求洪水への対応は約束しない。枯渇時は新規ローカル作業を拒否するか、既存の該当リソースの障害方針を適用する。共通 reader をアプリケーション consumer 待ちで止めない。新しいメタデータの具体的上限、バッファー形式、レジストリ方式、計測は実装開始時に確定して検証する技術上の選択とする。それを理由に解放を装ったり、停止した外部 I/O に有限時間での完了を約束したりしない。

#### 共通チャネルの今後の検証

合意済みの[27 ケースの計画](../drafts/whole-codebase-architecture-deepening.md#candidate-5-verification-plan)では通常の操作と観測を使い、内部の peer、I/O、時刻の adapter を制御する。実際の terminal/session/Rust と SFTP/file-operation の所有者、独立したプロトコルと暗号のベクトル、実際の接続先との検証を組み合わせる。これは将来そろえる証跡であり、今回の仕様作業で実行したテストではない。同じ seam で同等の動作を検証できてから補助テストを置き換え、独立したフレーミングと暗号の検証は保持する。

| ケース | 必要な証跡 |
| --- | --- |
| 1. 受け入れ拒否、不正な停止位置、元入力の変更 | 拒否は無送信。受け入れたバイト、要求、停止位置は不変で計上を維持し、待機者も有限。 |
| 2. 異なるローカルと相手の ID、ウィンドウ、パケット上限 | 正しいルーティング、宛先、分割、独立した検査付きクレジット。 |
| 3. コミット前、暗号やシーケンス変更中、保留書込中の停止 | 取り消せるのは未コミット作業だけ。writer の実決着を待ち、早期返却や再送をしない。 |
| 4. パケットとウィンドウによる端末単位の分割 | 速やかで単調な確定接頭部、完全単位の一度だけのエコーとペーシング。不完全なエコーや不確定部分の再送なし。 |
| 5. 途中 SFTP フレーム、クレジット 0、Close | フレーム完了を待たず閉鎖し、現在のパケット決着後に DATA を追加しない。端末と制御は進む。 |
| 6. 変更フレームの最後のパケットが不確定 | 全体書込成功がなくても完全な配信の可能性と必要な UnknownOutcome を報告し、盲目的に再試行しない。 |
| 7. 待機中またはコミット済み要求の停止、Notify、遅延応答 | 必要な元 FIFO 枠を保持し、防いだ作業と Notify には応答枠を作らず、遅延応答を付け替えない。 |
| 8. 遅い consumer、要求応答、その後も続く出力 | プロトコル結果は独立し、fence は先行配信だけを対象とする。 |
| 9. 先行 DATA/stderr、シェル成功、配信障害、停止 | 安全な出力と受信元の順序を保持し、合意した三条件を満たして使用可能とする。 |
| 10. 消費停止中の終了情報と未知の want-reply 要求 | 上限付き、順序付き、一度だけのプロトコル応答が進み、事実情報はペイロードとログの外で順序を保つ。 |
| 11. 微小または 0 バイトの DATA と拡張データの混在 | ペイロードバイト計上、受信元の順序、有限メタデータを保ち、偽のクレジットを返さない。 |
| 12. SFTP 長さ部と本体の分割、最大または不正長、チャンク内の複数フレーム | 割り当て前の検証、後続コールバックを待たない段階的消費、正確な所有量の計上。 |
| 13. ファイル要求 8 件、参照と制御、停止したローカル I/O | 既存の要求、バッファー、provider の上限と計上を維持し、許可された端末と制御が進む。 |
| 14. キュー内、コミット済み、完了、不確定の WINDOW_ADJUST | 返却資格と相手の許容量を分離し、早い相手応答にも安全に対応。二重通知や早期再利用なし。 |
| 15. 鍵再交換中のクレジット 0 または停止 consumer | ロックやリデューサーの循環待ち、不公平な転送停止なしに、他チャネルと許可された制御や鍵再交換が進む。 |
| 16. 防いだ OPEN、コミット後停止、遅延確認または拒否 | 未公開識別情報はローカル決着後に退役でき、遅延結果は元の試行だけを後処理する。 |
| 17. 来ない OPEN/CLOSE 応答と再開設の反復 | 現在の接続世代ごとに一枠、有限の待機者と記録、既存待機予算を保持。不意の開設や強制切断なし。 |
| 18. 明示的再開設待機の終了前後に旧閉鎖が退役 | 現在も有効な明示的要求だけが新チャネルを受け入れる。 |
| 19. 方向別 EOF、逆方向送信、EOF なしの終了情報、EOF なしの CLOSE | 必要な確定を一度だけ行い、許可された逆方向や後続の通信を保つ。正常終了を捏造しない。 |
| 20. 同時 CLOSE と保留書込、制御、コールバック | CLOSE 発行は最大一度。閉鎖、配信、解放、退役はそれぞれ区別する。 |
| 21. 受信出力と遅い記録がある端末 Disconnect | 既存の相手猶予、受信区切り、元世代の所有を保持し、2 秒以内の保存や解放を保証しない。 |
| 22. SFTP/file 障害と、不正 SSH/ID/ウィンドウ超過 | 適切な局所または接続全体の障害とし、未知の種別を破損と混同しない。 |
| 23. consumer の部分適用後障害と最後のコールバック拒否 | 独立した障害報告、安全な効果の保持、再実行や偽のクレジットなし、実後処理の観測。 |
| 24. 閉鎖後の parser/provider バッファー、保留変更、再開設 | チャネル解放後も上位所有者の計上と結果、既存の変更と更新確認の制約が残る。 |
| 25. 再接続後の旧 I/O、consumer、閉鎖の完了 | 旧所有だけを決着させ、新しい対応付け、クレジット、状態、使用可能判定、枠に影響しない。 |
| 26. 全メタデータ、制御、結果、観測者の上限と停止や Close の反復 | 有限の所有を維持。タスクや履歴の増加、未決着識別情報の追い出し、架空の解放なし。 |
| 27. 独立したクレジットベクトルと OpenSSH での微小通信、stderr、枯渇 | ローカル encoder から独立して EID 3878 に関する相互運用上の選択、バイト数、最大ペイロードを検証する。 |

## Telnet

新規プロファイルの初期選択は SSH とする。既存プロファイルを開く、編集する、または複製する際は、保存されている接続方式を使う。Telnet の設定ではパスワード、コマンド、端末出力が平文で送受信されることを説明する。プロファイルを直接開いた場合も含め、接続中はタブのステータスに暗号化なしと表示する。

BINARY、ECHO、SGA、TERMINAL-TYPE、NAWS に RFC 1143 の Q method をオプションと方向ごとに独立して実装する。初期状態で TTYPE/NAWS を提示し、接続先の ECHO を要求し、SGA を提示かつ要求する。BINARY の開始は既定オフの保存済みスイッチに従う。接続先からの BINARY 要求は受け入れ可能とする。ローカル ECHO と未知のオプションは交渉ループなしで拒否する。実効エコーは交渉済みの接続先方向のみから追跡する。ログイン検出、保存パスワード、vault は使わない。

IAC IAC はデータ 1 バイトに復号する。非バイナリ RX では CR NUL は CR、CR LF は CRLF とし、その他のデータの前にある CR は CR を出力してそのデータを再処理する。交渉バイトは端末ペイロードに含めない。保留中の CR は EOF またはその方向のバイナリ解釈を変更する前にフラッシュする。それ以外の 8 ビットデータは保持する。非バイナリ TX では直後に LF がない CR を CR NUL にし、CRLF を維持してから IAC を二重化する。バイナリ TX でも IAC は二重化する。ストリームの CR 状態を送信単位の境界と調整し、無関係なユーザー入力を無期限に待たないようにする。

受理した TTYPE SEND には取得済みの端末種別を返す。NAWS は現在の列数と行数を 16 ビットで送信し、副交渉内でも IAC をエスケープする。完結した上限内の未知の副交渉はテキストに漏らさず消費する。NOP/GA/AYT/BRK/IP/AO/EC/EL/DM はプロトコルコマンドとして認識し、受信テキストや暗黙のローカル編集にはしない。初期 UI が送るのは合意済みの AYT と BREAK のみ。不正な IAC/SB フレーミングや 64 KiB を超える副交渉は該当接続の失敗とする。TCP の断片化でオプション、副交渉、保留中の CR の状態はリセットしない。

## シリアル

合意済みの他のハンドシェイクと DSR/DTR を利用できる Microsoft Win32 通信 API を使う。選択した COM 名をオーバーラップ I/O で排他的に開き、DCB とタイムアウトを設定および検証し、Connected にする。ドライバーの失敗や未対応の設定は値を代用せず拒否する。ボーレートはドライバーが受け付ける範囲の正の uint32。データ、パリティ、ストップビットの選択肢は固定する。

RTS/CTS では CTS の出力ゲートと RTS ハンドシェイクを使う。DSR/DTR では DSR の出力ゲートと DTR ハンドシェイクを使う。XON/XOFF は DC1/DC3 によるソフトウェアの入出力フロー制御を使う。ハンドシェイクの管理外では保存した DTR/RTS を適用する。既定は On。端末バイトを黙って編集する追加の DSR 感度、NUL やパリティの置換は有効にしない。一時的な手動の制御線操作や 1000 ms の BREAK はプロファイルを書き換えない。キャンセルや閉鎖時にハンドルがまだ使える場合は BREAK を解除する。切断や取り外しは I/O 所有権を無効にする。USB の識別情報に自動で再バインドしたり、保留中の入力を再送したりしない。

CE_OVERRUN/CE_RXOVER はデータ損失またはリソースエラーとして報告し、該当セッションを切断する。利用可能な出力を保持し、記録が不完全と表示する。フレーミングとパリティのエラーは明示的に報告する。ドライバーが渡していないバイトは Raw に含まれない。ログ保存が遅くても読み取りは独立して続ける。キャンセル要求を発行しても、実際に完了するまでバッファーを解放しない。

## 根拠と今後の検証

SSH の規範的なフィールド符号化と許可されるメッセージは RFC 4251/4252/4253/4254、4256、5656、8308、8332、8731、9142、10042、OpenSSH の EtM/GCM プロトコル記述、固定した strict KEX ドラフトに従う。選択した正確な名称は、既定どおり実装開始時とリリース前にセキュリティの観点で再確認する。上記の合意済み上限は TabTty の選択であり、RFC 全般の最大値ではない。

今後の検証対象は、独立した暗号プリミティブと通信上のベクトル、許可した全アルゴリズムの組、現行 OpenSSH とサポート対象の strict KEX 非対応ピア、不正パケット、最大サイズの EXT_INFO、初回交換と同時の鍵再交換、ホスト鍵の置き換え、MFA のラウンド、stderr の混在と EOF、残りウィンドウが小さい場合の動作、Telnet のオプションループと CR/IAC の断片化、シリアルの使用中、取り外し、ハンドシェイク、オーバーラン。独立した SSH とセキュリティのレビューはリリース条件。この文書の段階では、これらのテストとレビューは未実施。

保存済み参照を設定した状態でも SSH ユーザー名を編集でき、項目の選択や変更で値が変わらないことを確認する。同じ vault のパスワードを参照し、異なるユーザー名を設定した二つのプロファイルで接続し、それぞれのユーザー名が認証要求に使われることを検証する。接続時の鍵選択画面にすべての秘密鍵が並び、読み込んだ版のプロファイルの SSH ユーザー名が表示されることも確認する。

保存済みの項目を使う場合と接続時に鍵を選ぶ場合の両方で、不在と 0 バイトの対象を検証する。参照先の vault に指定の鍵が見つからない場合も検証する。理由を表示し、使える次の方式があれば同じユーザー名で続行し、なければエラーで終了することを確認する。同じ不在の vault の保存済みパスワードは利用できないこと、種類の不一致では別方式があっても終了することを確認する。有効な vault に候補がない場合について、サーバーが別の方式を提示する場合としない場合を検証する。［別の認証方式を試す］では同じ接続試行で次の方式へ進み、［接続をキャンセル］では試行が終了することを確認する。SSH 接続からファイルを作成・初期化しないことも確認する。

新規プロファイルはパスワードの一行で始まり、公開鍵の行を追加できることを確認する。両方が提示された場合の優先順、最初の段階でキーボード対話認証だけが使える場合、部分成功の後で使う場合、無効設定で候補から外れる場合を検証する。
