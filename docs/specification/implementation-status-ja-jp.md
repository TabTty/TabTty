- UTF-8 経路では Rust の共通規則で操作を事前検証し、実行する。ループバック接続で端末応答、Raw・Text・Terminal の記録、IME 確定、切断後の WPF 表示を検証した。コアテストでは貼り付けのキャンセルと応答順、送信途中の障害を確認した。
- タブ単体・ウィンドウ・一括・自動削除に同じタブ閉鎖処理を使う。WPF で旧接続への承認、ウィンドウ閉鎖からの合流、後処理の待機継続、SFTP ウィンドウを閉じられない場合、Rust 状態の解放後に保持結果が読めることを検証した。
- 対応する47種類の文字変換には Win32 の厳密変換または Windows 同梱 ICU を用いる。JIS の切替と文字集合は ICU が決める。旧 IN/OUT の値はファイルの互換性のために読み込める。[文字コードの決定記録](../drafts/terminal-codec-consultation.md)
- レガシー受信では、文字単位の組み立て、途中のバイト列、カナ切替、記録区間の判定を Rust 側に移した。DATA と stderr で状態を分ける。Rust モデルを直接使う JIS テストでは、事前検証の拒否後も ICU の受信状態、表示内容、出力が変わらないことを検証した。通常のレガシーセッションは VT 解釈を C# で行う。
- UTF-8 の Rust 経路で、カーソル・スクロール・タブ位置、キーとマウス、代替画面、リサイズ、記録区間を処理する。記録中のリサイズでは表示用と受信専用 Text 記録用の準備が両方成功してから反映する。コアテストでは記録区間をまたぐ文字、折り返しの再計算後の記録、2 つ目のリサイズ準備の拒否、カーソル行がすでに存在する場合に高さだけを変えても保持行の識別子が変わらないことを検証した。
- ログ書き込み側で障害が起きた場合は、その記録区間を終了して端末の受信を継続する。書き込みに失敗した一時停止はエラーを返す。障害を注入するテストで前後の実ファイルを照合し、古い書き込み側の通知が再開後の記録を停止しないことを確認した。
- AI の画面読み取りでは Rust の表示中の画面から指定範囲を取得する。WPF のループバック Telnet テストで、範囲の境界にかかった全角文字、書式マーク、前景色を検証した。AI からの保持履歴の読み取りと検索は C# 側を使う。
- レガシーの VT 実行、保持履歴と検索、C# への切替の撤去、Rust のみで動く構成の配布・負荷検証が #16 に残る。

## Rust 端末コアの正式採用と応答性（2026-11-15）

対応する UTF-8 の受信解析、通常画面の編集、履歴保持、Text・Terminal の一括生成を Rust に移し、製品の既定経路に採用した。通信、セッションと入力の調整、ログファイル、WPF は C# を継続する。Rust コアに外部 crate の依存はない。[ADR 0006](../adr/0006-native-terminal-core-with-lossless-managed-handoff.md) に決定を記録した。

未対応の操作では、そのバッチを処理する前に完全な端末状態を既存の C# エンジンへ一度だけ引き継ぐ。出力、記録済みの版、行の識別情報、スタイル、カーソル、モード、未完のデコード・解析状態を保持する。UTF-8 以外は最初から C# を使い、受信後のサイズ変更・再フロー、代替画面、AI 観測、マクロのフック、一部の制御列は引き継ぎを起こす。一般的なシェルの OSC とブラケットペーストの切替は Rust のまま処理する。引き継ぎ後のモデルは C# を継続するため、高速化の効果は Rust 経路を維持する条件に依存する。性能試験では全バイトの native 処理と引き継ぎ 0 回を確認した。

遅延には、アプリ側のスナップショット全体の展開・WPF 描画の割り当てと、旧試験プログラム側の UI スレッドでの Raw ファイル確認が影響していた。後者だけで約 50～100 ms の停止が発生したため、下記の過去の試作時の操作遅延はアプリ自体の比較根拠から外し、同じ修正済み計測器で固定した旧版を再測定した。別の計測器を使った #15 の正式試験は影響を受けない。

アプリでは、不変の圧縮スナップショットを保持し、必要な行だけを展開するよう変更した。展開分の割り当て枠は描画前に確保する。タブ選択時に新しい描画を早め、描画用変換を上限付きで再利用する。Rust 側も検証済みバッチの完全一致による再利用を導入し、変更前の資源制限を維持した。保持行数、3 種類のログ、停止・タブ切替・スクロール時の強調仕様は維持した。3 フォントサイズ・2 DPI を含む 24 描画比較では、変更前の繰り返し描画と一致した。

SSH の相互運用には ssh2 1.17.0 のループバックフィクスチャを使った。Node の crypto API で独立実装した ML-KEM/X25519 ハイブリッドピアも含む。各実行を通じて、設定済みの全鍵交換グループ、両方の GCM 暗号、CTR/EtM の組み合わせ、すべてのホスト署名名、3 種類すべてのユーザー認証、鍵再交換、DATA と stderr の分離、UTF-8 以外のデータを検証した。最終ネイティブビルドは、PTY の寸法、シェル成功応答前に到着するチャネルペイロード、暗号化した OpenSSH/PKCS#8 鍵のインポートも検査した。フィクスチャは ssh2 の server-sig-algs に欠けていたカンマと、RSA の PK_OK のアルゴリズム名を修正する。これらのケースでは上流の未変更サーバーとの等価性は確認していない。

既定のピアテストを繰り返すには、`tests/fixtures/ssh-peer.cjs` と `tests/fixtures/prepare-ssh-peer.cjs` を `artifacts` 配下の新しいディレクトリへコピーする。そのディレクトリで、テスト専用の依存関係を `npm install --ignore-scripts --save-exact ssh2@1.17.0` でインストールし、Node 24 で `node prepare-ssh-peer.cjs` を実行する。`fixture_host` という使い捨ての Ed25519 OpenSSH ホスト鍵を作り、`node ssh-peer.cjs port.txt` を起動する。出力されたポートを `TABTTY_INTEROP_SSH_PORT` に設定し、リポジトリでコアスイートを実行する。PTY サイズとシェル開始前の取り込みを検査するには `TABTTY_INTEROP_EARLY_DATA=1` を設定する。bcrypt インポートの検査では、フィクスチャ用パスフレーズ `import-test-passphrase` で暗号化した使い捨て OpenSSH 秘密鍵を `TABTTY_OPENSSH_FIXTURE` に設定する。任意のテスト依存関係と鍵は Windows パッケージに含まない。

## 性能と残りの受け入れ項目

診断では、記録 3 形式すべてを有効にしたヘッドレスの合成セッション 20 個、120×40 のグリッド、5000 保持行、合計約 1 MiB/s を使った。最終のバッチ化の測定では、20 秒のウォームアップ後、負荷分布ごとに 30 秒間測った。入力受付の p95 は、均等負荷で 13.1 ms、一つの高負荷な生成元がある場合に 14.6 ms。送信完了の p95 はそれぞれ 64.2 ms、14.7 ms。各実行で 20 個すべての Raw ファイルが、独立に生成した受信バイト列のダイジェストに一致した。両方の実行でピークワーキングセットの実測値は約 2.42 GB。サイクルとレポートのファイルは `artifacts/core-stress-20261111-batched` にある。この短時間のヘッドレス測定は、[リソースと検証](resources-and-validation-ja-jp.md)の 30 分の SSH/WPF 受け入れ負荷試験とは別に実施した。

初期パッケージには、クリーンな PC での検証、物理 COM 転送とモデム制御線のテスト、対話的な IME とナレーター、タブのドラッグとファイルの関連付けの操作、ストレージの障害注入、規定の性能負荷試験一式、SSH、vault、ネイティブコードの独立レビューが残る。Store の認証と公開は今後の作業。

組み込みの Unicode17.bin は、Unicode 17.0.0 の UCD ファイル EastAsianWidth、GraphemeBreakProperty、DerivedCoreProperties（InCB）、DerivedGeneralCategory（結合記号）、emoji-data から生成した、ソート済みのプロパティ範囲を含む。SHA-256 は `e733cbce929cc14bea4191ef0c0982bb1296548fbbcbad88fc9417894ea3e0f6`。補助的な ISO-8859 テーブルは Unicode マッピングファイルを、CP932 の位置情報は Microsoft 公開のテーブルを使用する。
