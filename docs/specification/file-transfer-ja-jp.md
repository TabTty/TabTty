<a name="transfer-window-and-operation-ownership"></a>

## 転送ウィンドウと操作の所有権

両ペインの一覧には、接続プロファイル管理画面と vault 管理画面と同じ行の高さを使う。ドラッグ中は、転送先になるフォルダー行だけを強調する。

タブ見出しのコマンドは、クリックした接続済み SSH 端末タブを対象とする。別グループの非アクティブタブも含む。タブごとに転送ウィンドウを一つだけ開くか、既存のウィンドウにフォーカスを当てる。現在の接続世代に結び付け、認証済みのユーザー、ホスト、ポートを表示する。シェルのディレクトリ変更、`sudo`、入れ子の SSH、プロファイル編集で対象は変わらない。タブの分離で変わるのは表示上の所属だけである。切断後も端末タブを保持する場合は、転送ウィンドウで結果を確認できる。再接続後にユーザーが明示的に転送を開くと、切断済みのビューを新しい世代に置き換える。残っていた作業や以前の選択は再現しない。

アーキテクチャ Q10 に従い、「切断済みをすべて閉じる」と切断済みタブの自動削除では、個別タブ／ウィンドウを明示的に閉じる場合と同様に、対象タブに関連する転送ウィンドウも閉じる。[ウィンドウの仕様](persistence-and-windows-ja-jp.md)に従い、接続試行の失敗・タイムアウトや、接続成立後の通信エラーで黄色地の「!」が付いたタブは、理由を確認できるよう自動では閉じず、一括閉鎖の対象に含める。接続終了の警告は不要で、必要な後処理、報告、待機・損失の選択と、アプリの最終終了は既存方針に従う。これらの未実装の変更と、維持する実後処理の所有権は[閉鎖設計](tab-and-window-closure-ja-jp.md)に記録する。

ローカルペインは Windows の既知の「ドキュメント」フォルダーで開き、接続先の既定ディレクトリは `.` に対する SFTP REALPATH で取得する。通常の初回表示では左右のディレクトリを各1回列挙し、その結果を表示する。片側に失敗した場合は、成功側の一覧と選択を保ち、失敗側にはエラーを表示してパス入力欄で訂正できるようにする。現在のディレクトリ、一覧のリビジョン、選択はペインごとに保持する。移動や更新が行われた場合は、古い一覧取得結果を破棄する。両側のフォルダー操作はキーボードで行える。操作、ダイアログ、結果にはすべてアプリの言語とテーマを適用する。

パス欄の編集は移動先の下書きとして扱う。Enter で移動先の一覧を取得し、Escape で直前に一覧を表示したパスに戻す。一覧の取得中や、入力中のパスと表示済みの一覧が一致しない間は、そのペインの一覧・ファイル管理操作と、そのペインを使う転送を無効にする。移動に失敗した場合は入力値を残して修正できるようにする。バックグラウンドで一覧を更新しても編集途中のパスを保持する。実行中のバッチは開始時に確定したパスで継続する。

ボタン、キーボードショートカット、ドラッグ＆ドロップには、同じ操作について同じ実行条件を適用する。結果不明の変更後に一覧の更新を待つ間など、コピーできない状態ではコピー用カーソルも転送先の強調表示も出さない。ボタンを押した時点で、転送元の選択項目と反対側のペインの表示ディレクトリを確定する。ペインをまたぐドロップでは強調されたディレクトリを使う。ファイル行または空白へのドロップでは表示中のディレクトリを使う。ドロップ時にコピーの可否を再確認し、転送先がそのドラッグで最後にプレビューした転送先と一致する場合に限り確定する。どちらも同じコピー操作を呼び出す。転送元の選択、またはどちらかの一覧の世代が古いドラッグは破棄する。確定後の移動や更新はバッチに影響しない。転送バッチの実行中、そのウィンドウでは別のバッチやファイル管理の変更操作を開始できない。作成、名前変更、削除は同じウィンドウ内で直列化し、その処理中は新しいバッチを受け付けない。閲覧や転送から端末入力や同時送信操作を発生させない。

親ウィンドウを閉じる確認には、影響を受ける実行中の操作を重複なく表示する。転送ウィンドウ自体を閉じる際も、作業中ならキャンセルを確認する。明示的な切断や接続先の喪失で接続世代は無効になり、端末タブを保持する場合は結果も保持する。自動削除を含むタブ削除では、Q10 に従い、その転送ウィンドウを閉じる。端末タブやウィンドウの閉鎖が承認されたら、関連作業をキャンセルし、その転送ウィンドウを閉じる。アプリの最終終了は既存の端末ウィンドウ終了ルールに従う。必要な閉鎖の判断を得てから、閉鎖による作業のキャンセルを行う。ウィンドウを閉じるときは既存の上限付き終了方針を使い、パスや結果が得られる場合は、判明している未完了の後処理を閉じる前に報告する。

<a name="ssh-and-sftp-channel"></a>

## SSH と SFTP のチャネル

端末の準備ができたら、クライアントから SSH の `session` チャネルを要求し、応答ありで `sftp` サブシステムを要求する。PTY は要求しない。サブシステムの開始に成功したら SFTP INIT を送る。バージョン 3 を提示し、応答にもバージョン 3 を求める。チャネル、サブシステム、バージョンが拒否されたら転送ウィンドウに表示する。別の端末タブを開く場合は別の SSH 接続になる。SFTP では再ログイン、ホスト鍵の再確認、vault の再操作は発生しない。タブの現在の SSH 接続世代につき、開始中・稼働中・閉鎖中を通して SFTP の枠を一つに制限する。チャネルに障害が起きても SSH 接続が維持され、旧枠を安全に終了できれば、後述のとおり明示的に開き直せる。

トランスポートのパケット読み取りは一つにし、書き込みは直列化する。メッセージは SSH チャネル識別子で振り分け、クレジット、バッファー、要求、EOF/CLOSE 状態はチャネルごとに独立させる。SSH の応答はチャネルごとに順番で、SFTP の応答は未完了の要求 ID で対応付け、許容される応答順序の入れ替わりに対応する。閉鎖完了までチャネルの識別情報を保持し、識別子の再利用で遅延データや応答が別の処理に結び付かないようにする。キャンセル後の遅延応答が完了または解放できるのは元の作業だけである。SFTP のデータと標準エラーは端末デコード、強調表示、すべてのセッション記録から除外する。ファイル転送の結果は上限を設けてローカライズして表示する。サーバーからの文字列は単なるテキストとして扱う。

ソケット、暗号化、鍵再交換、死活監視は認証済みトランスポートで共用する。不正な SFTP フレーム、未対応の応答、ファイル I/O 障害、SFTP のみの閉鎖は、影響を受けた転送作業を止める。正常な端末は維持する。トランスポートのフレーミングや接続に障害があれば両方を終了する。SFTP 作業のキャンセルは要求やチャネルの境界で行う。共用 SSH パケットの直列化を途中で中断しない。共通の受信ループ内でファイルシステム、UI、転送クレジットを待たない。対話入力と SSH 制御をバルク転送より優先し、転送にも上限のある公平な処理機会を与える。

### SFTP チャネルの寿命と所有権

Q17〜Q19 で合意した[共通 SSH チャネルモジュール](transports-and-authentication-ja-jp.md#ssh-チャネルの共通所有)を使う。名前付きの完了操作が、チャネル開始、要求応答、通知・データの送出、フロー制御、閉鎖と実際の後処理を所有する。SFTP はサブシステム・INIT・バージョンの順序、フレーム、要求 ID の対応、ファイル操作の意味、診断を維持する。開始前に逐次処理する SFTP consumer と上限付きの受信要求拒否方針を結び付ける。通常の要求・データは開始確認後に受け付け、開始中でも Close は使える。consumer はサブシステム成功、INIT・バージョン確定、後続 callback を待たない。

本体を割り当てる前に各フレームの長さを検証し、最大 256 KiB を維持する。上限内のパーサー・フレーム記憶域へ実際に移した先頭部分だけを消費し、残りのフレーム、接続先の応答、ローカル I/O を待たない。SFTP 要求の受付時に必要な応答・パーサー容量を予約する。コピー中の元チャンク、未完成・完成フレーム、保留中の応答、ローカル I/O へ移したバッファーを、実際の所有期間まで計上する。SSH credit の返却ではその記憶域を解放しない。稼働中・閉鎖中チャネルあたり 2 MiB、アプリ全体 32 MiB のバッファー上限と、要求・プロバイダー・結果の独立した上限を維持する。別の上限へフレームの待ち行列を隠したり、容量を空ける唯一の callback を容量待ちで止めたりしない。

完全なフレームを順に送り、フレーム終端を許可された停止位置として渡す。共有 writer が暗号状態・連番の不可逆な変更を確定したパケットは、個別の停止で中断しない。未完成のフレームが残る場合は、受付済みの作業を安全に完了するか、既存の取消・障害方針でそのチャネルの後続 DATA をすべて止めて閉じる。放棄した先頭部分に新しいフレームを連結しない。Close は現在の確定済みパケットの決着後に進められ、credit がゼロの Send がフレーム全体を送り終えるのを待たない。取消後も必ずフレームを完了する、または同じチャネルを維持する保証は追加しない。

ファイルへの作用は、確実に送出したバイトと不確かな送信範囲から判断する。最終パケットが不確かな場合、フレーム全体の書き込みが成功を返さなくても、完全な変更要求が届いた可能性がある。必要な UnknownOutcome と既存の再読込み・復旧規則を維持し、自動再送や未実行の推定は行わない。共通チャネルモジュールはファイル操作の結果を決めない。

タブの現在の SSH 接続世代につき、開始中・稼働中・閉鎖中を通して一つの SFTP 枠を使う。開始中・稼働中の枠があれば別の開始を拒否する。明示的な開き直しは、既存の接続待ち時間内で閉鎖中の枠を待てる。待機者数に上限を設けるか、容量不足・Busy を返し、要求の繰り返しで期限を延ばさない。期限切れ・停止した要求が後から自動で開くことはない。旧枠を空けるにはプロトコル上の識別情報の終了とチャネル所有資源の実解放の両方が必要で、CLOSE の予約・送信、ペイロード解放、タイムアウトだけでは足りない。OPEN の確定後に取り消しても元の識別情報を保持する。遅延した開始確認は旧試行の後処理・CLOSE だけを進め、サブシステムを開始しない。遅延した拒否も旧試行だけを解決する。

OPEN・CLOSE が解決しなければ、その接続では開き直せない状態が続く場合がある。正常な端末を維持し、保留・Busy・期限切れを正確に報告する。閉鎖中の枠の増設、端末の強制切断、未解決 ID の再利用、自動再接続・再送で回避しない。明示的な再接続で作られた新しい世代は、共有容量と既存のファイル操作の制約に従って独立した枠を持つ。旧作業は元の所有者に計上し続け、遅延完了は新しい枠、credit、結果を変更しない。

チャネル所有資源の解放は、別途移譲したパーサー記憶域・ローカル I/O の解放や不明なファイル結果の消去を意味しない。取消後も I/O が残る間は、[ファイル操作の取消](file-operations-ja-jp.md#確認とキャンセル)に従って新しい変更操作を拒否する。チャネルの開き直しや UI の再読込みでこの制約を回避しない。既存のウィンドウ・タブ閉鎖確認と所有権は維持する。Q19 は別途依頼される実装へ進める設計の確定であり、[27 ケースの検証計画](../drafts/whole-codebase-architecture-deepening.md#candidate-5-verification-plan)は将来の必須作業で、実行済みの根拠ではない。

## パス、名前、ツリー

転送ウィンドウ作成時に端末の実効送信エンコーディングを取得する。入力した接続先パスと生成した転送先の名前をそのエンコーディングで符号化し、一覧の名前も同じもので復号する。コーデックのマッピングは各パス構成要素に個別に適用する。JIS のような状態を持つエンコーディングでは、構成要素ごとに状態を初期化し、出力を終端する。SFTP の構成要素間の区切り文字は ASCII `/` のみとする。名前には VT 制御処理、ストリーム先頭 BOM の除去、端末のカナシフト、置換文字を適用しない。一覧で取得した項目に対する要求には、元のバイト列を保持して使う。デコードできない名前はエスケープしたバイト列で表示できる。そのような接続先の項目では「名前変更」を無効にし、F2 を押しても改名を開始しない。他の操作でも、その名前をファイル名として解釈する必要があれば拒否する。名前の元のバイト列を使う操作は、ほかの実行条件を満たせば利用できる。選んだエンコーディングで往復変換できない生成名も拒否する。ファイルデータと改行はバイト単位でそのままコピーする。

一覧の子項目と新しく符号化した構成要素は、選択した親と連結する前に検証する。通信上の名前に空文字列、NUL、`/`、パストラバーサルの構成要素を許可しない。構成要素内に区切りバイトを生成するコーデックでは、その名前を SFTP で表せない。通常の `.` と `..` の一覧行は飛ばす。ユーザーによるパス入力での移動は別操作で、親へのパスも使える。Windows では不正名や予約名、子項目名のデバイス構文と代替データストリーム構文、区切り文字、末尾のピリオドや空白、選択した転送先の外に出るパスを拒否する。ローカルの転送先では、可能な限りファイルシステムの識別情報と比較規則を使う。ディレクトリごとの大文字小文字の区別も含む。ファイル作業中は実際に選択したディレクトリの同一性を維持する。

書き込み前に、上限を設けて転送元と転送先の名前の集合を計画する。大文字と小文字を区別しない転送先で等価になる名前など、同一バッチ内で判明した別名はまとめて失敗とする。接続先の大文字小文字や正規化の挙動が不明なら、互いに異なると確認できない衝突候補の兄弟項目を拒否する。サーバーの作成や名前変更の結果を確認し、同じバッチの別項目が作ったファイルの置き換えは承認しない。検証エラーは対象の項目またはサブツリーの失敗とする。同一項目への複数の参照は重複排除する。

通常ファイルとディレクトリをコピーする。空のディレクトリも対象とする。リンク、ジャンクション、未対応の種類、転送先の安全性を確認できない子パスはスキップする。同名ディレクトリを統合し、無関係な項目はそのままにする。再帰削除では対象ツリーを列挙し、子を先に削除して空の親を最後に削除する。リンクと判明している項目はリンクをたどらずに削除する。子に進む前や変更の前に種類を再確認し、種類が判定できない項目は残す。Windows ではリンクをたどらない方法で開き、アプリ主導の再帰処理では解決後のディレクトリの同一性を検査する。SFTP v3 はパスベースで、複数の要求にわたり接続先のパス構成要素をロックできない。変化を観測したら該当サブツリーを停止する。サーバーは検査の間にもファイルシステムのパスを変えられるため、この検査でスナップショットは得られない。

## ファイルの書き込みと置き換え

フォルダーのコピーおよび「フォルダー作成」で作成するフォルダーは、所有者だけがアクセスできる権限で作成する。Windows では作成前にボリュームがアクセス権を保持できることを確かめ、現在のユーザーだけにフルコントロールを許可する保護済み DACL を作成時に設定する。この権限は子ファイルと子フォルダーにも継承する。子項目のコピー前に、所有者と DACL を検証する。接続先では SFTP MKDIR に POSIX モード 0700 を指定し、サーバーが拒否したらそのフォルダー以下の作成を中止する。同名の既存フォルダーに統合する場合は既存の権限を保つ。接続先での実効権限はサーバーが管理する。[Windows のディレクトリ作成](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw)

一覧と上書き・削除の確認画面では、ローカル・リモートの名前に同じ表示規則を適用する。制御文字、Unicode の書式制御文字、行区切り、通常の空白以外の空白文字、エスケープ表記の開始記号を可視化する。復号できない構成要素は区別可能なバイト列表記にする。操作には元のパスを使う。ウィンドウごとの一覧容量 32 MiB のうち、行データは各子の完全なパス、復号名、表示名を含めて 16 MiB までとする。

ダウンロードする通常ファイルは、SSH の認証を完了した接続先やフォルダー単位のコピーでも、すべて Windows のインターネットゾーン 3 とする。受信データを書き込む前に、一時ファイルにローカルで `Zone.Identifier` ストリームを作り、`[ZoneTransfer]` と `ZoneId=3` のみを記録する。確定前にストリームが元の一時ファイルに属することと内容を検証する。新規作成と承認済み上書きの両方で、確定後のファイルにこの情報を引き継ぐ。転送先で保存または検証できない場合は、その項目を確定前に失敗とし、既存ファイルを保持する。これは Windows のゾーン情報を利用するソフトウェアに由来を伝える仕組みで、ウイルス検査や実行判断は Windows と利用側のアプリケーションが行う。[Windows のゾーン情報ストリーム形式](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/6e3f7352-d11c-4d76-8c39-2516a9df36e8)

可能なら転送元を開くときに属性を読む。同じディレクトリに排他的に作成した一時ファイルへ、上限付きのバッファーでストリーム書き込みする。すべての書き込みと一時ファイルの閉鎖が成功してから最終名で確定する。確定前に期待される長さと比較可能な転送元の属性を再検査する。転送元が変化していれば、そのファイルは失敗とする。転送元の最終更新日時は、表現可能なら、できる限り一時ファイル上で設定して保持する。アップロード時に公開する日時は最終更新日時だけとする。SFTP v3 ではアクセス日時と更新日時を一組で指定するため、両方に転送元の最終更新日時を設定する。データを確定できた場合、日時設定の失敗はメタデータ警告とする。

ダウンロード用の一時ファイルの所有者を現在の Windows ユーザーとし、作成時にそのユーザーだけにフルコントロールを付与した継承無効の DACL を設定する。受信内容を書き込む前に、実ファイルの所有者と DACL、および保存先ボリュームがアクセス権を保持できることを確認する。保持できない場合はその項目を失敗とする。新規保存・承認済み上書きのどちらも、この保護を維持する。アップロードでは、一時ファイルを排他的に作成する SFTP OPEN に POSIX モード 0600（所有者の読み書きのみ）を指定する。サーバーが要求を拒否したら失敗とし、権限を省いた再試行や名前変更後の権限拡大は行わない。ACL や POSIX モードを持たない環境での対応付けを含め、実際のアクセス権は接続先が管理する。接続先が POSIX モードを報告しない場合もアップロードを利用できる。アップロード先の所有者は接続先の規則で決まる。[Windows のファイルアクセス権と継承](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)・[SFTP v3 の OPEN 属性](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.3)

新規ファイルは置き換えを禁止した移動で作る。通常ファイルと名前が衝突したら、両側の名前、バイト単位のサイズ、Windows のローカル時刻での最終更新日時を照会して表示する。値が得られないときは **取得できません** と表示し、不在を確認できた場合と照会に失敗した場合を区別する。スキップは転送先を保持してバッチを続行し、キャンセルはバッチを止める。承認済みの上書きの直前に、転送先の種類、比較可能なメタデータ、取得可能なら同一性を再検査する。変化があれば再度確認を求める。ファイルが消えていれば、置き換えを禁止して作成する。SFTP v3 の POSIX 名前変更は無条件に置き換えるため、メタデータを別途調べても検査と置き換えの間の競合は防げない。解決後の同じローカル転送先に対する TabTty 自身の最終変更は、別タブからの書き込みも含めて直列化する。外部の書き込みや接続先の別名によって検査の間にファイルシステムが変わる場合はある。

ローカルの上書きでは、同じファイルハンドルからボリュームシリアル番号、128 ビットのファイル ID、サイズ、最終更新日時を取得する。一時ファイルへの転送後と置き換え直前に、承認時の値と照合する。Windows が既存の転送先のファイル ID を取得できない場合は上書きせず、元のファイルを保持する。Windows の名前変更 API は転送先をパスで指定するため、最後の検査と名前変更の間に外部で行われた変更は防げない。[Windows のファイル識別情報](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)・[名前変更の引数](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)

承認済みのローカル上書きには同一ディレクトリ内の Windows のファイル置き換え操作を使う。接続先の上書きにはサーバーが通知した `posix-rename@openssh.com` バージョン `1` を使う。安全な置き換えができない側では、元の転送先を残して上書きを失敗とする。削除後の名前変更、元ファイルの切り詰め、ボリュームをまたぐ書き込みへのフォールバックは行わない。Q28 では置き換えを伴わない標準の名前変更を使う。ファイルシステム操作の失敗は実際の結果を報告し、完了の有無が不明なら両方のパスを検査する。

確定前のキャンセルや失敗では、開いたハンドルを閉じ、その操作の一時ファイルだけの削除を試みる。後処理の成否を確認できなければパスを記録する。確定要求を送ったあと応答を失った場合、結果は不明となる。確定要求の再送、確定済みとしての集計、後処理としての最終パスの削除は行わない。結果は確定済み、スキップ、失敗、未処理、不明を識別する。失敗項目は元の有効な接続世代で明示的に最初から再試行する。その時点のパス、転送元、衝突を改めて確認する。

コピーまたは再試行ごとに、計画のカウンターと結果の重複を防ぐための情報を保持し、成功、キャンセル、失敗のいずれでも、その処理の終了時に解放する。直近の上限付きの結果には未処理の項目と後処理が未確認の一時パスを含め、再試行可能な項目の計画だけを保持する。新しい操作の受け付けを拒否した場合は、直前の結果と再試行情報を維持する。走査の中断時も各項目を一度だけ報告し、3件のうち再試行可能な失敗が1件なら、その1件だけを再試行することを確認する。[#181](https://github.com/TabTty/TabTty/issues/181)

## ファイル管理、待ち時間、上限

削除の確認は選択ごとに一度行い、対象がローカルか接続先か、親パス、選択した名前、フォルダーの中身を含むことを示す。可能なら Windows のごみ箱を使う。ごみ箱に入れられないローカル項目の完全削除は別途確認する。接続先の確認では最初から完全削除であることを示す。子項目で失敗したら、該当する最上位ツリーを停止し、可能なら他の選択項目を処理する。キャンセルは新しい破壊的要求を止め、完了済みの変更を保持し、失敗と未処理の項目を報告する。

発行済みの変更要求の結果が確認できなければ不明と報告する。次の変更操作を受け付けるには、未完了の I/O がすべて終了した後で左右の一覧取得を開始し、両方とも最新の一覧として表示できることを必要とする。同じ接続で転送ウィンドウを開き直したときも、その間に新たな結果不明の操作がなく、初回取得がこの条件を満たせば復旧時の更新として数える。開始が早すぎた取得、取消、後続の取得で古くなった結果、失敗では制限を解除しない。実行直前にも条件を再確認する。[#202](https://github.com/TabTty/TabTty/issues/202)

SFTP の起動と、関連する接続先の応答やバイト転送の進捗がない期間には、プロファイルの接続待ち時間を使う。無関係な端末通信や別の SFTP 操作でタイマーを延長しない。確認を待つ時間とローカル処理だけを待つ時間は除外する。ローカル I/O にも同じ設定時間で独立した上限を適用し、遅延したプロバイダー作業は元の操作に計上し続ける。進捗がある転送に全体の時間上限は設けない。タイムアウトした要求を安全に終了できない SFTP チャネルは、残りの処理を排出するか閉じる。

| リソース | 初期の技術的制限 |
| --- | --- |
| 実行中の転送バッチ | タブごとに一つ、アプリ全体で最大四つ。新しいバッチを開始できなければ容量不足を画面に表示する。 |
| SFTP バッファー | 稼働中または閉鎖中の転送チャネルごとに最大 2 MiB、アプリ全体で 32 MiB。受信クレジットと所有するステージング済みおよび転送中のバッファーを計上し、共有分を二重計上しない。 |
| SSH 転送チャネルのペイロード | 受信ウィンドウは 1 MiB、SSH チャネルデータは最大 32 KiB。割り当て前に SFTP フレーム長を独立して検査し、フレーム本体の上限を 256 KiB とする。 |
| ファイル要求 | ファイルごとに最大 32 KiB の読み取りまたは書き込み要求を同時に八つまで許可し、対話的な閲覧と制御に別枠を設ける。サーバー応答は要求範囲に制限する。 |
| 一覧とツリー操作 | 一覧または操作ごとに最大 50,000 項目、深さは最大 128、符号化済みパスは最大 32 KiB。保持する一覧、計画、結果のメタデータは、ウィンドウごとに 32 MiB、アプリ全体で 128 MiB に計上する。上限超過は報告する。アプリが最初の完全削除を発行する前に再帰削除の事前検査を行う。 |
| ファイル I/O | SFTP 関連のローカルプロバイダー呼び出しはアプリ全体で同時に八つまで。キャンセル済みでも復帰までは含める。端末とログ用に予約した予算は転送作業で消費しない。 |

合意済みの操作、エラー時の挙動、端末の応答目標を保ったまま、測定後に上限を調整できる。

## 受け入れケース

- 別のタブを選択中に、非アクティブな SSH タブのコンテキストメニューを使う。接続先、ローカライズ、キーボード操作、分離、タブごとに一つのウィンドウ、再接続後の明示的な再オープンを確認する。端末を使える状態でサブシステム拒否と SSH チャネル上限を試す。
- 空フォルダー、同名ディレクトリの統合、長い名前と非 ASCII 名、ゼロバイトファイル、大きなファイルを含めて送受信する。ボタンとペイン間ドラッグでの転送先、転送中の閲覧、確定したパスの維持を確認する。送信と受信の端末コーデックが異なる場合、不正なファイル名バイト、曖昧な表示名、バイト列の一致も確認する。
- 通常の新規確定、承認済み置き換え、スキップとキャンセル、衝突時のメタデータ欠落、置き換え前の変化、読み取り専用や空き容量不足、リンクや種類の衝突、表現できない名前、転送先で同一視される名前を試す。名前変更拡張がない場合、確定応答の遅延、古い結果、後処理の失敗、転送元の変化、進捗なしのタイムアウト、再試行も試す。
- ローカルでのごみ箱への移動と確認後の完全削除、リンクを含む接続先の空でないフォルダーの削除、子項目の失敗、キャンセル、権限拒否、変更の応答の喪失を試す。影響を受けたパスと結果の区分を確認する。
- 独立した OpenSSH の v3 サーバーとスクリプト化された SSH ピアで、同時のシェル I/O、送受信、鍵再交換、転送の停滞、切断を試す。Raw ログを期待する端末バイト列と比較し、転送負荷の下で既存の対話応答目標を測る。独立した上限を検証し、遅延したキャンセルが再オープンしたチャネルや新しい接続世代に影響しないことを確認する。
