# 認証情報 vault バージョン 1 の契約

2026-11-10 時点の仕様。合意済みの OpenSSL の利用範囲で Q107～Q108、Q135、Q161 を確定する。この時点で暗号処理の実装と検証は未実施。独立したセキュリティレビューはリリース条件に含む。TabTty 独自の形式であり、標準化や認証は受けていない。

管理の完了操作には、2026-11-18 に確定したアーキテクチャ Q12～Q16 を統合する。設計は別途承認された実装を開始できる状態にあるが、以下に定める将来の検証は、この設計レビューでは実行していない。

## 鍵階層とマスター入力

v1 の KDF プロファイルは Argon2id v1.3、メモリ 65,536 KiB、3 パス、4 レーン、ソルト 16 バイト、出力 32 バイトに固定する。ファイルにはレーン数を記録する。実行スレッド数は記録しない。機器に応じた強度の低下やパラメーターの推測は行わない。マスター入力は合意済みの NFC の後に厳密な UTF-8 を適用する。作成と変更では 14～1024 Unicode スカラー値とし、トリム、大文字小文字の同一視、NFKC は行わない。不正な Unicode、制御文字、改行を拒否し、入力を二度求めて確認する。ロック解除も同じバージョン付き規則に従う。

2026-11-12 にユーザーの要望で最小長を 15 から 14 に変更した。これはポータブルファイルの暗号鍵導出に対する製品上の制限。[NIST SP 800-63B-4 の 15 文字ルール](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#password-verifiers)は中央の検証者が検証する単一要素認証に適用される。以前の TabTty ビルドは 14 文字のマスターパスワードを拒否する。既存の vault は元のパスワードで引き続き読み取れる。

KEK はランダム生成した 32 バイトのルート DEK を AES-256-GCM でラップする。起動中にロックが解除されている間だけルートを保持し、マスター入力と KEK の作業バッファーを破棄する。ペイロードを暗号化するたびに、ルートを IKM とし、新しい 32 バイトのランダムソルトと後述の info を使い、HKDF-SHA-256 で専用の 32 バイト鍵を導出する。その鍵で JSON ペイロード全体を一度だけ AES-256-GCM で暗号化し、導出鍵を消去する。以前の DEK をペイロードに直接使用する記述を更新し、ペイロード全体の保護とロック解除の有効期間を維持する。

GCM のノンスはすべて 12 バイト、タグは 16 バイト。独立した鍵、ソルト、ノンスは、戻り値を確認する OpenSSL の乱数生成呼び出しで作る。RNG、KDF、暗号化、認証に失敗したら保存せず失敗とする。キャンセルや保存失敗の後も、新しい暗号化試行には新しいソルトとノンスが必要。完成した暗号文のコピーでは新たな暗号化を行わない。

確率的な鍵の分離では、ポータブルなコピー間の衝突が一切ないことまでは証明できない。導出したペイロード鍵を別の暗号化で再利用せず、ローカルカウンターをグローバルなノンスの証明に使わず、ロールバック防止や前方秘匿性を保証しない。ルートは HKDF 専用とし、ペイロードの GCM には直接使わない。通常の保存は既存のルートラッパーを再利用する。明示的なマスターパスワード変更では、新しい Argon ソルト、KEK、ルート、ラッパー、ペイロードのソルト、ノンス、暗号文全体を作る。古いコピーは古いパスワードで引き続き復号できる。

## 厳密なフレーミング

ファイルは固定 184 バイトのヘッダー、N バイトの暗号文、16 バイトのペイロードタグの順。整数はすべて符号なしビッグエンディアン。UUID は RFC のネットワークバイト順を使う。.NET の Guid の既定の混合エンディアン配列は使わない。v1 ではパディング、任意ヘッダーフィールド、末尾バイト、圧縮を許可しない。

| オフセット | バイト数 | フィールドと v1 の値 |
| ---: | ---: | --- |
| 0 | 8 | ASCII `TTTYKEY` に続いてゼロ 1 バイト |
| 8 | 2 | コンテナバージョン、1 |
| 10 | 2 | フラグ、0 |
| 12 | 4 | ヘッダー長、184 |
| 16 | 16 | ゼロ以外のランダムな vault UUID。通常保存やパスワード変更をまたいで固定 |
| 32 | 2 | KDF プロファイル。1 は上記の Argon2id プロファイル |
| 34 | 2 | ラッピング方式。1 は AES-256-GCM |
| 36 | 2 | ペイロード方式。1 は HKDF-SHA-256 の後に AES-256-GCM |
| 38 | 2 | マスター入力規則。1 は合意済みの NFC/UTF-8 規則 |
| 40 | 4 | Argon メモリ、65536 |
| 44 | 4 | Argon パス数、3 |
| 48 | 4 | Argon レーン数、4 |
| 52 | 16 | Argon ソルト |
| 68 | 12 | ルートラッピングのノンス |
| 80 | 32 | 暗号化したルート DEK |
| 112 | 16 | ルートラッピングのタグ |
| 128 | 32 | 新しいペイロード HKDF ソルト |
| 160 | 12 | ペイロードのノンス |
| 172 | 8 | N、ペイロード暗号文の長さ |
| 180 | 4 | 予約、0 |

`H[a:b]` はファイルヘッダーの位置 a を含み b を含まない厳密なバイト列を表す。以下のラベルは暗黙の NUL を持たない ASCII。明記したゼロバイトは形式に含まれる。

- ラッピング AAD は ASCII `TabTty/vault/v1/wrap`、ゼロ 1 バイト、H[0:80] の順。
- ペイロード AAD は ASCII `TabTty/vault/v1/payload`、ゼロ 1 バイト、H[0:184] の順。
- HKDF info は ASCII `TabTty/vault/v1/payload-key`、ゼロ 1 バイト、H[8:10]、H[34:38]、H[16:32] の順。

ラッピングが認証するのは通常保存で変化しないメタデータのみ。ペイロードの認証はラッパー全体とリビジョンのフレーミングを結び付ける。HKDF info はルートに依存するラッパーのハッシュや暗号文を含まない。AAD と info の再構成に JSON の直列化は使わない。メモリ割り当てや KDF より先に、固定値、ファイルの正確な長さ、ゼロ以外の ID、N の上限を検証する。未認証のメタデータを復号成功の証拠にしない。

ルートのラップを解除し、タグを検証してからルートを使う。導出した鍵でペイロードを所有下の一時メモリに復号し、解析前にタグを検証する。内部の vault 識別情報はヘッダーと照合する。ラッパータグが正しくても、破損したペイロードは使えない。認証失敗だけでは誤ったパスワードと入力の改変や破損を確実に区別できない。

## 暗号化ペイロードのスキーマと上限

BOM なし UTF-8 JSON のオブジェクト一つ。重複したプロパティやコメントは許可しない。`schemaVersion: 1`、`vaultId`（正規 UUID 文字列）、`entries`（配列）を持つ。非公開の v1 スキーマに未知のプロパティは許可しない。将来のフィールドには対応する新しいスキーマまたはコンテナルールが必要。配列の順序はユーザーの項目順とする。

各項目は `kind`（`password` または `privateKey`）、`name`と、該当する秘密フィールド一つだけを持つ。`passwordUtf8` は正規化していない厳密な UTF-8 の正規パディング付き Base64。`privateKeyPkcs8` は検証済みの非暗号化 PKCS#8 DER の正規パディング付き Base64。鍵の項目には公開鍵の種類と SHA-256 フィンガープリントも保存し、読み込み時に再計算して検査する。インポート元の鍵のパス、パスフレーズ、記憶したエンコーディング、不透明な外部ファイル依存は保存しない。vault 自体の ID は項目と独立して生成し、コンテナーの認証と復元に使う。

初期の防御的制限は、N が 16 MiB 以下、ファイル全体が 16 MiB + 200 バイト以下、最大 1,024 項目、JSON の深さ 8 以下、名前は Unicode スカラー値で 256 以下、パスワード素材は 16 KiB 以下、正規の秘密鍵 DER は 64 KiB 以下。これらは実測済みの容量ではない。Base64 の割り当て前に符号化後と復号後の長さの制限を適用し、その後内容を検証する。名前は種類をまたいで vault 内で一意とする。大文字・小文字を区別し、前後の空白の除去や Unicode 正規化を行わず、序数で照合する。読み込み、追加、インポート、改名の際に重複を拒否する。参照は選択中の vault で完全一致する項目名を解決し、期待する種類を確認する。同名項目を再登録した場合や vault を選び直した場合も、以降の操作ではその時点の同名項目を解決する。

SSH ユーザー名は接続プロファイルで管理する。vault 項目の追加、編集、秘密鍵のインポート画面にユーザー名欄は設けない。旧形式の `username` プロパティを持つ保管庫はスキーマ検証で拒否する。リリース前の形式のため、移行機能は設けない。[SSH 認証仕様](transports-and-authentication-ja-jp.md#認証とユーザー向けメッセージ)

## インポートした鍵

Q134～Q135 の鍵と格納形式の厳密な許可リストを維持し、新しい形式へのフォールバックを加えない。インポート元のパスフレーズは厳密な UTF-8 のみを使用する（Q161）。正規化、BOM や NUL の付加、エンコーディング選択、別エンコーディングでの再試行は行わない。不正な Unicode と NUL を拒否する。既存の鍵の入力にはマスターパスワードの最小長を適用しない。インポート元のファイルは変更しない。インポート成功時に保存するのは検証済みの正規形式の素材だけ。

ネイティブ解析前に、入力の上限を 1 MiB、復号したオブジェクトを 256 KiB、入れ子を 16、PBKDF2 の反復を 1～10,000,000、bcrypt_pbkdf のラウンド数を 1～1,024、KDF ソルトを 1～64 バイトに制限する。未知の暗号や KDF オプション、末尾の追加鍵オブジェクトは拒否する。対応オブジェクト一つの外側に許すのは枠の空白のみ。これらは初期の処理上限であり、標準の最大値や正確な実行時間を示すものではない。負荷の高いインポートや KDF は、UI とセッションのワーカーから外し、一度に一つだけ実行する。キャンセルは結果を無効にし、ネイティブ処理の完了まで所有権を維持する。使用中のネイティブバッファーを強制解放しない。

負荷の高い検証前に、鍵の種類とサイズを確認する。Ed25519、対応する厳密な名前付き EC 曲線、または 2048～8192 ビットの RSA。初期の RSA インポートでは追加の素数を拒否する。対応する公開鍵、秘密鍵、鍵ペアの妥当性検査を行い、公開鍵素材を導出して比較する。検査が未対応を返したら、文書化された鍵種別ごとの同等の検査を使うかインポートを拒否する。公開鍵と秘密鍵の整合性が不正な鍵は vault に登録しない。パーサー入力、パスフレーズ、復号した ASN.1、秘密情報を含む OpenSSL のエラーデータはログに出さない。

## 秘密情報の所有者と後処理

| 所有者 | 素材 | 所有権の終了 |
| --- | --- | --- |
| マスター入力の操作 | 入力、正規化した UTF-8、確認用コピー | 導出の完了、キャンセル、失敗。実際のネイティブ利用が終了した後。 |
| KDF とラッピング操作 | Argon メモリ、KEK、暫定ルート | 実際の完了。認証済みのルートだけを、正当な役割を持って存続する保管庫の所有者へ移せる。 |
| 選択中の保管庫の所有者 | 接続、管理タブ、対象ファイルの編集ウィンドウで共有するルートと認証済みの暗号化スナップショット | 手動ロック、アプリの完全終了、編集ウィンドウがない状態での選択解除、またはアーカイブの完了。依存する処理が終了した後。 |
| 選択外の保管庫の編集ウィンドウ | 開いたファイルのルートと認証済みの暗号化スナップショット | 対象が選択中になった場合を除く編集ウィンドウの閉鎖、またはアーカイブの完了。依存する処理が終了した後。 |
| ペイロード操作 | 導出鍵と暫定平文全体 | タグやスキーマの検証失敗、または対象の抽出や保存の完了 |
| 認証の所有者 | 選んだ認証情報とネイティブ秘密鍵 | 認証の成功、失敗、キャンセル、切断 |
| インポートの所有者 | インポート元のパスフレーズ、復号鍵、ネイティブ一時オブジェクト | インポートの完了、キャンセル、失敗。実行中のネイティブ呼び出しの終了後。 |
| ファイル操作 | 暗号化した候補ファイルとハンドル | 検証済みの確定、または上限付きの復旧と後処理 |

使える場合は消去可能な所有バッファーを使い、不変の秘密文字列を最小化する。復号済みの全項目を終了までキャッシュしない。バッファーの消去は、ランタイムや OS、ダンプ上のすべてのコピーの消去を保証しない。保管庫の外部変更は既存接続を維持しつつ、古いスナップショットからの新規取得と書き込みをブロックする。選択中の保管庫で外部変更を検出したら、Q108 に従って次回起動までその場所での取得と書き込みをブロックする。編集用としてのみ開いた保管庫で外部変更を検出した場合は、所有権を解放してファイルを開き直した後に新たにロック解除できる。ただし、アプリ自身の保存による独立した部分成立・未解決の制限は解除しない。以下の整合性回復はアプリ自身が進行中の保存に限り、独立した外部変更による制限を解除しない。

保管庫の選択を変更するときは、関連する処理の完了後に所有者の役割を移す。新たに選択したファイルを編集用にロック解除済みで利用できる場合は、その所有者を引き継ぐ。以前の保管庫の所有者は、そのファイルの独立した編集ウィンドウが開いている間だけ維持する。使う所有者がなくなったらルートを解放する。接続用の資格情報は選択中の保管庫から取得する。設定、役割移行、ウィンドウの調整は[保管庫の選択と操作の表示](persistence-and-windows-ja-jp.md#保管庫の選択と操作の表示)を参照。編集用ファイルのロック解除期間は[OWASP のメモリ内の秘密情報に関するガイダンス](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet#25-handling-secrets-in-memory)を踏まえる。

## 保存、バックアップ、復元、障害

保管庫ファイルごとに一つの所有者があり、同時に書き込める処理は一つ。各管理画面からの操作を直列化し、検証済みの確定結果をそのファイルの利用元すべてに反映する。Q108 に従い、置き換え対象から独立したロックで協調する他の書き込み処理を防ぐ。読み込み時に対象の識別情報とダイジェストを取得し、確定前に再確認し、外部変更を検出したら拒否する。同一ディレクトリにユーザーアクセスを制限した暗号化候補だけを書き、フラッシュしてから、一つ前の有効な暗号化バックアップを残して対象を置き換える。新規の対象は上書き禁止で作成する。前世代には `.bak`、候補や復旧名には一意の操作 ID を使う。平文の一時ファイルを使ったり、書き込み失敗の復旧のために保存時の保護を弱めたりしない。

| 結果 | 必須の状態 |
| --- | --- |
| 置き換え前の失敗 | 以前の有効なスナップショットとルート、下書きを保持する。可能な場合は自分の候補だけを安全に閉じて削除する。 |
| 候補が対象にあり、必須の退避もすべて検証済み | 新しい暗号化スナップショットを公開する。パスワード変更では新しいルートを移し、古いルートと KEK を消去する。 |
| 候補が対象にあるが、必須の退避が欠落、不一致、または未検証 | 以前の有効なスナップショット、ルート、下書きを保持し、通常の書き込みと新規取得を停止する。対象の変更と退避の失敗・未解決を分けて報告し、通常の成功や変更なしとして扱わない。 |
| 置き換え API のエラーやファイル名の状態が不明 | 対象、候補、バックアップを調査し、期待するダイジェスト、長さ、認証結果で識別する。解決まで以後の書き込みと取得を凍結する。 |
| 元ファイルが維持された | 古い有効世代を保持し、保存失敗を報告する。保存済みとは表示しない。 |
| 失敗が報告されたが候補が対象になった | 確定扱いの前に検証する。確認なしに置き換えを繰り返さない。 |
| 対象が欠落または破損したが有効なバックアップがある | 明示的な復旧を提示する。空の vault に暗黙に置き換えない。 |
| 別の書き込み元との競合 | 外部ファイルと自分の復旧候補を保持する。自動で統合や上書きを行わない。 |

パスワード変更では、責任を持つ所有者の既存の寿命内で、未完了の作業や結果照合に必要な間だけ、旧ルートと候補ルートを保持する。保存結果が不明だからといって必要なルートを捨てず、ファイル操作の記録のためだけに所有者の寿命を超えて保持しない。キャンセルだけを根拠に反映なしと判断できるのは、保存処理の発行を防げた場合だけ。発行後は実作業の終了と作用の調査を必要とし、キャンセルからロールバックを推定しない。手動バックアップは完成して認証済みの暗号化バイト列をコピーする。明示的な復元は選んだバックアップを検証し、現在のファイルを重複しない復旧名で保持して、同じ保護付きの確定経路を使う。バックアップには作成世代のパスワードを使う。ローカルのファイルロックとダイジェストは、協調しない書き込み元やクラウド上の書き込み元すべてに対するトランザクションや、あらゆる電源断に対する永続性までは保証しない。

### ファイル操作との連携と未解決時の所有権

物理的な保存、調査、後処理の全体には、[共通の検証付きファイル操作](persistence-and-windows-ja-jp.md#結果を検証するファイル操作)を使う。暗号化した不変の候補バイト列、元の編集基準の根拠、既存のアクセス・書き込み排他・退避の要件を渡す。暗号、スキーマ検証、ルートの採用、外部変更による停止の判断は vault の所有者が担う。認証済みの暗号化イメージとの一致はその世代を立証するが、vault ID の一致だけでは未知のバイト列を認証しない。別途選んだ復元元は独立して認証し、復旧コピーには破損していても元のバイト列をそのまま保持する。共通モジュールは平文やルート鍵を所有しない。

候補スナップショットとルートを採用するのは、対象への反映と必須のバックアップ・復旧コピーの両方を検証した後だけ。部分成立では以前の有効なメモリ内状態を保持し、通常の書き込みと新規取得を停止する。既存の端末接続は続ける。パスワード変更では、ディスク上で観測した世代が候補世代であることを正確に伝え、そのファイルに旧パスワードが引き続き適用されるとは表示しない。取得不能だった根拠は再調査できるが、欠落が確定した成果物は調査では修復されない。通常の開き直しではこの制限を解除しない。静止した操作から予約を引き継ぐ明示的な復旧か、次回起動での通常の検証を使う。いずれも以前の部分成立を遡って成功に変えず、独立した外部競合のより厳しい寿命規則に反して制限を解除しない。

未完了の I/O、ネイティブ処理、所有者を必要とする検証は、その所有者を維持する。実作業が終われば、共通契約に従い、暗号化した復旧成果物と秘密でない未解決の根拠を残して、状態を明示した閉鎖・終了ができる。所有者の解放と、その所有者を必要とする新しい調査の受付を直列化する。アプリが続く間は画面を閉じてもファイル操作の記録と対象の制限を維持する。選択中の所有者は既存のアプリ実行期間の役割を維持し、編集専用の所有者は ADR 0008 に従い閉鎖と進行中の処理の終了後に秘密を解放できる。暗号化成果物を調べるためだけに鍵を保持したり、解放した所有者に対して遅延コールバックを開始したり、隠れたアプリ寿命を加えたりしない。

## 保管庫管理の完了操作

一つの深い保管庫管理モジュールが、既存の共有ファイル所有者を使って、作成・ロック解除、項目管理、秘密鍵のインポート、マスターパスワード変更、暗号化バックアップ、復元、アーカイブを完了させる。インターフェースは、秘密を持たずファイルに固定されたコンテキストに、`Unlock`、`Initialize`、`AddPassword`、`EditEntry`、`DeleteEntry`、`ImportPrivateKey`、`ChangeMasterPassword`、`Backup`、`Restore`、`Archive` のような名前付きの完了操作を提供する。名称は例示であり、呼び出し元はロック解除済み所有者を取り出したり、ロック状態別の復元経路を選んだり、直列化と変更処理を組み立てたり、ルートを採用したり、別途一覧更新を要求したりしない。モジュールがこれらの手順と、確定したメタデータ・リビジョンの公開を所有する。

ローカライズしたフォーム、コントロール、ファイル選択、確認・影響表示、表示先、閉鎖は UI の所有者が担う。登録済みの既知の参照の調査とプロファイル保存は既存のプロファイル所有者が、設定保存は設定所有者が担う。公開インターフェースに汎用コマンドディスパッチャー、準備済み操作のライフサイクル、第二の秘密所有者は追加しない。平文エクスポートと初期マクロランタイムは引き続き対象外とする。選択・設定とウィンドウの順序は、設定保存前の Busy 拒否と、有効な選択パスを採用する全経路の調整を含め、[保管庫の選択と操作の表示](persistence-and-windows-ja-jp.md#保管庫の選択と操作の表示)に従う。保管庫操作が編集対象を暗黙に変更したり、設定・プロファイル・保管庫ファイルを一つのトランザクションにしたりしない。

### コンテキスト、受付、観測

コンテキストが持つのは、秘密でない開いた場所、束縛、役割の情報だけ。ルート、平文、独立した暗号化スナップショット、有効なリビジョンを所有しない。コンテキストやメタデータ購読の保持でロック解除期間を延長しない。同じ ID の保管庫コピーでも役割世代と開いた場所を区別し、既存のディレクトリ・別名の調整規則を適用する。A→B→A と選択を戻しても、最初の選択中 A のコンテキストは復活しない。別の役割が共有所有者を維持していても、編集用の束縛はその編集役割の終了とともに終わる。選択中専用のコンテキストは選択変更後の新規要求には無効だが、受け付け済みの操作と存続する編集ウィンドウは固定された対象を維持する。

各名前付き操作は容量を同期的に予約し、ファイルシステムやネイティブ処理を待たず、受け付けた操作 ID・観測用オブジェクト、または型付きの拒否結果を返す。拒否はファイルを変更せず、入力所有権も移さない。受付が移すのは明示的に受領した入力だけで、後の検証を省略する権限ではない。遅延実行でも対象、操作の種類、項目の基準情報（束縛、変更前の項目名、期待する種類、観測済みリビジョン）を維持する。競合する処理はファイルごとの所有者が順序付ける。新しいリビジョンに同名の項目があっても、古い基準情報やコンテキストでの操作は拒否する。待機中の入力、ロック解除への参加、取得済みイメージは所有権と容量計上を維持する。

同じ管理画面で処理中にボタンやキーを連打しても、最初の操作とその確認は一度だけ行う。別画面から同じ金庫に競合する管理操作を指示した場合は、その画面に直ちに使用中と表示する。先行する操作が終わった後に実行するには、利用者が改めて指示する。

項目メニュー、ダブルクリックによる編集、Delete キーによる削除は、同じ形式で操作対象を記録する。メニューを開いた時点、またはダブルクリック・キー入力の時点で、その画面の保管庫への束縛と役割の世代、表示中のリビジョン、対象全件の元の名前と種類を一組にする。ファイルごとの所有者が選択全体をまとめて照合する。書き込み時には、確認中に起きた変更を取り違えないよう、実際に変更する直前にも記録したリビジョンを照合する。

束縛の失効、リビジョンの変更、対象項目の不一致のいずれかを検出したら、全件をそのままにし、選択した項目が変わったことを伝える。検索条件と並び順を保った最新の一覧を表示し、対象を選び直せるようにする。同じ名前の別項目に置き換わった場合も、マスターパスワードの変更で表示行はそのままリビジョンだけが進んだ場合も同様に扱う。一覧更新時に同名の行を選択表示に戻しても、既に記録した操作対象は古いままとする。

通常の呼び出し元は最初の観測を一度待てばよく、監視ループは不要。操作の観測用オブジェクトは、現在状態、明示的な作業キャンセル、同じ操作の結果照合、実リソースの解放も公開する。観測待ちのキャンセルや観測用オブジェクトの破棄は、観測だけを終える。観測には操作 ID と単調増加する観測リビジョン、メタデータには束縛・所有者の世代と有効な保管庫リビジョンを持たせる。古い観測が新しい状態を戻したり、アーカイブ済み・解放済みの束縛を復活させたりしない。通知は現在状態に集約し、後から購読しても無制限の履歴再生なしで現在状態を取得できる。

検証済み候補から秘密でない表示用メタデータを事前に作り、対象と必須の退避の完全な立証を得た後だけ、共有所有者で採用する暗号化スナップショット、有効リビジョン、必要な新ルートとともに公開する。その後で利用元へ通知する。UI への通知失敗は確定を取り消さず、保存失敗に変えず、変更操作の再実行を許可しない。現在状態の読み取りで追いつくことができ、再実行は不要。部分成立では、前述の採用・新規取得の停止と、ディスク上の世代の正確な表示を維持する。

### 操作ごとの必須結果

| 操作 | 必須の完了条件と採用 |
| --- | --- |
| 既存ファイルのロック解除 | 上限内で取得した一つのイメージを認証・検証し、その試行の共有ロック解除状態とメタデータを公開する。ファイルへの反映、暗黙の初期化、全平文項目のキャッシュは行わない。 |
| 存在しないパスへの作成 | 新しい ID・ルートを持つ検証済み暗号化保管庫を非上書きで反映し、対象と該当する退避の立証後だけ採用する。途中で対象が出現したら競合とする。 |
| 空ファイルの初期化 | 確認した同一の通常ファイルを再検証し、保護付き初期化中は元の空ファイルを正確に保持し、対象と必須の退避の立証後だけ採用する。新ファイルの設置に失敗しても、元ファイルの退避は物理的な変更として扱う。 |
| 項目の追加・編集・削除 | 正確な名前・種類・リビジョンを検証する。秘密情報の変更と破壊的操作には既知のプロファイルへの影響確認を適用する。種類の変更は新しい項目にする。完全な反映後にリビジョン・メタデータを採用する。認証済みセッションは接続を維持する。改名は下記の確認に従う。参照した名前が vault にない間は参照を解決できない。 |
| 秘密鍵のインポート | 上限内で取得した一つの入力元イメージと、それに対応するパスフレーズ入力を使う。合意済み格納形式と実際の鍵検証を適用し、検証済みの正規 PKCS#8 だけを反映する。実際の完了までネイティブバッファーを維持し、入力元を変更せず、そのパス・パスフレーズを認証時の依存として残さない。 |
| マスターパスワード変更 | 既存の入力規則と新しいルート・ラッパー・ペイロード暗号化を適用する。完全な立証後にルート・スナップショット・メタデータを採用する。必要な旧・候補ルートは既存の寿命内だけ保持し、ディスク上の候補世代を正確に伝える。古いコピーは古いパスワードを維持する。 |
| 暗号化バックアップ | 認証済みの暗号化世代をそのまま、別途選んだ非上書きの保存先へコピーして検証する。元のリビジョンを変えず、新しいパスワードを暗示する再暗号化を行わない。 |
| 明示的な復元 | 別のバックアップを独立して認証・検証し、以下の ID 条件を適用する。対象が存在すれば元のバイト列を正確に保持し、対象と必須の復旧コピーの検証後にスナップショット・ルートを採用する。編集ウィンドウの対象パスを維持する。 |
| アーカイブ | 確認した入力元だけを同じディレクトリの一意の名前へ非上書きで移動し、実際の入力元・移動先への作用を検証する。完了で旧所有者の利用可能状態を終え、新しい保管庫の作成や選択パス・プロファイル・`.bak` の変更は行わない。アーカイブ先を表示し、了承後に独立した編集ウィンドウを閉じる。 |

改名前に旧名と新名を表示し、古い名前を使うプロファイルやマクロが項目を参照できなくなることを説明する。選択中の vault では、種類に対応するフィールドで旧名を参照する登録済みプロファイルを表示する。無効な認証方式の参照も含め、確認できなかった登録済みプロファイルの件数を示す。［改名して登録済みプロファイルを更新］［改名のみ］［キャンセル］を用意する。選択中でない vault の単独エディターでは改名のみかキャンセルを選ぶ。

vault の改名が検証済みになった後にプロファイルを更新する。確認した登録が残り、ファイルの内容が確認時の版と一致し、編集画面に未保存の変更や保存待ちがない場合に限る。通常の検証付き保存で該当フィールドだけを更新し、更新件数と更新できなかったプロファイルを表示する。各保存結果は独立し、別の保存に失敗しても改名と保存済みの変更は維持する。マクロと未登録のファイルは手動で更新する。

プロファイルカタログは1ファイルずつ処理し、ファイルとファイルの間にはエディターからの保存や再確認も実行できる。各ファイルを更新する直前に、登録、改名の確認時に読み取った版、未保存の編集、そのファイルの保存待ちを再確認する。保存待ちにはエディターを閉じた後も保持している依頼を含む。条件を満たさないファイルはパスと理由を報告してスキップし、次に進む。

書き込みの結果が未確定で再確認できる場合は、そのパスを未確定として報告し、今回のアプリ起動中はカタログが元の操作 ID を保持する。対象プロファイルのエディターで［保存結果を確認］を押すと、その書き込みを照合する。エディターを開いただけでは確認待ちの状態を維持する。再確認はそのファイルだけに適用し、プロファイルへの信頼は付与しない。

書き込みの検証が完了したとき、開いているエディターでその間に編集していなければ、新しい認証情報の参照名を表示し、次の編集には検証済みの版を使う。書き込み開始後に利用者が編集していれば、下書きと元の編集基準を保持する。ファイルが更新されたことを伝え、利用者が保存済みの版を確認してから次の保存に進む。

［vault の管理］を選んだとき、選択中の保管庫が不在または 0 バイトなら、共通のマスターパスワード設定画面を表示する。この画面で設定パスと観測した状態を示し、保存を選ぶと新規作成または保護付き初期化を確定する。キャンセルした場合は対象を維持する。初期化が確認できた場合に管理タブを開く。管理タブ内に個別の作成コマンドは設けない。メニューからのロック解除とプロファイル編集時の認証情報選択でも、不在または 0 バイトなら同じ設定画面を使う。エクスプローラーからの編集には空でない既存の保管庫が必要。

SSH 認証ではどちらの状態も理由を表示し、その保管庫を必要としない方式が利用可能な場合に続行できる。[SSH 認証仕様](transports-and-authentication-ja-jp.md#認証とユーザー向けメッセージ)

入口ごとの初期化後の表示先と、プロファイルの選択画面から管理画面への移動は、ウィンドウ仕様に従う。[エクスプローラーと編集ウィンドウ](persistence-and-windows-ja-jp.md#エクスプローラーと編集ウィンドウ)

マクロのパスワード送信では、不在と 0 バイトのどちらもマクロが捕捉できる認証情報取得エラーとして返す。[マクロの認証情報参照仕様](../drafts/macro-specification.md#profile-password-and-explicit-references)

確認を開いた場所と観測した欠落・空状態に束縛する。空の対象では、変更前に同一の通常ファイルの識別情報と長さゼロを立証する。別ファイルへの置き換わり、非空ファイル、前提条件の取得不能は競合・取得不能とし、より広い上書き権限へ変えない。非空ファイルのロック解除失敗、未対応形式、外部変更による停止、部分成立・未解決の反映は初期化を許可しない。新しい ID・ルートの作成で古い参照を修復したり、設定パスを変更したりしない。

復元では次の ID 判定の分岐を維持する。ロック解除済みの所有者がある場合、独立して認証したバックアップの保管庫 ID が所有者の ID と一致する必要がある。ロック中の復旧では、上限内の元ファイルが v1 のフレーミング・ヘッダー・長さ検証を通る場合だけ、期待する ID を得る。その ID は復元を制約するが、破損した対象を認証したとは扱わない。元ファイルが欠落、ゼロバイト、構造不正なら確立した ID はなく、認証済みバックアップの ID を使う。プロファイル参照や名前から ID を推測しない。識別可能な新しいコンテナバージョン、または v1 のゼロ以外のフラグは拒否し、破損した空の入力として扱わない。対象が欠落した場合の復元は明示的な復旧であり、上記で禁止する暗黙の空保管庫初期化ではない。

外部変更による停止後も、認証済みの暗号化スナップショットが残っていれば、Q108 の暗号化救出コピーを許可する。その保持済み世代だけを、世代と外部変更による停止状態を明示して、別途選んだ非上書きの保存先へコピーする。未知の現在バイト列を信頼したり、認証情報を取得したり、停止中の元ファイルへ書き込んだり、制限を解除したりしない。認証済みイメージが利用不能ならそれを報告し、部分的な根拠から再構成しない。これは暗号化状態での保全であり、秘密情報のエクスポートではない。

### 保護付き初期化、アーカイブ、物理的な結果

通常の反映、退避、結果照合には共通の検証付きファイルモジュールを使う。初期化・アーカイブの限定された内部処理も、関連する入力元、移動先、候補、退避・復旧名すべてについて、同じ内部の対象・名前空間の受付権限を使い、一貫した順序で予約する。別の移動用レジストリーから重複変更を受け付けない。呼び出し元へ予約・書き込み・確定・解放の段階を公開せず、公開の汎用移動操作も追加しない。

空ファイルの初期化では、退避した元ファイル、欠落した対象、設置された候補、復旧素材をそれぞれ報告する。元の実行中に限り、候補設置を防いだ、または設置せずに確実に処理が終了した後、限定的な補償処理として、自分が所有する元の空ファイルを、欠落が確認された元のパスへ非上書きで戻せる。補償結果を検証し、失敗も報告する。競合ファイルを上書きせず、発行済み処理と競合させず、再調査中にこの移動を行わない。反映が不確かな場合は、明示的な復旧に向けた根拠と制限を維持する。退避を立証した後に自分の退避済み空ファイルを削除できなくても、反映失敗ではなく後処理失敗とする。

アーカイブはロック解除や内容認証の成功を前提にせず、既存の上限内で、ロック中、読み取り可能な破損ファイル、未対応のバイト列を保全できる。バイト列の検証、パスワードの復旧、利用可能性の保証はしない。独立した外部変更・部分成立・未解決の制限は引き続き適用する。確認前に、通常ファイルの開いた場所、物理 ID、長さ、内容の根拠を上限内で取得する。ディレクトリ、reparse の対象、取得不能な前提条件は拒否する。ロック解除済み所有者があれば編集基準とも比較し、外部変更なら既存の停止経路を使う。入力元のパスと操作の効果を表示し、その根拠と操作に回答を束縛してから、非上書き移動の発行前に再確認する。入力元が変更・置換されたら承認を無効にし、古い回答で新しいバイト列を移動しない。内部 ID・ダイジェストをユーザーに表示する必要はなく、識別根拠を内容認証と扱わない。

実際の完了と調査まで調整と所有権を維持する。アーカイブ先でバイト列を検証できても、元の名前が欠落している証明にはならない。入力元に別ファイルが現れた、または調査不能なら、判明しているアーカイブの事実を保持し、入力元の競合・未解決状態を報告する。その新しいファイルには触れず、旧所有者から認証情報を使わない。元ファイルが不変で移動先が欠落していることから移動なしと判断できるのは、発行済み処理が終わった後だけ。エラーや観測待ちのキャンセルは移動なしの証拠にしない。移動を盲目的に繰り返さず、識別できないファイルを削除せず、協調しない全書き込み元への耐性を保証しない。欠落が確定した成果物には復旧が必要であり、無限の調査ループで対応しない。アーカイブ完了では依存する作業の終了後に旧ルートを解放し、後の作成は新しい ID を持つ別の明示操作とする。

ドメイン上の結果、観測したファイルの事実、有効状態の採用、制限、成果物、未完了処理を分ける。完了、ユーザーの拒否、発行前の停止、表示先の消失、不正・未対応入力、認証失敗、競合、既知の部分成立、根拠の取得不能を区別する。変更前のアダプター失敗は入力・確認操作の失敗であり、認証失敗や同意ではない。反映後のエラーと検証済み確定は両立し得る。後の外部変更は、以前の検証済み確定を遡って失敗に変えない。入力元の鍵のパスフレーズ要求は保管庫のロック解除失敗ではない。秘密を含まないエラーコードを使い、生の例外、パーサー・OpenSSL のエラーデータ、秘密入力を履歴や診断に残さない。キャンセルだけを根拠に反映なしと判断できるのは、変更処理の発行を防げた場合だけ。発行後に作用なしと判断するには、実作業の終了と物理的な結果の検証を必要とし、キャンセルをロールバックと扱わない。

結果照合は現在の調査に合流し、再暗号化、再反映、基準変更、復元、アーカイブの繰り返しを行わない。後の調査は新しいリソースを取得し得るため、一回分の解放を操作の最終的な終了や現在の静止の証明と扱わない。所有者を必要とする新しい調査と所有者の終了を調整する。実作業の終了後は既存の状態を明示した未解決時の閉鎖方針を適用し、秘密でない根拠と制限は、そのためだけにルートを保持せず画面閉鎖後も残せる。調査の受付を最終的に終えるのは操作の記録を終了するときだけ。隠れたプロセス寿命や受信記録の 5 秒・10 秒のタイムアウトでこれらの規則を延長・置換しない。

### 入力・確認、一時的な秘密、共有ロック解除

入力・確認の調整役は型付き要求を生存する UI の表示先へ送り、回答を操作・要求 ID、対象、関連リビジョン、調査済みの入力元の事実へ束縛する。前提が変われば古い確認・競合の結果とし、自動で基準を変えたり確認を繰り返したりしない。既存の必須確認だけを表示する。正確な登録済み既知参照の影響、取得不能、調査範囲の情報はプロファイル所有者が提供する。未知のファイルを固定済みの全体一覧として扱わない。表示した影響を無効にする既知の変更には新しい確認が必要だが、改名時のプロファイル更新は、一覧を確認した利用者が明示的に選んだ場合だけ許可する。

コントロールと未受領の回答はアダプターが、受領した入力は操作が所有する。受付と清掃責任の受渡しを一度だけ定義し、遅延・重複回答はその時点の所有者が消去して再利用しない。上限付き実行が所有できる前に秘密入力を取得しない。マスター入力・KEK、インポートのパスフレーズ、ペイロード平文、認証の作業コピーは、実際のネイティブ利用が終わった後、既存の利用終了時点で消去する。失敗した下書きの保持は、秘密でない編集と結果情報を残すことであり、パスワード・パスフレーズや復号済みの全項目を残すことではない。再試行では再入力が必要になる場合がある。必要な候補ルートと暗号化復旧イメージは、前述の不確かな結果と寿命の別規則に従う。

ロック解除を実際に必要とする利用元と、結果の観測者を別々に管理する。観測のキャンセルや表示の破棄では、受け付けた操作のロック解除への参加を取り除かない。明示的な停止や、調整された表示先・役割の終了はその利用元を取り除けるが、他の利用元は共有するファイルごとの試行を続ける。共有プロンプトでユーザーがキャンセルした、または失敗した場合は、自動再プロンプトなしで参加中の要求を終える。生存ウィンドウへ表示先を移すか、調整役が入力操作を終了できる。

最後の利用元が離れたら、その試行への受付を止めてキャンセルを要求する。実際の完了までネイティブ作業、入力、ワーカーの容量計上を維持する。新しい利用元は取消し済み試行に参加せず、別の世代で遅延した成功を採用しない。新しい試行は旧作業を安全に終了できた後に新規受付を必要とし、キャンセルによって第二の高負荷ワーカーを作らない。ルートの採用をキャンセルと所有者の終了に対して直列化する。正当な役割を持つ存続所有者へ採用されなかったルートは、遅延コールバックから公開せず、実際の利用終了後に消去する。

共有ロック解除の完了が、それを待つ変更操作の受付解除を必要とする循環待ちを作らない。人の入力、ファイル選択、影響確認を待つ間は全体の高負荷作業枠を占有しない。再入する UI・プロファイル・設定のコールバック前に物理 mutex を解放し、非同期待機中に mutex を保持せず論理的な受付所有権を維持する。

選択中専用の認証情報解決は、要求された正確な認証情報だけを引き渡す。受渡し時に選択世代、リビジョンの利用資格、制限を再確認し、失効した選択に対する抽出結果は届けたり別保管庫で再試行したりせず消去する。正しい受渡し後は認証所有者の既存の寿命に従う。管理更新は既存セッションを切断せず、その平文認証情報を保管庫モジュールにキャッシュしない。

### 容量と記録の終了

実装では、保管庫の反映結果を最大64件、管理画面への結果通知を最大64件まで予約する。秘密を含まないメタデータの共有枠は64 MiBとする。解除済みの所有者が発行した反映の結果が未確定の場合、結果の枠は採用または所有者の破棄まで保持する。画面は確定したメタデータを共有し、その容量は新しいリビジョンに移った後も参照が解放されるまで計上する。

所有者の役割・束縛記録、受付済み・待機中操作、ロック解除の利用元、観測者・購読、入力操作と回答、待機中の秘密入力、ネイティブ・KDF 作業、不変の暗号化イメージ、メタデータ通知、成果物に、有限でバージョン管理する内部上限を設ける。暫定平文とネイティブバッファーもバイト数に含める。受付・割り当て前に容量を予約し、満杯なら新たな作用なしで拒否・延期する。反映の発行前に、結果の根拠、制限、ルート移行、確定メタデータの容量を予約する。判明したディスク変更の報告を、後から予約していない結果記録の割り当てに依存させない。

キャンセル後も実作業を、ルート解放後も秘密でない未解決記録を計上する。十分な場合は小さな根拠記録にする。実際に所有権を共有するイメージだけを一回分として数え、観測者ごとのコピーを暗黙に作らない。購読解除は通知量を抑えるが、作業を取り消したり結果を消したりしない。成果物の計上は共通ファイルモジュールと調整し、所有権を計上から落としたり独立した重複コピーとして数えたりしない。未解決成果物の計上が終わるのは、検証済み削除か明示的な計上先への受渡し後だけ。検証済みの手動バックアップ・アーカイブ先は、所有権と計上先を明示的に移した後、通常の長期保管ユーザーファイルにできる。不確かな保存先、退避・候補ファイルは引き続き計上する。

記録を終了できるのは解決済みで実リソースがない操作だけ。未知・終了済み ID はその事実を返し、変更を再実行しない。TTL、メモリ圧力、コンテキストの作り直し、選択変更で未解決の制限を破棄しない。最終的なユーザーファイルになったことも、未解決の根拠を捨てる理由にはしない。具体的な型名と新しい有限上限は実装開始時に固定し、しきい値を検証する。既存のファイル・KDF・インポート上限は維持する。実測済みの性能や、ネイティブ・OS I/O が有限時間で完了する保証はしない。

## 検証条件

パスワードと秘密鍵の項目をユーザー名なしで追加、編集、再読み込みできることを確認する。旧形式の `username` プロパティを持つ認証済みのペイロードが拒否されることも確認する。

種類をまたぐ同名の項目を、追加、インポート、改名、保管庫の読み込みで拒否することを検証する。改名後は旧名で解決できず、後から同名で登録すると以降の参照で解決できることを確認する。再登録より前に受け付けた編集操作はリビジョン照合で拒否する。

[受け入れ済みの管理操作 23 ケースの検証計画](../drafts/whole-codebase-architecture-deepening.md#candidate-4-verification-plan)は、将来必要な検証であり、実行済みの根拠ではない。通常の名前付き操作、観測、共有メタデータ、選択中の認証情報解決を、実際の保管庫・OpenSSL の動作と独立した既知解・独立に生成した fixture で検証する。自分の書き込み・読み込みの往復や保管庫のモックだけでは不十分。制御可能な内部のファイルシステム、完了・時間、入力・確認、プロファイル・設定のアダプターで障害と順序を再現し、実ハンドル、アクセス規則、別名、実際の完了には Windows・ネイティブ統合検証を維持する。所有権の計測は秘密を記録せず、暗号を置き換えずに解放を観測できる。共有ロック解除・表示先、古い回答、役割と選択の競合、ネイティブ清掃、初期化・アーカイブ・復元の制約、部分成立、通知失敗、結果照合・開き直しによる制限、全容量のしきい値を検証する。Q12～Q16 は設計の準備完了を確定するものであり、実装の許可やテストを実行したという主張ではない。

実装承認後に Argon2/HKDF/GCM の既知解ベクトル、PC 間でのロック解除、ヘッダー各フィールドの AAD の対象範囲、誤ったパスワード、切り詰め、重複や上限超過のある JSON、対応する全鍵格納形式、コピーと復元と分岐した保存、乱数生成の失敗、部分書き込みと置き換えの結果、キャンセル、メモリ所有権を検証する。サポート対象の基準機器で固定 Argon プロファイルを測定する。リリース前に独自形式、ネイティブアダプター、SSH 統合の独立レビューが必要。設計上の問題が見つかったらこの契約に戻って修正する。
