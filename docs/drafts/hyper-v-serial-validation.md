# Testing TabTty serial sessions in Hyper-V

Research and acceptance procedure, 2026-11-19. One Windows 11 x64 guest and a small byte-recording process on the same Hyper-V host can exercise the application's serial path if the guest exposes a working COM device. The operator provides the VM and OS. The validation agent configures the virtual port, prepares the peer, operates TabTty and records the results. [Desktop acceptance inventory](../specification/desktop-acceptance-inventory.md)

On 2026-11-22, the supplied generation 2 guest exposed COM1 and COM2 after a cold boot with Secure Boot enabled and the Hyper-V COM1 `DebuggerMode` set to Off. A host process running elevated connected to `TabTty-QA-COM1`. The normal host token returned Access Denied. Release `13cb898` opened COM1 at 9600 8N1 without flow control, displayed the peer marker and UTF-8 `£`, and sent the expected ASCII marker followed by CR to the host. A second TabTty open was rejected until the first tab released the port. The reopened tab stayed connected when the peer disconnected during observation.

The follow-up with XON/XOFF enabled matched the full 27-byte received Raw file, including NUL, UTF-8 `£`, and CRLF. The host saw no transmitted bytes during the XOFF hold and saw transmission after XON. The long hold lost the first two bytes of the queued marker, and a fresh marker after XON matched in full. This run did not measure byte retention on a hold shorter than the configured 5-second write timeout. Physical signals still require physical observations.

The next run used a 600 ms XOFF hold. The elevated pipe peer received zero bytes during the hold and the complete marker once after XON. The Windows guest disconnected and the host pipe peer reconnected. After a profile review cancellation and an explicit approval, the terminal reopened COM1 and the peer received the new marker without replay. The closed Raw log contained the peer acknowledgment. The virtual run leaves the earlier long-hold behavior and physical signaling unverified.

## VM and port setup

Microsoft's feature matrix lists serial ports for generations 1 and 2 and specifies PowerShell configuration for generation 2. Its terminology overview limits named-pipe application COM ports to generation 1, and its generation guide describes the optional generation 2 UART in a kernel-debugging scenario. The documents leave regular Windows 11 application access uncertain. The test guest uses generation 2 with Secure Boot and vTPM enabled, as required for Windows 11 on Hyper-V. Leave kernel debugging off and cold-start the guest after assigning the pipe. [Feature matrix](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/hyper-v-feature-compatibility-by-generation-and-guest#development-and-test) · [Controllers and ports](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#controllers-and-ports) · [Generation 2 UART](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/should-i-create-a-generation-1-or-2-virtual-machine-in-hyper-v#add-a-com-port-for-kernel-debugging) · [Windows 11 VM requirements](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements#virtual-machine-support) · [Virtual COM cold start](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/attaching-to-a-virtual-machine--kernel-mode-#generation-2-virtual-machines)

With the test guest shut down, use Hyper-V management PowerShell on its host. Replace the example VM name with the supplied name. Choose an unused virtual COM slot and a pipe name unique to this VM. [Set-VMComPort](https://learn.microsoft.com/en-us/powershell/module/hyper-v/set-vmcomport?view=windowsserver2025-ps) · [Get-VMComPort](https://learn.microsoft.com/en-us/powershell/module/hyper-v/get-vmcomport?view=windowsserver2025-ps)

```powershell
$qaVmName = 'TabTty-W11'
Get-VMComPort -VMName $qaVmName
Set-VMComPort -VMName $qaVmName -Number 1 -Path '\\.\pipe\TabTty-QA-COM1' -DebuggerMode Off
Get-VMComPort -VMName $qaVmName -Number 1
```

Cold-start the guest. Find its port in Device Manager and in TabTty. Open a saved profile using the enumerated name, 9600 baud, eight data bits, no parity, one stop bit and no flow control. On the Hyper-V host, connect a local .NET named-pipe client to server `.`, pipe name `TabTty-QA-COM1`, with `PipeDirection.InOut` and a bounded connection timeout. Use binary reads and writes. Record host and guest builds, VM mapping, guest port, package hash and the two byte transcripts. If enumeration or opening fails, capture the mapping, guest device/driver state and error. Confirm cold start and exclusive access before classifying the setup. A host mapping alone provides no application result. [NamedPipeClientStream](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeclientstream) · [TabTty serial contract](../specification/transports-and-authentication.md#serial)

## Observations and limits

| Exercise | Evidence to collect |
| --- | --- |
| Bidirectional payload | Send a known peer sequence containing NUL, high bytes and line endings. Compare its SHA-256 with the guest's closed Raw log and check screen text against the selected encoding. Send known text and Enter from TabTty and compare the host's capture with the expected transmit bytes and configured line ending. Record each direction separately. |
| Ownership and reconnect | While the first tab holds the port, start a second connection using the same profile and verify visible contention. Explicitly disconnect, reopen, exchange fresh markers and check that input from the earlier connection is never replayed. Separately close the pipe client and reconnect it, recording any guest notification and what the next exchange actually delivers. |
| Software flow control and settings | With XON/XOFF selected, independently send XOFF and then XON and observe whether a newly submitted output marker is held and resumed. Record port settings accepted or refused by the guest driver. Report only the behavior observed under the selected virtual configuration. |
| Physical observations unavailable | RTS/CTS and DTR/DSR wiring and gating, electrical baud/parity/stop-bit framing, duration and release of the one-second BREAK, adapter-specific errors or overruns, and USB unplug/re-enumeration require an independent hardware observation for physical acceptance. A pipe close exercises the virtual peer's lifetime. A successful BREAK command records only local acceptance unless the far end independently observes the line. |

Win32 exposes modem-signal changes and receive errors separately from received characters. A named-pipe capture supplies an independent byte record. It does not measure pin levels or timing on a physical UART. Record virtual integration results alongside existing controlled serial tests and keep the physical acceptance cases explicitly unverified with the available equipment. [Win32 communications events](https://learn.microsoft.com/en-us/windows/win32/devio/communications-events) · [SetCommBreak](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setcommbreak) · [ClearCommError](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-clearcommerror) · [Recorded serial test status](../specification/implementation-status.md#native-cutover-acceptance-on-the-current-candidate-2026-11-19)

A fallback on a disposable copy of the Windows guest is a pair of software COM ports connected by a virtual null-modem driver. TabTty opens the first port through the normal profile and a separate peer process opens the second. Repeat the byte and ownership checks and label the driver used.
